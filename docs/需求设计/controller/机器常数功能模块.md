# 《机器常数功能模块》需求设计

> 版本：v1.0　日期：2026-11-08　覆盖系统：MockController（配置与归档中心）、MockRunner（执行端）
> 格式依据：《需求设计》skill（requirement-design）——SR/AR 两级，每个需求三字段。

## 一、范围与决策

**模型口径（用户给定）**：机器常数按被测对象设备建模。标定前原始模型按 `Module.xml` 命名（`Module` 为模型键，如 `SPM_RH.xml`），携带常数名称、单位、结构、默认值、范围；标定后按被测对象 SN 命名 `<SN>_Module.xml`，常数值被替换为实测值。

**来源前提（本轮纠正）**：这些文件**不是 Controller 导出的**，而是由**外部机器常数管理系统**（下称 MCS）导出并交付给 Controller。Controller 是**接收方与归档方**：不生产模型、不定义模型版本号，只做来源核验、分类入库、审批、留档与向 Runner 下发。Controller 自身的导出仅用于备份与迁移，**不再作为导入的信任凭据**。

| 决策 | 内容 |
| --- | --- |
| 唯一事实源 | 模型结构与版本库在 Controller；Runner 只读并缓存，离线兜底 |
| 模型身份 | `(产品, 子系统, PN, modelKey)` 唯一；`Module.xml` 是结构模板，`<SN>_Module.xml` 是标定实例 |
| 标定实例归属 | 按 SN 归档，一个 SN 一个模型实例；同一 SN 重复标定产生新版本，不覆盖旧版本 |
| 包的可信来源 | 只认 MCS 导出包：清单须声明来源系统、批次、导出时间、内容摘要；来源系统走白名单 |
| 本系统导出的备份包 | 导入通道一律拒绝，提示改用备份回滚，避免备份包冒充新模型进入产线 |
| 本轮范围 | 17 条需求（原 15 条 + 外部包契约、SN 实例归档）落到 SR/AR：Controller 侧 10 个 AR、Runner 侧 9 个 AR |
| 不做 | 不作真实 MES 联调、不作真实下位机部署；Demo 用本地模拟下位机与 SQLite 标定库 |

## 二、需求清单

### SR01 外部机器常数接入与模型管理（Controller）

【需求价值】外部常数系统与产线之间需要一道可校验、可审批、可回溯的接入层，避免来源不明或残缺的模型进入测试。
【设计目标】Controller 只接收 MCS 标准包，完成来源核验、模板与 SN 实例分类入库、审批、归档与下发，全过程可按批次追溯。
【需求描述】覆盖外部包全量与部分导入、外部包契约与来源核验、SN 标定实例归档、引入与停用审批及权限、按子系统清单与版本历史、TPS 关联复数模型、标定标识与元数据二级菜单。

#### SR01-AR01 外部标准包全量导入

【需求价值】产线换型或 MCS 重建版本后，一次把模型库铺齐，不必逐条维护。
【设计目标】上传 MCS 标准 zip，来源与内容摘要校验通过后全量替换模板库，旧结构可回滚。
【需求描述】包内须有 MCS 清单（来源系统、批次号、导出时间、内容摘要）与逐文件 SHA-256；来源系统须在白名单、摘要重算一致后，同一事务内替换模板库；SN 标定实例默认保留，除非显式要求清除；任一校验不符整包拒绝，库不动。

#### SR01-AR02 外部包部分导入与备份留存

【需求价值】MCS 只变更少量模型时按子集下发，减少误覆盖与停线风险。
【设计目标】从 MCS 标准包中择取模型导入，覆盖旧模板并保留全部旧结构，可单模型回滚。
【需求描述】包同样须通过来源与摘要校验；可按模型清单或子系统筛选，未选中的模型不动；被覆盖的旧模板写入 `const_backup` 并记录 MCS 批次号、操作人、时间；同一批次重复导入幂等；支持按备份编号回滚单个模型。

#### SR01-AR03 常数模型新建与废弃审批

【需求价值】模型变更需本领域系统工程师把关，避免错误结构流入产线。
【设计目标】新建与废弃均走审批流，通过后线上推送结果，未审批的模型不对外可见。
【需求描述】提交新建或废弃申请时记录申请人、模型键、变更前后结构差异；审批人为该产品所属领域的系统工程师，通过后模型状态变为生效或已废弃并推送通知给申请人与关联用户组；驳回需填理由；待审批期间模型对 Runner 不可见。

#### SR01-AR04 审批权限配置与用户组关联

【需求价值】审批权按领域和职责分配，管理员可随组织调整而调整。
【设计目标】管理员能在界面上配置哪些用户组具备哪类审批权，用户可按组申请权限。
【需求描述】管理员维护审批角色与用户组的映射，粒度到产品领域与审批类型（新建、废弃）；用户提交加入某用户组的申请，由组管理员审批；权限变更即时生效并留审计记录；无权限用户提交审批时给出明确拒绝原因。

#### SR01-AR05 按子系统的模型清单与版本历史

【需求价值】工程人员按子系统直接查模型，不必回 Controller 逐层翻找。
【设计目标】Runner 元数据-机器常数模块内可按子系统列出模型，点击模型展示完整版本历史。
【需求描述】列表按产品、子系统筛选，显示模型键、名称、字段数、当前版本、最近更新时间；点击模型展开版本历史（版本号、变更人、变更类型、差异摘要、生效状态）；数据来自 Controller，离线时用缓存并标注来源。

#### SR01-AR06 TPS 关联复数常数模型

【需求价值】一个测试程序集同时用到多台设备、多套常数，避免拆分 TPS。
【设计目标】创建或编辑 TPS 时可关联任意多个模型，同一模型可重复添加并各自指定用途。
【需求描述】在 TPS 编辑器中以列表维护关联模型，每行指定模型键、绑定别名、取值来源（默认值、指定版本、按 SN 标定值）；同一模型允许重复添加且别名不得重复；保存时校验模型存在且已审批生效；清单随 TPS 导出与下发。

#### SR01-AR07 标定类 TPS 差异化显示

【需求价值】产线人员能一眼区分标定类与普通类 TPS，减少误执行。
【设计目标】TPS 清单每行在名称前或后显示标定标识，位置可配置。
【需求描述】TPS 清单按是否引用标定型模型或含标定步骤判定为标定类，在名称前或后显示「标定」徽标与配色；显示位置由系统设置项控制（前置、后置、仅图标）；与筛选条件联动，可只看标定类 TPS。

#### SR01-AR08 机器常数与工序作为元数据二级菜单

【需求价值】元数据相关内容集中收敛，减少一级菜单膨胀与来回跳转。
【设计目标】机器常数与工序列表成为元数据下的二级菜单，原一级入口保留跳转。
【需求描述】元数据菜单展开后含装备树、机器常数、工序三个二级项；二级菜单显示各自条目数；从旧一级入口访问时自动定位到对应二级项；面包屑与页签标题同步显示二级层级。

#### SR01-AR09 外部包契约与来源核验

【需求价值】防止非授权来源、残缺或伪造的包进入产线模型库，这是接入层的第一道闸。
【设计目标】外部包契约固定可校验，来源、批次、摘要、签名逐项可核，拒绝原因可定位。
【需求描述】清单声明来源系统与版本、批次号、导出时间、内容摘要；来源系统须在白名单；内容摘要按路径与逐文件哈希重算比对；签名可选，配共享密钥时校验 HMAC，未配置时标注"未验签"但不阻断；本系统导出的备份包在导入通道一律拒绝并提示走备份回滚。

#### SR01-AR10 SN 标定实例导入与归档

【需求价值】MCS 已标定好的 SN 数据可直接入库复用，产线不必重复标定。
【设计目标】把 `<SN>_<Module>.xml` 稳定归入标定实例库，绝不覆盖结构模板。
【需求描述】以文件名与 XML 内 `calibrated`/`sn` 双重判定实例，两者矛盾即拒绝并指出文件；实例写入 `const_calibration`，键为 SN + 模型 + 版本，同键新版本追加不覆盖；实例不得进入模板库；可按 SN、模型、批次查询。

### SR02 机器常数在 Runner 的标定与执行（Runner）

【需求价值】标定结果在执行端闭环：能写入、能清除、能校验、能人工确认后再回传 MES。
【设计目标】Runner 支持常数读写与范围校验、单用例人工确认门禁、标定类标识，并提供上位机与下位机两种标定 Demo。
【需求描述】TPS 清单新增机器常数字段与解析方案；执行端提供常数写入、清除与范围校验；单条用例可设 manual check 属性，人工确认后才回传机器常数与测角结果；标定类用例显示标识；标定支持 Windows 本机与 Linux 下位机两种方案。

#### SR02-AR01 TPS 机器常数字段与解析方案

【需求价值】TPS 能声明所需常数及其解析方式，执行端无需硬编码。
【设计目标】TPS 清单可声明常数模型引用与解析器，Runner 按声明解析出可写入的常数集合。
【需求描述】清单新增 `machine_constants` 段，含模型键、别名、解析器类型（xml 契约、kdb 查询、python 回调）与解析参数；解析器输出统一为字段键到值的映射与单位；解析失败给出精确错误位置；旧版 TPS 无该段时按空集合处理。

#### SR02-AR02 常数写入与清除

【需求价值】标定结果与默认值切换无需手工改文件，减少错写。
【设计目标】提供一次写入与一次清除两套能力，操作可批量、可回滚、有审计。
【需求描述】写入按 TPS 声明把常数集合落到目标 `Module.xml` 或 `<SN>_Module.xml` 并生成结果文件；清除将目标模型恢复为默认值或删除该 SN 的标定实例；两者支持按模型、按字段选择范围；每次操作记录操作人、时间、前后值、来源 TPS 与任务号。

#### SR02-AR03 常数值范围校验

【需求价值】超范围的标定值直接拦截，防止错误常数进入后续测试。
【设计目标】写入前逐字段校验范围与单位，越界即拒绝并定位到字段。
【需求描述】按模型定义的上下限、单位、枚举取值校验；越界或单位不符时拒绝整次写入并列出全部违规字段（键、值、允许范围、来源）；支持配置为警告放行并标记；校验结果写入执行记录。

#### SR02-AR04 单用例 manual check 与回传门禁

【需求价值】关键结果由人确认后才回传 MES，避免自动误判流出。
【设计目标】单条用例可设 manual check，确认后机器常数与测角结果才回传，界面同步产生确认按钮。
【需求描述】用例新增 `manual_check` 属性（布尔、可指定复核角色、可指定需确认字段）；执行到该步后暂停，界面显示确认按钮，确认或带理由驳回；未确认的结果滞留本地并标记待确认；确认后一次性回传机器常数与测角结果到 MES，回传失败可重试且不重复。

#### SR02-AR05 标定类用例差异化标识

【需求价值】执行端能快速识别标定步骤，避免与生产结果混淆。
【设计目标】标定类用例在步骤列表、执行面板、结果报告中均带统一标识。
【需求描述】用例或 TPS 声明标定类型后，步骤行显示「标定」徽标、执行面板顶部显示标定模式条、结果报告单独分区；标识与 Controller 侧 TPS 清单标识同一套图标与配色；标识不影响执行顺序。

#### SR02-AR06 Windows 本机标定 Demo

【需求价值】验证上位机直接标定链路，作为标准标定 TPS 的最小可运行样例。
【设计目标】提供一条可运行 Demo，用 python 程序或人工输入填值并生成带 SN 的标定结果文件。
【需求描述】Demo TPS 关联 1 个模型，步骤含 python 程序填值与人工输入两条路径；填值完成后生成 `<SN>_Module.xml`，默认值被实测值替换并附标定时间与操作人；结果文件可被 AR01 解析器读回校验。

#### SR02-AR07 下位机 Linux 标定 Demo

【需求价值】覆盖下位机已部署另一套系统的现场，标定数据从下位机数据库取出。
【设计目标】通过 paramiko 远程登录目标机，查询其数据库标定清单，生成一个或多个常数文件并回传 PC。
【需求描述】目标机连接信息（主机、端口、账号、密钥或口令）取自装备属性配置；paramiko 登录后执行只读查询取得标定数据清单；按清单生成一个或多个常数文件并回传 PC，再走 AR02 写入；连接失败、查询超时、数据缺失分别给出明确错误，不静默降级。

#### SR02-AR08 下位机连接配置

【需求价值】下位机地址与凭据集中管理，避免散落在用例脚本里。
【设计目标】装备属性配置中可维护下位机连接项，Runner 与 Demo 统一取用。
【需求描述】在装备属性配置新增下位机连接项，含主机、端口、用户名、认证方式（密钥、口令）、数据库类型与查询语句模板；凭据加密存储且界面上不明文回显；连通性测试按钮给出往返时延；配置随装备包下发与备份。

#### SR02-AR09 下位机返回数据映射

【需求价值】下位机字段与模型字段口径不同，需要一处可维护的映射。
【设计目标】提供字段映射表，把下位机查询结果稳定映射到模型字段与单位。
【需求描述】映射表在 Controller 随模型维护，含下位机字段名、模型字段键、单位换算系数、缺省值策略；映射缺失时报错并指出未映射字段；单位换算可逆，回传时按原口径还原。

## 三、方案设计

### 3.1 常数模型文件与命名（SR01-AR01、SR01-AR02、SR02-AR01、SR02-AR06）

三类文件分工：

| 文件 | 语义 | 命名 | 由谁产生 | 入库去向 |
| --- | --- | --- | --- | --- |
| 结构模板 | 未标定的原始模型，含名称/单位/结构/默认值/范围 | `<Module>.xml`，如 `SPM_RH.xml` | MCS | `constant_model` |
| 标定实例 | 按被测对象 SN 生成，值被实测值替换 | `<SN>_<Module>.xml`，如 `SC0012345678_SPM_RH.xml` | MCS | `const_calibration` |
| 清单 | 批次元数据、文件索引与哈希 | `manifest.json`（MCS 契约） | MCS | `const_package` + `const_import_log` |

判定规则：文件名形如 `<SN>_<Module>.xml`、XML 内 `calibrated="true"` 且 `sn` 与文件名前缀一致 → 标定实例；`calibrated="false"`、文件名无 SN 前缀 → 结构模板；两者矛盾（文件名带 SN 但 `calibrated="false"`）→ 整包拒绝并指出文件名。

结构模板骨架（沿用现有 `constants.build_xml` 的 XML 风格，保证 Runner 现网解析器可读）：

```xml
<MachineConstants schema="ate.constants.v2" module="SPM_RH" pn="SPM-RH-01"
                  version="2026.11.01" calibrated="false" generatedAt="...">
  <Meta product="1000-A" subsystem="SPM" name="SPM 读头机常数" />
  <Fields>
    <Field key="gain_offset" label="增益偏移" type="float" unit="mV"
           default="0.0" min="-50.0" max="50.0" />
    <Field key="bias_voltage" label="偏置电压" type="float" unit="V"
           default="1.85" min="1.5" max="2.2" />
    <Field key="head_grade" label="读头等级" type="enum" unit=""
           default="B" values="A,B,C" />
  </Fields>
</MachineConstants>
```

标定实例只替换 `calibrated="true"`、`sn`、各 `Field` 的 `value`，并追加 `<Calibration>` 记录（时间、操作人、TPS、任务号、来源）。字段结构不变，因此比对结构哈希等于比对未变字段集合。

### 3.2 数据库变更（SR01-AR01 ~ SR01-AR05）

在现有 `constant_version / constant_model / constant_value` 之上增量建表，不改旧表列：

| 表 | 关键列 | 用途 |
| --- | --- | --- |
| `const_import_log` | id, kind(full/partial), package_hash, file_count, prev_version, new_version, operator, created_at | 全量与部分导入记录 |
| `const_backup` | id, pn, model_key, version, fields_json, replaced_by, reason, operator, created_at | 被覆盖的旧模型备份 |
| `const_request` | id, kind(create/deprecate), pn, model_key, payload_json, status, applicant, approver, reason, created_at, decided_at | 新建/废弃审批单 |
| `const_approval_role` | id, product, kind, group_id, enabled | 审批权限与用户组映射 |
| `const_group_apply` | id, user, group_id, status, reason, created_at | 用户组申请 |
| `const_calibration` | id, sn, pn, model_key, version, values_json, source_tps, task_id, created_at | 按 SN 的标定实例归档 |
| `const_push_log` | id, request_id, channel, target, payload, status, created_at | 审批结果线上推送记录 |
| `const_package` | id, batch_id, source_system, source_version, exported_at, package_hash, content_digest, template_count, instance_count, signature_status, operator, created_at | MCS 批次台账（SR01-AR09） |

导入接口流程：读 zip → 校验总量与文件数（沿用 20 MB / 200 文件上限）→ 逐文件 SHA-256 与清单比对 → 结构校验（字段类型、默认值在范围内、键唯一）→ 写库（全量清空重建 / 部分 upsert 并写备份）→ 事务提交 → 写导入日志。

### 3.3 接口（增量，复用现有 `/api/constants/*`）

现状盘点（已实现，可直接复用）：

| 方法 | 路径 | 现状 |
| --- | --- | --- |

### 3.4 执行端流程（SR02-AR01 ~ SR02-AR07）

```
TPS 载入
  └─ 解析 machine_constants（AR01）
       ├─ 取模型：Controller（在线）→ 缓存 → 本地兜底
       └─ 写入前校验范围（AR03）── 越界 → 拒绝并定位字段
执行用例
  ├─ 普通用例 → 结果入账
  └─ manual_check 用例（AR04）→ 暂停 → 界面确认按钮
        ├─ 驳回（带理由）→ 标记待确认，不回传
        └─ 确认 → 回传机器常数 + 测角结果到 MES
标定用例（AR05 标识）
  ├─ 方案一：Windows 本机（AR06）python 填值 / 人工输入 → <SN>_Module.xml
  └─ 方案二：Linux 下位机（AR07）paramiko → 查询标定库 → 映射（AR09）→ 常数文件 → PC
```

### 3.5 前端改动

- Controller：元数据二级菜单（SR01-AR08）；常数视图增加导入（全量/部分）、审批单、备份列表、版本历史抽屉、标定标识设置（SR01-AR01~AR05、AR07）；TPS 编辑器增加关联模型复选列表与别名列（SR01-AR06）。
- Runner：执行面板增加标定模式条与 manual check 确认按钮（SR02-AR04、SR02-AR05）；设置页增加下位机连接项与连通性测试（SR02-AR08）；元数据-机器常数页按子系统列表与版本历史（SR01-AR05 的 Runner 侧落点）。

### 3.6 两套 Demo 用例（SR02-AR06、SR02-AR07）

| Demo | 模型 | 步骤 | 产出 | 校验点 |
| --- | --- | --- | --- | --- |

## 五、未覆盖范围

- 不覆盖 MCS 的实际导出工具与签名算法：按"来源系统 + 批次 + 内容摘要 + 可选 HMAC"设计，未拿到 MCS 真实密钥与算法。
- 不覆盖 MES 真实接口联调，回传在 Demo 内以本地记录替代。
- 不覆盖真实 Linux 下位机与生产数据库方言（Oracle/MySQL 未验证），Demo 只验证 SQLite 与 SSH 通道。
- 审批推送未确定生产渠道（企业微信/邮件），本轮按可插拔适配器设计，未接生产账号。
- 不覆盖多工位并发导入同一模型库的冲突合并，只做加锁串行。
- 标定值的计量溯源与证书管理不在本轮。
- 元数据二级菜单的移动端适配未覆盖。
- 真实 Linux 下位机成功取数未联调（paramiko 已安装，失败路径为真实 socket 验证，成功路径为单测打桩）。
- MES 回传与审批推送均为 dry-run，未接生产通道。
- 跨进程并发写同一 `<SN>_Module.xml` 未压测；写入为原子替换但无跨进程锁。
