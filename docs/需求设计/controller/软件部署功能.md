# 《软件部署》需求设计

> 版本：v1.0　日期：2026-11-08　覆盖系统：MockController（归档与编排）、MockRunner（部署执行）
> 格式依据：《需求设计》skill（requirement-design）——SR/AR 两级，每个需求三字段。

## 一、范围与决策

| 决策 | 内容 |
| --- | --- |
| 二级目录数量 | 原文写「三个二级目录」但列了四项（装备助手、驱动软件、TPS、三方软件），按**四项**设计；TPS 由一级入口迁入，旧入口保留跳转 |
| 归档维度 | 软件按**产品 + 子系统**归档，不绑测试台类型；一个软件可被本子系统多个 TPS 交叉引用 |
| 部署对象 | 复用现有 `target: {id}`：`local` 表示上位机（默认，且**不出现在设备清单**），其它 id 为设备清单中的别名 |
| 三类软件 | 驱动软件 = TPS 运行依赖，必须可探测与静默安装；装备助手 = 独立装调软件，可独立部署与卸载；三方软件 = 归档分发，可选随 TPS 部署 |
| 现状复用 | Controller 已有 `/api/packages` 归档与 `deploy` 字段；Runner 已有 `deploy.py`（批次互斥、probe、脚本执行、运行库）。本轮在其上扩展目标类型与界面，不重建 |
| Python 三方依赖 | 测试台无外网，全部经 Controller 供给；采用**离线仓 + 子系统只读基础环境 + TPS 锁哈希叠加环境**（见 3.7），否决"打包进 Runner"与"每次用完即删" |
| 不做 | 不做真实下位机与跳板机联调、不做三方软件许可校验、不做驱动签名与数字证书验证 |

## 二、需求清单

### SR01 装备软件归档与部署编排（Controller）

【需求价值】软件类型与依赖关系显式化，部署才可复现、可交叉引用、可追溯。
【设计目标】Controller 具备四个二级目录、按产品-子系统归档、TPS 选择驱动与顺序、部署目标选择与归档助手校验。
【需求描述】覆盖装备助手、驱动软件、TPS、三方软件四类归档；驱动按产品-子系统成清单供 TPS 引用；TPS 记录 deploy 与目标；装备助手带静默部署/卸载脚本与是否需部署属性；归档助手校验格式。

#### SR01-AR01 装备软件一级导航与二级目录

【需求价值】软件按用途分区，找包、授权与责任边界都清楚。
【设计目标】一级「装备软件」下含装备助手、驱动软件、TPS、三方软件四个二级目录。
【需求描述】四个二级目录各有独立清单与条目计数；TPS 从原一级入口迁入，旧入口保留跳转；目录内按产品、子系统两级过滤；支持按名称与版本搜索。

#### SR01-AR02 按产品-子系统归档与交叉引用

【需求价值】同一子系统的软件只归档一份，多个测试台类型可直接复用。
【设计目标】归档键为产品+子系统+软件类型+名称+版本，不绑定测试台类型。
【需求描述】归档时必选产品与子系统；清单按子系统聚合，并显示被哪些 TPS 引用及次数；跨子系统引用默认拒绝，需显式授权后才能被引用；删除前检查引用，仍被引用时阻止并列出 TPS。

#### SR01-AR03 驱动软件归档与探测契约

【需求价值】驱动是 TPS 运行依赖，探测与安装脚本决定部署能否自动化闭环。
【设计目标】驱动包必须带探测与静默安装脚本，Runner 能直接执行并拿到明确结论。
【需求描述】包内 `scripts/probe` 与 `scripts/install` 为必需项；probe 退出码 0 已安装、10 未安装、其它为错误；install 必须静默且可重复执行；归档时校验脚本存在、可执行与退出码约定。

#### SR01-AR04 装备助手归档与静默部署/卸载

【需求价值】装调类软件与测试台无关，需要能静默装、也能干净卸。
【设计目标】装备助手归档可声明是否需要部署，并提供静默部署与静默卸载脚本。
【需求描述】归档属性 `needs_deploy` 决定货架是否出现部署按钮；包内需 `scripts/install`、`scripts/uninstall`、`scripts/probe`；卸载须清理安装目录与注册项；脚本失败返回非零并输出可读原因。

#### SR01-AR05 三方软件归档

【需求价值】第三方依赖同样要版本受控，避免现场临时找安装包。
【设计目标】三方软件归档与分发，不强制脚本，标注是否随 TPS 自动部署。
【需求描述】归档记录厂商、版本、许可类型与安装包；`auto_deploy` 为真时随 TPS 部署，否则只提供手工下载；许可文件单独存放且不出现在公开清单；缺许可仅告警不阻断。

#### SR01-AR06 TPS 选择驱动并定义部署顺序

【需求价值】TPS 依赖哪些驱动、按什么顺序装，必须写在 TPS 里才可复现。
【设计目标】建 TPS 时可选本子系统任意驱动，写入 `deploy` 并支持排序。
【需求描述】`deploy` 行为 `{key, package, mode, target, order?, depends_on?}`；数组顺序即部署顺序，`depends_on` 仍优先做拓扑排序；可多选并拖动排序；保存校验包存在、同子系统、key 不重复；未选驱动时为空。

#### SR01-AR07 TPS 部署目标选择

【需求价值】同一 TPS 可能装在上位机或下位机，目标必须显式可查。
【设计目标】TPS 可从设备清单选部署目标，默认上位机 PC，PC 不出现在设备清单。
【需求描述】目标沿用 `target: {id}`：`local` 为上位机默认且无需选择，其它 id 取自装备属性配置的设备别名；多目标按声明顺序部署；目标设备不在设备清单时保存即报错并指出别名。

#### SR01-AR08 装备软件归档助手

【需求价值】把归档格式要求变成可执行校验，减少现场反复退回。
【设计目标】提供归档助手，按类型校验目录、清单、脚本与命名，产出可直接上传的包。
【需求描述】助手读取源目录生成标准 zip 与 manifest；校验必填字段、脚本、版本号与哈希；不通过时逐项列出缺失；产物可直接上传 Controller 归档；助手与 Controller 校验规则同源。

### SR02 部署执行（Runner）

【需求价值】三类目标各自可部署、可探测、可追溯，失败不掩盖。
【设计目标】Runner 支持本机、下位机、装备助手三种部署路径，均带探测、结果提示与记录。
【需求描述】TPS 部署按钮与执行同级且互斥；部署记录独立 TAB；下位机经 Controller 取包；装备助手货架可部署与卸载，成功清包、失败保留。

#### SR02-AR01 本机 PC 部署

【需求价值】上位机软件一键装进 TPS 工作空间，不再手工拷贝。
【设计目标】点部署后下载到本 TPS 的 workspace 并静默安装，全过程可观测。
【需求描述】按 `deploy` 顺序逐项下载、校验哈希、解压到 `workspace/deploy`；先跑 probe，已安装则跳过；安装失败中止后续并保留现场；部署期间按钮置灰。

#### SR02-AR02 部署按钮与互斥

【需求价值】避免两个测试台同时装驱动导致版本互踩。
【设计目标】部署按钮与执行 TPS 同级，部署期间与其他测试台部署互斥。
【需求描述】按钮位于执行页右上角；同一 Runner 同时只允许一个部署批次；他台部署进行中时按钮禁用并提示占用方；部署结束（成功或失败）立即恢复可用。

#### SR02-AR03 部署结果提示

【需求价值】部署成败要让操作员立刻知道，不能只躺在日志里。
【设计目标】成功与失败都弹窗，弹窗关闭后按钮恢复可用。
【需求描述】成功弹窗显示包名、版本、耗时；失败弹窗显示失败项、退出码与日志路径；弹窗不阻塞后续操作；关闭后可直接跳到部署记录查看详情。

#### SR02-AR04 部署记录

【需求价值】部署历史可追溯，但不应干扰正常测试界面。
【设计目标】部署记录以独立 TAB 呈现，位置与日志模块相近，平时不占主界面。
【需求描述】记录含时间、TPS、目标、包与版本、结果、耗时、操作人；默认折叠，点 TAB 打开；支持按结果筛选与查看日志；只保留最近 N 条并自动清理。

#### SR02-AR05 下位机部署

【需求价值】目标机在隔离网段时，仍要把软件装到位并确认结果。
【设计目标】经 Controller 取包，拷贝到下位机执行部署与探测，回传结果。
【需求描述】Runner 只向 Controller 请求软件，不直连版本服务器；经跳板通道传输并校验哈希；远程执行安装脚本，probe 结果回传；连接失败、传输失败、安装失败分别给出明确错误码。

#### SR02-AR06 装备助手货架部署

【需求价值】装调软件在货架上即可安装，不必回 Controller 操作。
【设计目标】货架卡片提供部署按钮；成功后删除安装包，失败保留并打开资源管理器。
【需求描述】仅在软件下载后可点部署；部署中按钮禁用；成功后删除本地安装包并标记已部署；失败保留安装包并打开资源管理器便于手工处理；结果直接显示在卡片上。

#### SR02-AR07 货架部署状态与卸载

【需求价值】避免重复安装与残留，状态要看得见、也要能撤销。
【设计目标】卡片显示已部署/未部署（仅下载后可见），并提供卸载入口。
【需求描述】状态来自本地部署记录与 probe 复核；卸载调用包内 `uninstall` 脚本，成功后状态回到未部署；卸载失败给出原因并保留记录；未下载的助手不显示部署状态。

### SR03 Python 三方依赖供给（Controller）

【需求价值】测试台无外网，三方包必须可离线、可复现、可隔离地供给，不能靠现场临时装。
【设计目标】Controller 提供离线依赖仓与分层环境制品，TPS 按锁文件取得隔离环境，冲突在发布前拦截。
【需求描述】覆盖依赖登记与离线仓、TPS 依赖锁、子系统基础环境、TPS 叠加环境、离线构建校验、缓存回收与 SDK 兼容边界；同环境多版本冲突与平台不符在发布时即失败。

#### SR03-AR01 依赖登记与离线仓

【需求价值】所有三方包先登记后使用，现场不再临时找包、装错版本。
【设计目标】Controller 维护带平台标签与哈希的 wheel 仓，供测试台离线分发。
【需求描述】登记项含包名、版本、Python 标签、平台标签、wheel 哈希与来源；同名多版本并存；上传即校验 wheel 元数据；缺目标平台标签时拒绝登记并提示应上传的平台。

#### SR03-AR02 TPS 依赖锁文件

【需求价值】TPS 到底用哪些包、哪个版本，必须随 TPS 固化才可复现。
【设计目标】每个 TPS 携带 `python.lock`，发布时逐项校验依赖可供给。
【需求描述】锁文件声明 Python 版本、目标平台、包名/版本/哈希与 Runner SDK 版本范围；发布 TPS 时比对离线仓，缺包或哈希不符即拒绝发布；锁文件任一变更生成新的环境键。

#### SR03-AR03 子系统基础环境

【需求价值】同一子系统常用的大包只装一次，减少重复下载与磁盘占用。
【设计目标】每个子系统维护只读基础环境制品，站点注册时预取。
【需求描述】基础环境含 numpy/scipy 等稳定重包，按 Python 与平台出制品；生成后只读，升级必须新版本号；站点注册时由 Runner 预取并校验哈希；TPS 可复用但不可改写。

#### SR03-AR04 TPS 叠加环境

【需求价值】不同 TPS 的版本冲突被隔离在各自环境内，互不影响。
【设计目标】按锁文件哈希生成不可变叠加环境，同一 TPS 多版本可并存回滚。
【需求描述】环境键为 TPS 编号 + 锁哈希；创建时复制基础环境并只安装差异包；环境只读，复跑直接复用；每个 TPS 保留最近 N 个环境供回滚；不提供"随用随清"。

#### SR03-AR05 离线构建与校验

【需求价值】构建过程不依赖外网，结果必须可核验，否则复现无从谈起。
【设计目标】Runner 在断网环境用本地仓完成安装，构建结果有指纹可校验。
【需求描述】以 `pip --no-index --find-links` 安装；装完比对包清单与锁文件；失败保留临时目录与日志不删；成功写环境指纹，后续启动先校验指纹再运行。

#### SR03-AR06 环境缓存与回收

【需求价值】环境占磁盘，必须有确定性回收策略，又不能删掉还要回滚的版本。
【设计目标】按最近使用与保留数回收，正在使用与基础环境不参与回收。
【需求描述】默认每 TPS 保留最近 2 个锁哈希环境，全局磁盘上限可配；LRU 回收并记录；使用中的环境加锁；基础环境常驻不回收；回收前校验无运行任务引用。

#### SR03-AR07 SDK 兼容边界

【需求价值】TPS 既要装三方包，又要用 Runner 公共能力，边界不清就会互相污染。
【设计目标】三方包与 Runner SDK 分离，SDK 由 Runner 注入并校验版本范围。
【需求描述】叠加环境不继承 Runner 的 site-packages；通过路径注入 `ate_dm`/`ate_drivers`/`ate_rt`；锁文件声明 SDK 范围，越界拒绝启动并提示；SDK 升级不重建三方环境。

#### SR03-AR08 冲突与平台校验

【需求价值】冲突要在发布前发现，而不是现场跑到一半才报错。
【设计目标】同环境同包多版本、平台或 Python 不符时，发布即失败并定位到包。
【需求描述】检测同包多版本、wheel 平台与目标不符、Python 版本不匹配；错误信息列出冲突包与两个来源；允许显式覆盖但必须记录理由与批准人。

### SR04 依赖环境执行（Runner）

【需求价值】环境预取、构建与隔离在 Runner 侧落地，测试结果才可复现。
【设计目标】Runner 在站点注册与 TPS 执行前完成环境预取、构建与校验，失败不静默。
【需求描述】覆盖站点注册预取、执行前就绪检查、运行隔离与 SDK 注入、环境诊断与回收；环境未就绪时拒绝执行并给出缺失清单。

#### SR04-AR01 站点注册预取

【需求价值】把下载放到注册阶段，避免首件测试时长时间等待。
【设计目标】站点注册时预取本子系统基础环境，可查看进度与磁盘占用。
【需求描述】注册请求带产品、子系统与 Python 平台标签；Runner 拉取基础环境制品并校验哈希；已存在同版本跳过；预取失败允许注册成功但标记环境未就绪。


#### SR04-AR02 执行前就绪检查

【需求价值】环境没准备好就执行，只会在中途失败并浪费时间。
【设计目标】执行前校验锁文件与环境指纹，未就绪拒绝执行并列出缺失。
【需求描述】执行前读 `python.lock` 计算环境键；缺基础环境或叠加环境则先构建；构建失败不启动用例；就绪时记录使用的环境键到任务。

#### SR04-AR03 运行隔离与 SDK 注入

【需求价值】用例只能看到自己的依赖与 Runner 公共能力，不能看到别的 TPS 的包。
【设计目标】每条 TPS 用独立解释器路径运行，SDK 按声明注入。
【需求描述】以环境内 Python 启动 pytest 子进程；PYTHONPATH 只含本环境与 SDK 路径；不继承 Runner site-packages；环境变量与临时目录按任务隔离。

#### SR04-AR04 环境诊断与回收

【需求价值】现场出问题要能快速定位是缺包、版本冲突还是环境损坏。
【设计目标】提供环境自检与手工回收入口，输出可读结论。
【需求描述】自检比对锁文件与实际包清单、指纹与目录；输出缺失/多余/版本不符三类结果；支持手工回收指定环境，使用中拒绝并提示占用任务。

## 三、方案设计

### 3.1 归档模型与目录（SR01-AR01、AR02、AR05）

归档键：`(product, subsystem, kind, name, version)`；`kind ∈ {assistant, driver, tps, thirdparty}`。

```
repo/software/<product>/<subsystem>/<kind>/<name>/<version>/
    package.zip          # 原始包（驱动/助手/三方）
    manifest.json        # 平台生成：类型、脚本、哈希、属性
    files/<...>          # 归档助手展开的可读副本（可选）
```

- 驱动：`manifest.scripts = {probe, install}`，`manifest.requires = []`。
- 装备助手：`manifest.scripts = {probe, install, uninstall}`，`manifest.needs_deploy = true|false`。
- 三方：`manifest.vendor/license/auto_deploy`，`scripts` 可空。
- TPS 仍按 `repo/tps/<id>/` 存放，二级目录只是导航与清单视图，不搬动物理路径，避免破坏 Runner 现有取包契约。

### 3.2 数据库（SR01-AR02、AR06、AR07、SR02-AR04）

| 表 | 关键列 | 用途 |
| --- | --- | --- |
| `software_archive` | id, product, subsystem, kind, name, version, path, sha256, size, scripts_json, needs_deploy, auto_deploy, vendor, license, uploaded_by, created_at | 软件归档主表 |
| `software_ref` | id, software_id, tps_id, alias, target, order_no, created_at | 交叉引用与部署顺序 |

TPS 的 `deploy` 字段沿用 Runner 现有形态（`deploy.py` 已在用），只补 `order`：

```json
{"key":"drv_spm","package":"spm_driver@2.1.0","mode":"ensure",
 "target":{"id":"local"},"order":1,"depends_on":[]}
```

- `target.id=local` 表示上位机；其它值必须是设备清单里的别名。
- 部署顺序：先按 `depends_on` 拓扑排序（有环即报错），无依赖关系时按 `order`／数组顺序。
- `mode=ensure` 表示已安装则跳过，与现有探测语义一致。

### 3.4 部署流程（SR02-AR01、AR05、AR06）

```
TPS 部署按钮（右上角，与执行同级）

       ├─ 否 → 禁用并提示占用方
       └─ 是 → 建立批次
            ├─ target.id=local：下载 → 校验哈希 → 解压 workspace/deploy → probe → install

  └─ 已下载？→ 部署按钮
       ├─ 成功 → 删安装包 → 标记已部署
       └─ 失败 → 保留包 → 打开资源管理器
```

### 3.5 归档格式与助手（SR01-AR03、AR04、AR08）

驱动包：

```
package.zip
├── manifest.json        # name/version/kind/product/subsystem/scripts
├── install/...          # 安装介质
└── scripts/{probe,install}
```

装备助手包：


归档助手做四件事：读源目录 → 补全 manifest → 按类型校验（字段、脚本、退出码约定、版本号）→ 生成 zip 与 sha256。校验不通过逐项列缺失，不生成半成品包。

### 3.7 Python 三方依赖的部署形态（SR03、SR04）

#### 方案对比

| 方案 | 冲突隔离 | 离线可行 | 磁盘/下载 | 可复现与回滚 | 运维复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 打包进 Runner 安装包 | 无：全体 TPS 共用一个 site-packages | 最彻底 | 安装包巨大，每次加包都要重打 | 只随 Runner 版本回滚，无法按 TPS 回滚 | 低 | 否决：正是要避免的版本冲突，且把 TPS 依赖绑架到 Runner 发版 |
| 2 每子系统一个 venv | 子系统内仍冲突 | 可行 | 中等：环境数 = 子系统数 | 升级一个 TPS 会改共享环境，其他 TPS 跟着变 | 中 | 不作为唯一方案：同子系统里两个 TPS 要 numpy 1.x / 2.x 时无解 |
| 3 每 TPS 一个 venv，随用随清 | 最好 | 可行 | 每次重建要重新装包，首件慢 | 清掉即无法回滚，日志难复现 | 高 | 方向对，但"随用随清"要改 |
| **推荐：离线仓 + 只读基础环境 + 锁哈希叠加环境** | 最好：环境按锁哈希不可变 | 可行：pip --no-index | 基础环境共享，叠加层只装差异包 | 保留最近 N 个环境，可回滚 | 中 | 采用 |

#### 推荐形态

```
Controller（离线仓 + 制品）
├── wheels/<pkg>/<version>/<pyTag>-<platTag>/*.whl     # 登记即校验哈希
├── base/<product>/<subsystem>/<python>-<plat>/env.zip # 只读基础环境
└── TPS 清单里的 python.lock                           # 锁死版本与 SDK 范围

Runner（站点注册 + 执行）
envs/
├── base/<product>-<subsystem>-<pyTag>/     # 预取、只读、可多版本
└── tps/<tpsId>/<lockHash>/                 # 复制基础环境 + 只装差异包，只读
```

三条关键规则：

1. **环境键 = TPS + 锁哈希**：锁不变就不重建；同一 TPS 可并存多个哈希，回滚只是切换键。
2. **不做"随用随清"**：改为保留最近 2 个 + 全局磁盘上限 + LRU。清空等于放弃回滚与复现。
3. **SDK 不装进环境**：`ate_dm`/`ate_drivers`/`ate_rt` 由 Runner 以路径注入，锁文件只声明兼容范围，避免 Runner 升级把环境搞坏。

#### 为什么不选方案 1 和方案 2

- 方案 1 把"版本冲突"从 TPS 之间搬到了 Runner 安装包里，且每次新增一个包都要重发整包，产线无法接受。
- 方案 2 的共享环境会被任一次 TPS 部署改写：A 测试台跑 TPS1 升了包，B 测试台跑 TPS2 就复现不了上次结果。子系统只是"大多数情况一致"，不是隔离边界。

#### 体量估算（单站点）

| 项 | 估算 |
| --- | --- |
| 基础环境（numpy/scipy/pandas 等） | 300–500 MB / 子系统 |
| 单个 TPS 叠加层 | 20–80 MB（只含差异包） |
| 每站点常驻 | 1–2 个基础环境 + 每 TPS 最近 2 个叠加层 |
