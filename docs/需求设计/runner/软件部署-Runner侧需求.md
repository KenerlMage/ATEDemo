# 《软件部署》Runner 侧需求（SR02、SR04）

> 来源：`controller/软件部署功能.md`（Runner 章节抽取，与 Controller 备份同源）
> 目录约定：Runner `docs/需求设计/` 为统一查阅入口；Controller 工程内保留规范备份。
> 格式：SR/AR 两级，每个需求三字段（需求价值 ≤50 字、设计目标 ≤100 字、需求描述 ≤200 字）。

## 一、范围

本文件只收 Runner 执行侧需求：SR02 三类部署执行、SR04 Python 依赖环境执行。
Controller 侧的归档、编排与离线仓见 `controller/软件部署功能.md`。

## 二、需求清单

### SR02 部署执行（Runner）

【需求价值】三类目标各自可部署、可探测、可追溯，失败不掩盖。
【设计目标】Runner 支持本机、下位机、装备助手三种部署路径，均带探测、结果提示与记录。
【需求描述】TPS 部署按钮与执行同级且互斥；部署记录独立 TAB；下位机经 Controller 取包；装备助手货架可部署与卸载，成功清包、失败保留。

#### SR02-AR01 本机 PC 部署

【需求价值】上位机软件一键装进 TPS 工作空间，不再手工拷贝。
【设计目标】点部署后下载到本 TPS 的 workspace 并静默安装，全过程可观测。
【需求描述】按 `deploy` 顺序逐项下载、校验哈希、解压到 `workspace/deploy`；先跑 probe，已安装则跳过；安装失败中止后续并保留现场；部署期间按钮置灰。

#### SR02-AR02 部署按钮与互斥

【需求价值】避免两个测试台同时装驱动导致版本互踩。
【设计目标】部署按钮与执行 TPS 同级，部署期间与其他测试台部署互斥。
【需求描述】按钮位于执行页右上角；同一 Runner 同时只允许一个部署批次；他台部署进行中时按钮禁用并提示占用方；部署结束（成功或失败）立即恢复可用。

#### SR02-AR03 部署结果提示

【需求价值】部署成败要让操作员立刻知道，不能只躺在日志里。
【设计目标】成功与失败都弹窗，弹窗关闭后按钮恢复可用。
【需求描述】成功弹窗显示包名、版本、耗时；失败弹窗显示失败项、退出码与日志路径；弹窗不阻塞后续操作；关闭后可直接跳到部署记录查看详情。

#### SR02-AR04 部署记录

【需求价值】部署历史可追溯，但不应干扰正常测试界面。
【设计目标】部署记录以独立 TAB 呈现，位置与日志模块相近，平时不占主界面。
【需求描述】记录含时间、TPS、目标、包与版本、结果、耗时、操作人；默认折叠，点 TAB 打开；支持按结果筛选与查看日志；只保留最近 N 条并自动清理。

#### SR02-AR05 下位机部署

【需求价值】目标机在隔离网段时，仍要把软件装到位并确认结果。
【设计目标】经 Controller 取包，拷贝到下位机执行部署与探测，回传结果。
【需求描述】Runner 只向 Controller 请求软件，不直连版本服务器；经跳板通道传输并校验哈希；远程执行安装脚本，probe 结果回传；连接失败、传输失败、安装失败分别给出明确错误码。

#### SR02-AR06 装备助手货架部署

【需求价值】装调软件在货架上即可安装，不必回 Controller 操作。
【设计目标】货架卡片提供部署按钮；成功后删除安装包，失败保留并打开资源管理器。
【需求描述】仅在软件下载后可点部署；部署中按钮禁用；成功后删除本地安装包并标记已部署；失败保留安装包并打开资源管理器便于手工处理；结果直接显示在卡片上。

#### SR02-AR07 货架部署状态与卸载

【需求价值】避免重复安装与残留，状态要看得见、也要能撤销。
【设计目标】卡片显示已部署/未部署（仅下载后可见），并提供卸载入口。
【需求描述】状态来自本地部署记录与 probe 复核；卸载调用包内 `uninstall` 脚本，成功后状态回到未部署；卸载失败给出原因并保留记录；未下载的助手不显示部署状态。

### SR04 依赖环境执行（Runner）

【需求价值】环境预取、构建与隔离在 Runner 侧落地，测试结果才可复现。
【设计目标】Runner 在站点注册与 TPS 执行前完成环境预取、构建与校验，失败不静默。
【需求描述】覆盖站点注册预取、执行前就绪检查、运行隔离与 SDK 注入、环境诊断与回收；环境未就绪时拒绝执行并给出缺失清单。

#### SR04-AR01 站点注册预取

【需求价值】把下载放到注册阶段，避免首件测试时长时间等待。
【设计目标】站点注册时预取本子系统基础环境，可查看进度与磁盘占用。
【需求描述】注册请求带产品、子系统与 Python 平台标签；Runner 拉取基础环境制品并校验哈希；已存在同版本跳过；预取失败允许注册成功但标记环境未就绪。


#### SR04-AR02 执行前就绪检查

【需求价值】环境没准备好就执行，只会在中途失败并浪费时间。
【设计目标】执行前校验锁文件与环境指纹，未就绪拒绝执行并列出缺失。
【需求描述】执行前读 `python.lock` 计算环境键；缺基础环境或叠加环境则先构建；构建失败不启动用例；就绪时记录使用的环境键到任务。

#### SR04-AR03 运行隔离与 SDK 注入

【需求价值】用例只能看到自己的依赖与 Runner 公共能力，不能看到别的 TPS 的包。
【设计目标】每条 TPS 用独立解释器路径运行，SDK 按声明注入。
【需求描述】以环境内 Python 启动 pytest 子进程；PYTHONPATH 只含本环境与 SDK 路径；不继承 Runner site-packages；环境变量与临时目录按任务隔离。

#### SR04-AR04 环境诊断与回收

【需求价值】现场出问题要能快速定位是缺包、版本冲突还是环境损坏。
【设计目标】提供环境自检与手工回收入口，输出可读结论。
【需求描述】自检比对锁文件与实际包清单、指纹与目录；输出缺失/多余/版本不符三类结果；支持手工回收指定环境，使用中拒绝并提示占用任务。

## 五、未覆盖范围

- 三方软件 `auto_deploy` 只落在归档属性，Runner 部署未按该标记筛包。
- 部署记录界面沿用现有实现，未按“与日志并列的折叠 TAB”重做。
- 本机部署沿用既有 deploy.py，本轮未重跑真实静默安装。
- 下位机部署只验证“未配置/未知目标”两类错误，真实 SSH 与跳板机传输未联调。
- Python 依赖分层（SR03/SR04）只完成设计，基础环境制品与断网 pip 安装未实测。
- 未做 sdist 编译；只接受预编译 wheel。
- 未做跨 Python 小版本复用。
