PyInstaller 替代方案选型 · ATE Runner 打包场景

ATE 当前只用 PyInstaller 打一个「纯标准库启动器」ATE_Launcher.exe；后端是「嵌入式 Python + app/ + web/ + runtime/」整包部署。所以这里比较的不是「把整个应用打成 exe」，而是「怎么得到一个双击即用的入口」。

结论先行 3 条现实路线 8 个打包器对比 工控机现场约束优先

一、结论：优先考虑「不打包」

启动器做的事只有三件：定位目录、起 uvicorn、开浏览器。它没必要背一个打包器的复杂度。

路线 A · C# 小启动器 最推荐

复用现有 csc 工具链
  • 构建机只要有 Windows 自带的 .NET Framework 4.x（csc.exe），零额外依赖
  • 产物约 10–20 KB，双击秒开，**不落 %TEMP% 解包**，AV 误报概率最低
  • 和现有 installer\setup.cs 同一套做法，团队已有先例
  • 代价：启动逻辑改一次要重编（逻辑本来就很少）

路线 B · 换 Nuitka 编启动器

保留 Python 写法
  • Python → C → 原生 exe，启动比 PyInstaller 快、反编译更难、误报更少
  • 命令：--mode=onefile（免费版即可）
  • 代价：构建机要装 MSVC/MinGW，首次编译较慢；依赖扫描偶有坑

路线 C · 裸文件启动

零构建成本
  • start-ate.bat + 桌面快捷方式（包里已有）
  • 或 Inno Setup 快捷方式直指 runtime\python.exe app\ate_launcher.py
  • 代价：会出控制台窗口（可设最小化/用 pythonw、VBS 包一层缓解）
判断依据：工控机现场的两个真实痛点是「离线」和「杀毒软件/白名单」。PyInstaller onefile 每次启动都要把内容解到 %TEMP%，这正是企业级 AV 最敏感的行为；而 C# 或 Nuitka 产物没有这一步。体积和启动速度上，C# 启动器也明显占优（~10 KB vs 7.9 MB）。

二、打包器横向对比

工具原理典型产物优点代价 / 风险
PyInstaller
现状		冻结 + bootloader 运行时解包单文件 / 单目录零编译链、hook 生态最成熟、资料最多启动解包到 %TEMP%、体积大、AV 误报多、新版 Python 的 hook 需跟进
NuitkaPython → C → 原生编译standalone 目录 / onefile exe启动快、运行性能更好、反编译难、误报通常更少需 C 编译链（MSVC/MinGW）、编译慢、个别 C 扩展/动态导入要额外处理
cx_Freeze冻结（同 PyInstaller 思路）目录为主，可用 bdist_msi 出 MSI稳定、跨平台、能直出 MSI 安装包不产单 exe；要单文件得自己套 SFX；打包后目录需自己维护
py2exe冻结（setuptools 集成）目录（multifile）纯 Windows、和 setuptools 命令行集成维护节奏慢；单文件支持在 3.11 之后被弱化，3.12/3.13 以目录模式为主
PyOxidizerRust 编译，把解释器静态链进 exe真正的单 exe（不含解包）无解包、启动快、单文件干净配置概念重（Rust/Cargo）、动态导入与数据文件坑多、项目活跃度已下滑
PyApp（ofek）Rust 引导器 + pyproject 配置单 exe，首次运行准备环境配置极小、适合 CLI 工具分发依赖联网拉取（或自带 wheels）、Windows 场景资料相对少
shiv / pex / zipapp打包成 .pyz zipapp单文件 zipapp构建秒级、体积小目标机必须已有 Python —— 与「工控机零依赖」目标冲突
Briefcase（BeeWare）面向桌面应用工程化打包MSI / 安装包GUI 应用流程完整面向 App 工程，不适合「自有嵌入式运行时整包 + 目录启动器」的部署形态

三、安装器 / 分发层（与打包器搭配，不是替代）

工具作用对你的价值
Inno Setup 已用向导式安装包（ate_runner.iss）默认 C:\ATERunner、快捷方式、防火墙规则、静默 /S /DIR=；可直接指向 bat 或 exe，省掉启动器
csc 自编译 Setup 已用构建机没有 Inno 时的兜底安装器同一套 csc.exe 完全可以顺手编一个 C# 启动器，替代 PyInstaller
7-Zip SFX自解压 exe最省事的「绿色包」入口，可配置解压后自动运行 bat
WiX / MSI企业级 MSI 安装客户 IT 有统一分发/组策略要求时更受认可；学习成本高于 Inno
Velopack / Squirrel安装 + 自动更新将来要做「现场自动升级到新版本」时再引入，现在不需要

四、按现场约束怎么选

现场约束优先选避免
构建机干净、不想装 VS / Rust 工具链C# 小启动器（csc）、bat + 快捷方式Nuitka、PyOxidizer（都要重工具链）
企业 AV 严格、常要求加白名单C# 启动器、NuitkaPyInstaller onefile（%TEMP% 解包最容易被拦）
必须绝对离线、目标机零依赖嵌入式 Python 整包（现状）+ 任意启动器PyApp 默认联网拉取、pyz（要目标机有 Python）
希望启动器仍用 Python 写Nuitka --mode=onefilepy2exe（单文件能力弱化）
客户 IT 要 MSI 统一下发cx_Freeze bdist_msi 或 WiX 包住现有整包只交一个裸 exe

五、迁移成本对照（从现状切过去要动什么）

切 C# 启动器新增一个 packaging\launcher\ate_launcher.cs（约 100 行：找根目录 → 自检 → 端口探测 → Process.Start 调 runtime\python.exe -m uvicorn → 轮询 /api/health → Process.Start 开浏览器）；build_package.ps1 里把 PyInstaller 那一步换成 csc /target:winexe，其余流程（web/、app/、runtime/、zip、Setup）完全不动。
切 Nuitka把 PyInstaller 那段换成 python -m nuitka --mode=onefile --assume-yes-for-downloads packaging\launcher\ate_launcher.py；构建机需要 C 编译器，首次构建耗时明显变长，其余不变。
完全不打包删掉启动器构建步骤，Inno 的快捷方式指向 {app}\start-ate.bat（或 runtime\python.exe + 参数，并处理控制台窗口）；ATE_Launcher.exe 从产物里消失，安装包体积也少 7.9 MB。
什么时候该保留 PyInstaller？只有当启动器逻辑继续膨胀（例如要做托盘图标、服务注册、单实例守护、自动更新检查）时，Python 写法 + PyInstaller 的开发效率才有优势。按目前 7 个函数不到的规模，C# 或 bat 更划算。
适用对象：ATE Runner Windows 工控机部署（packaging\build_package.ps1）。 PyInstaller / Nuitka / cx_Freeze / py2exe / PyOxidizer 为打包器；Inno Setup / WiX / 7-Zip SFX / Velopack 为安装与分发层，两者可叠加使用。 具体版本支持与商业版功能范围请以各项目官方文档为准。
