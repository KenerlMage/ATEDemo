ATE PLATFORM / DRIVER DEPLOYMENT DECISION DRV-DEC-001 · 2026-10-18 · v1.0

Architecture decision · driver shelf

驱动不要全塞进 Runner，
也不要把现场交给手工拷贝。

建议采用 “内核随包 + 型号外挂” 的混合形态：传输层、家族契约、通用驱动和基线厂商包随 ATE_Runner 安装；新增型号、客户定制和固件差异走受控的驱动货架。驱动包是独立发布单元，但安装、校验、回滚都在 Runner 内完成。

00

结论

Decision

内核随包，型号外挂；驱动包独立发布，但不独立安装。

Runner 安装包必须自带“能开机、能注册、能仿真、能跑基线”的驱动内核。任何需要跟着仪器型号、客户现场或固件版本变化的内容，都不应该绑定 Runner 的发版节奏。驱动货架负责“长出来”，Runner 负责“装得进、验得过、退得回”。

随 Runner 安装包（Built-in）

  • 传输层、端点解析、错误模型、契约版本
  • 家族契约：scope / dmm / psu / eload / awg / motion
  • 通用 SCPI 驱动与仿真基线
  • 经过认证的基线厂商包
  • 驱动加载器、清单校验、导入时仿真冒烟

独立货架（Shelf）

  • 新增厂商型号、同族衍生型号
  • 客户定制协议、特殊夹具、运动机构
  • 固件差异包、现场补丁包
  • 未随 Runner 认证的第三方驱动
  • 按台架锁版本的驱动组合

一句话判断：驱动是“可替换的仪器适配层”，不是“Runner 的一部分”，但 Runner 必须自带一个可工作的最小驱动集。

01

现状：两套驱动系统

D:\ATE 里现在有两套并行的驱动实现，这是部署方案必须先讲清楚的前提：

位置角色运行时是否使用关键事实
backend/drivers/Runner 当前的生产驱动层是内置 DRIVER_SPECS，按字段权重打分选型，随 app/ 打进安装包
sdk/ate_drivers/驱动 SDK / 目标架构否型号精确派发、driver.json 清单、19 项门禁、scan_dir() 外置扫描；但构建脚本没有把它复制进 Runner

这不是“要不要独立货架”的空白题，而是“把 SDK 已经设计好的货架接进生产运行时”的工程题。当前的主要缺口：

位置现状直接影响
packaging/build_package.ps1只复制 backend/，没有复制 sdk/ate_drivers外置包即使放进目录，运行时也无法 import
backend/drivers/factory.py硬编码 DRIVER_SPECS，打分兜底新增型号要改核心文件；型号写错可能悄悄套用相似驱动
backend/runner_info.pyPAYLOAD_DIRS = app / web / runtime；PRESERVED_PATHS 没有 drivers放在 app/drivers 的外部驱动会被 Runner 升级覆盖
packaging/installer/ate_runner.iss只创建 app/logs/workspace；整个 app 给 users-modify没有正式货架目录；驱动完整性缺少权限边界
sdk/ate_drivers/kit/registry.py已有 scan_dir / merge_specs / resolve_spec能力已具备，缺的是运行时接入和安装入口
关键判断如果驱动放在 app/ 下，Runner 升级会按 PAYLOAD_DIRS 整目录替换，现场驱动和台架适配会一起消失。独立货架首先是为了升级不被覆盖，其次才是发布解耦。
02

三种方案比较

方案适合代价判断
全量随 Runner
所有驱动都进安装包		 型号固定、客户不新增设备、只有一条产线 每加一个型号就要重打整包、重测 Runner、停产升级；驱动回滚等于 Runner 回滚；厂商许可也可能不允许随包分发 不推荐作为长期形态
全量独立货架
安装包不带任何驱动		 驱动团队完全独立、每台机器有专人维护 首次安装是“空壳”；设备注册、仿真、基线验收都依赖外部包；现场版本漂移，出了问题无法判断是 Runner 还是驱动 不推荐
混合：内核随包 + 型号外挂
本文推荐		 多型号、多产线、客户定制 需要一次性的加载器、清单、签名、回滚和 UI 投入；边界必须写死 推荐

全量随包的问题不是“安装包太大”，而是发布节奏被驱动绑架。全量独立的问题不是“不够灵活”，而是首次交付和故障恢复没有底座。混合方案把这两个问题分开处理：稳定性靠内置，变化性靠外挂。

03

推荐架构

推荐目录

<RUNNER_HOME>\                 # 以 D:\ATE\Runner 为例
├── app\
│   └── drivers\               # 内置：随 Runner 升级替换
│       ├── transport.py
│       ├── family\scope.py
│       └── vendors\tektronix_mso\
├── drivers\                   # 货架：升级保留，管理员可写
│   ├── .state\
│   │   ├── active.json        # key -> 版本
│   │   ├── installed.json     # 安装台账
│   │   └── audit.log
│   ├── tektronix_mso\1.6.0\
│   │   ├── driver.json
│   │   ├── driver.py
│   │   └── SHA256SUMS
│   └── acme_scope\0.3.1\
│       ├── driver.json
│       ├── driver.py
│       └── native\acme.dll
├── runtime\                   # 嵌入式 Python
├── web\
├── updates\
├── workspace\
└── ate.db

为什么不是 app/drivers/shelf：因为 runner_info.PAYLOAD_DIRS 明确把 app 当作可替换代码目录。升级时 app 整目录换掉，放在里面的外部驱动会被清空。货架必须在 RUNNER_HOME 根下，并加入 PRESERVED_PATHS。

04

部署方式

独立货架不等于“把 .py 文件拷到目录”。推荐把驱动包做成一个受控的、可验证的发布单元，由 Runner 内的驱动管理器安装。这样现场不需要 Python、不需要 pip、不需要联网。

4.1 发布单元：.atepkg

.atepkg 本质是一个 zip，扩展名用于区分“驱动包”而不是普通压缩包。内容固定：

tektronix_mso-1.6.0.atepkg
├── driver.json          # 清单：型号 / 契约 / 接口 / 后端 / 能力
├── driver.py            # 入口实现（或整个 package/）
├── native\              # 可选：厂商 DLL / 固件配置，不放系统目录
├── SHA256SUMS           # 包内文件哈希
├── signature.ed25519    # 对 SHA256SUMS 的签名
└── README.md            # 版本说明 / 适用型号 / 已知限制

不要为每个驱动做独立 MSI。MSI 适合“机器级安装/卸载”，而驱动是 Runner 的插件：需要按型号派发、按台架锁版本、保留 N-1 回滚。每驱动一个 MSI 会把注册表、卸载项、版本冲突和权限问题放大，最后仍然要回到应用内管理。

4.2 清单示例

{
  "schema": "ate.driver.manifest.v1",
  "key": "tektronix-mso5",
  "version": "1.6.0",
  "family": "scope",
  "api": "1.2",
  "min_platform": "1.0.260101",
  "models": ["MSO54", "MSO56", "MSO58", "MSO64"],
  "interfaces": ["LAN", "SERIAL"],
  "backends": ["native", "visa"],
  "entry": "driver:TekMsoScope",
  "simulate": true,
  "sha256": "...",
  "signature": "..."
}

字段口径沿用现有 sdk/ate_drivers/contract.py 的 ate.driver.manifest.v1；只增加 sha256 / signature / min_platform 的强制校验，不另造一套清单。

4.3 安装流程

  1. 01

    构建与门禁

    SDK 生成骨架，驱动作者只填差异面；python -m ate_drivers.kit.cli check <包> 必须 19/19。门禁不绿，不允许打包。

  2. 02

    签名与打包

    CI 对包内文件算 SHA256，私钥只在发布机本地签名，产出 .atepkg 和发布说明。私钥不进入 Runner，也不进入驱动包。

  3. 03

    进入现场

    统一从内网驱动仓库或 MES 推送获取：先取签名 index.json，再按需下载包。只传包和索引，不在现场 pip install。

  4. 04

    导入与校验

    Runner「驱动管理」选择 .atepkg：验签 → 校验 api/min_platform → 检查型号冲突 → 解压到版本目录。任何一步失败都不激活。

  5. 05

    仿真冒烟

    用 fake transport 跑一遍身份、能力、安全退出；不接真机也能判断“包是否可用”。真机再加 *IDN? 校验。

  6. 06

    激活与锁定

    原子更新 .state/active.json；台架/设备档案记录 driver_key + driver_version。生产环境不自动追最新。

4.4 三种在线分发拓扑

拓扑怎么做适用注意
工位直连Runner 从内网 HTTP 仓库拉 index.json 与包，本地缓存最近一次索引单台工控机、小批量工位首次配置仓库地址；断网时只读缓存，不静默降级
内网仓库文件共享/HTTP 放 index.json + 包，Runner 手动检查更新多台 Runner、同一车间不要运行时自动拉取；生产默认只读缓存
集中分发MES/运维平台推送签名包到各台，Runner 导入多产线、统一版本需要资产台账、审批、回滚窗口

三种拓扑共用同一个包格式和同一套校验，区别只在“包从哪个地址来”。不要为不同产线各做一套驱动格式。

05

加载与版本

5.1 加载顺序

# 启动时只做清单扫描，不 import 所有驱动
builtin  = load_builtin_specs()                  # app/drivers
shelf    = scan_dir(RUNNER_HOME / "drivers")      # 货架
specs    = merge_specs(builtin, shelf)
model    = device_registry["model"]
spec     = resolve_spec(model, specs)            # 精确匹配，无兜底
driver   = resolve_entry(spec)(cfg, mode=mode)   # 用时才 import

合并规则必须写死：

  • 同 key、不同版本：货架版本高于内置且通过签名/兼容校验才允许覆盖；低版本拒绝，避免“现场降级覆盖官方修复”。
  • 不同 key、同型号：启动即报冲突，拒绝激活。不能让“先扫到谁就用谁”。
  • 坏包：只标记该包不可加载，不影响其它包；Runner 启动不因一个坏驱动整体失败。
  • 未登记型号：报 E_NOT_FOUND 并列出可用型号，不回退到“最像的驱动”。

这套规则与 sdk/ate_drivers/kit/registry.py 的 merge_specs / resolve_spec / model_conflicts 对齐；运行时不要另写一套打分逻辑。

5.2 版本锁定

层级记录什么用途
驱动包version / api / min_platform判断能不能装、能不能跑
安装台账.state/installed.json：key、版本、哈希、签名人、安装时间审计与回滚
台架driver_lock：key → 精确版本同一产线结果可复现
设备档案driver_key + driver_version换台/换型号时解释“当时用的是哪个驱动”
运行结果run_result.json 写入驱动版本/后端/接口异常复盘，不靠人回忆
生产规则生产台架默认锁定精确版本，不启用“自动最新”。只有开发/仿真环境才允许“最新兼容版本”。否则同一份 TPS 在两台机器上可能因为驱动升级而产生不同结果。
06

安全与治理

驱动是会被 Runner 进程 import 的代码，等价于“以 Runner 权限执行”。货架一旦可写，就必须有签名、审批和审计，否则独立货架会把安装包的安全边界打穿。

控制点要求原因
签名Ed25519/RSA 对 SHA256SUMS 签名；Runner 内置公钥/信任库防止仓库被篡改与包被替换
哈希安装前校验包内每个文件；解压拒绝路径穿越防止 zip slip 和半包安装
兼容api 主版本不等直接拒绝；min_platform 不满足拒绝避免“装上了跑出错”
权限app/ 和 runtime/ 只读；drivers/ 仅管理员/服务账号可写当前安装器给整个 app users-modify，应收紧
审批生产环境导入驱动需管理员确认；记录操作者与来源防止现场随意装包
回滚保留 N-1（建议 2 个版本）；激活失败自动回退新驱动真机异常时快速恢复
审计audit.log：谁、何时、装了什么、从哪来、哈希质量问题可追溯到具体驱动版本

驱动包不应携带 pip install 脚本，也不应在运行时访问公网。需要厂商 DLL 时，放进包内 native/，按架构（x64）和许可分发；需要 VISA 时，把 NI-VISA/Keysight VISA 当环境前置条件检测，不把整个 VISA 运行时塞进驱动包。

07

迁移路线

不建议一次性重写。现有 sdk 已经把“扫描、清单、精确派发、19 项门禁”做出来了，迁移的关键是把它接到 Runner 运行时，并把旧打分逻辑降为兼容层。

阶段动作产出风险
P0 打通货架构建脚本加入 sdk/ate_drivers 运行时；安装器创建 {app}\drivers；PRESERVED_PATHS 加 drivers；/api/runtime/drivers 返回来源/版本Runner 能扫到外置包，升级不丢不要同时改驱动实现，先打通路径
P1 统一派发把 backend/drivers/factory.py 的 DRIVER_SPECS 映射到 SDK 规格；型号精确匹配；冲突拒绝；保留旧 key 做兼容新增型号不改核心库旧设备档案的 model 字段要先清洗
P2 驱动管理UI/CLI 导入 .atepkg、验签、仿真冒烟、激活、回滚；台账与审计现场可自助装驱动，不靠手工拷贝权限与签名必须先于 UI
P3 多台分发内网 index.json + 镜像；台架 driver_lock；集中推送多产线版本一致、可复现不要做运行时自动升级

如果只能先做一件事：先把 drivers/ 放到 RUNNER_HOME 根下并加入保留清单。否则后面所有货架能力都会被 Runner 升级覆盖，等于白做。

08

验收清单

  • 全新安装：不导入任何外置包，也能看到内置驱动、注册设备、跑仿真基线。
  • 外置包可见：放入签名包后，驱动清单显示 key、版本、型号、来源。
  • 型号冲突拒绝：两个包声明同一型号，启动/导入时明确报错，不静默选一个。
  • 契约不兼容拒绝：api 主版本不匹配或 min_platform 不满足，安装阶段就失败。
  • 仿真冒烟：不接真机，驱动能完成身份、能力、采集/读数、安全退出。
  • Runner 升级保留：升级 app/web/runtime 后，drivers/ 和 active 版本不变。
  • 版本锁定：台架锁定 1.6.0 时，即使货架有 1.7.0 也不会被自动替换。
  • 回滚可用：激活新版本失败或真机异常，一条命令/一个按钮回到 N-1。
  • 审计可查：能回答“这台机器上周装了什么驱动、谁装的、哈希是多少”。
  • 权限正确：普通操作员不能改 app/ / runtime/ / drivers/ 代码。
