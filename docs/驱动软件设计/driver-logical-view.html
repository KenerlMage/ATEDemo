01

视图边界：只回答结构问题

逻辑视图的读者是驱动开发者、TPS 作者与评审人。它要回答的是：设备调用从哪来、经过谁、由谁决定用哪个驱动、失败在哪一层被拦下。它不回答部署形态（单机还是内网仓库）、不回答进程边界（FastAPI 与 pytest 子进程）、也不回答文件装在哪——这些属于开发视图与部署视图。

视图结论

驱动层由「一个契约 + 一张精确类型表 + 两条实现来源」组成，其余都是消费者。

契约是 InstrumentDriver / Driver 基类；类型表是 DRIVER_TYPES 的八个受控键；两条来源是随包内置（backend/drivers/）与货架外挂（<RUNNER_HOME>/drivers）。

不在本视图签名算法细节、安装事务的落盘顺序、升级包替换哪些目录，分别属于货架设计、部署设计与升级设计。
02

上下文：谁在驱动层之外

驱动层不主动发起任何业务动作。它被四类外部角色调用，也只向这四类角色返回结构化结果，不返回面向人的文案。

外部角色向驱动层要什么驱动层返回什么不允许发生
TPS 用例按别名取已连接实例；按动作名执行数值、波形、状态字典驱动里出现业务阈值判断
测试台注册中心受控设备类型清单；类型合法性校验类型键、家族、可用动作前端自由文本填类型
仪器SCPI 命令、二进制块、串口帧应答原文驱动解析失败后返回近似值
驱动仓库包清单、哈希、签名安装结论与错误码未验签就落盘
03

分层与依赖方向

依赖只能向下，不能向上，也不能横向穿透。这条规则的可执行判据是：backend/drivers/* 不允许 import tps_runtime；sdk/ate_drivers 不允许 import backend。

层职责允许依赖代码落点
L4 消费组织测试流程、判定阈值、记录结果L3 门面tps_runtime/conftest_template.py、workspace/<tps>/testcase/
L3 派发把 device_type 精确映射到实现类；做合法性校验L2、L1drivers/factory.py、drivers/__init__.py
L2 实现家族语义：示波器取波形、电源设压设流、负载拉载L1、L0drivers/scope.py、scpi.py、货架包 payload/
L1 传输socket / 串口 / VISA 会话、超时、重连、分块读取L0drivers/transport.py、sdk/ate_drivers/transport.py
L0 契约基类、动作名、结果结构、错误码、版本兼容无drivers/base.py、errors.py、sdk/ate_drivers/contract.py

向下依赖的好处

传输层可以单独做超时与重连测试，不必拉起整个 Runner；契约层可以在没有仪器的机器上跑一致性门禁。

向上依赖的代价

驱动一旦 import 了 TPS 运行时，货架包就会绑死 Runner 版本，现场无法单独升级驱动——这是禁止项，不是风格偏好。

05

一次派发：从别名到 SCPI 写读

以 ctx.driver("dmm") 为例，调用链固定为九步。任何一步失败都返回稳定错误码，而不是降级到"差不多的驱动"。

  1. 1

    TPS 声明别名

    device_config.dmm = {"device_id": "rh-dmm", "role": "dmm"}，别名只在本次运行内有效。

  2. 2

    运行时查注册表

    从 SQLite device_registry 按测试台与 device_id 取出设备行，含 device_type、型号、IP、串口参数。

  3. 3

    工厂查类型表

    resolve_driver_key() 只做一次字典查找；键缺失或非法立即抛 DriverNotFound。

  4. 4

    实例化

    cls(cfg, mode=..., alias=...)；此时不建立任何连接。

  5. 5

    打开会话

    open() 选择 LAN 或串口传输，设置超时，发 *IDN? 完成握手。

  6. 6

    能力校验

    动作不属于该家族时抛 E_UNSUPPORTED，不发送任何字节。

  7. 7

    动作执行

    do(action, **params) 组装 SCPI，写命令、读应答、按结果结构返回。

  8. 8

    阈值判定

    判定发生在 TPS 层（ctx.expect），驱动只给数值。这是职责边界，不是实现细节。

  9. 9

    记录与释放

    结果写入运行目录；close() 关闭会话并释放资源。

为什么强调第 8 步驱动一旦内建阈值，同一台电源在不同 TPS 上就有了不同"合格"定义，测试结果无法复核。
06

状态模型

系统里有两个独立状态机：一个是驱动会话，一个是货架包。它们不共享状态，也不互相引用。

驱动会话

状态进入条件允许动作离开条件
new刚实例化openopen 成功 → ready；失败 → error
ready握手完成do、closedo 期间 → busy
busy正在读写无（重入被拒绝）完成 → ready；异常 → error
error传输或协议失败close、重新 open重新 open → ready
closedclose 完成无终态

货架包

状态含义可见性允许操作
incoming已收包、尚在校验不参与扫描校验通过 → installed；失败 → quarantine
installed已落盘、未被选中可列出，不参与派发activate、uninstall
active该类型当前生效版本参与派发被新版本取代 → superseded；rollback
superseded被更高版本取代，保留用于回滚可列出，不派发activate（回退）、uninstall
quarantine校验失败被隔离仅审计可见人工删除，不再重试加载
07

数据流：device_type 如何贯穿

device_type 是注册记录的一等字段，不是运行时推导出来的。它从录入那一刻确定，之后每一层都只做搬运和校验。

环节字段形态谁写入校验规则
BOM / 预设device_type: "generic-psu"工艺或设备工程师必须在受控清单内
注册请求DeviceConfig.device_type前端下拉框非空且存在于 DRIVER_TYPE_MAP
测试台文件testbenches.json 设备项注册中心保存第二步强校验，缺失即拒存
SQLite 投影device_registry.device_typeate_db与 driver 列并存，后者存解析后的键
TPS 运行row["device_type"]conftest纯读取，不再猜测
工厂cfg.device_type—精确查表，缺失抛 E_NOT_FOUND

旧数据

只做一次类别映射补齐（如"示波器"→tektronix-mso5），映射表外的类别落 generic-scpi。

运行期

不做任何映射、不打分、不看型号相似度。查不到就是查不到。

修正

类型选错由 PATCH /api/testbench/{id}/devices/{dev} 改正，留审计。

当前态与目标态的差距

逻辑视图必须能对上代码。下表左侧是本次改造后已经成立的事实，右侧是尚未接通的环节——不把 SDK 能力写成已上线能力。

能力当前态目标态差距性质
类型选择注册时下拉选 device_type，保存强校验同左已达成
运行时派发内置八类精确查表，无打分同左已达成
缺失类型抛 E_NOT_FOUND，不回退同左已达成
货架路径运行时不扫描 drivers/启动时扫描并合并未接通
货架安装器SDK 有扫描与合并，无安装事务验签、安装、激活、回滚未实现
升级保护PRESERVED_PATHS 不含 drivers升级不动现场驱动待修
包分发无在线仓库HTTP 索引 + 签名包待建
评审口径凡在文档里写"支持货架"的地方，都要同时给出这行差距的状态，否则会被读成"已经能装包了"。
