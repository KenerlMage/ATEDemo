00

摘要与边界

Design position

货架管理供应链，内核管理运行时。

独立货架负责“驱动包从哪里来、是否可信、能否安装、当前激活哪个版本、如何退回上一版”；内核只负责“拿到合并后的注册表，按型号派发并执行”。两者通过 driver.json 与 merge_specs 对齐，不通过共享全局变量或目录扫描耦合。

原则 01

包是发布单元

驱动以 .atepkg 发布，包含清单、实现、哈希与签名；不以单个 Python 文件或独立 MSI 作为现场交付单位。

原则 02

一个 key 一个 active

同一驱动 key 只允许一个激活版本；旧版本仅保留用于回滚，不参与运行时派发。

原则 03

失败不阻断启动

坏包进入隔离区并告警；当前 active 版本与 Runner 启动不受影响。安装失败不得留下半包。

当前资产与缺口

位置已有能力缺口 / 风险本文要求
kit/registry.pyscan_dir / load_manifest / merge_specs / resolve_spec / model_conflicts没有安装事务、状态文件、签名校验；merge_specs 对同 key 的已装包是无条件覆盖保留扫描与合并接口；补版本门槛、状态与信任层
driver.json已有 schema / key / version / api / models / entry / min_platformmin_platform 只声明，加载阶段未执行；signature 字段未验证在安装阶段强制校验兼容性与签名
resolve_entry可按 module:Class 导入每次导入把包目录插入 sys.path，存在模块遮蔽与重复导入风险使用受控加载器；包内模块名带 key 命名空间
build_package.ps1可打 Runner 安装包未复制 sdk/ate_drivers；没有货架目录与保留项运行时随包；drivers 根目录加入保留清单
packaging/installer可创建 app / logs / workspace没有 drivers 目录；整个 app 可被普通用户修改创建货架目录；代码目录只读，货架仅管理员可写

非目标

货架不负责

  • 驱动内部协议、单位、测量算法。
  • TPS 业务逻辑、阈值判定与报告。
  • 设备发现与台架注册。
  • 替代内核的型号派发。

货架必须负责

  • 包格式、清单、哈希与签名。
  • 安装事务、隔离、激活与回滚。
  • 同 key 版本治理与同型号冲突拒绝。
  • 安装台账、审计与离线分发。
01

术语与现状

术语定义边界
货架<RUNNER_HOME>/drivers 下的已安装包集合与状态本地目录；可选由内网静态索引或 MES 提供来源
驱动包一个 .atepkg，含清单、实现、依赖声明、哈希与签名发布单元，不是安装器
激活把某个 key 的某个版本写入 active 指针不复制文件；只改变运行时可见版本
隔离把未通过校验或探测的包移出可加载路径保留证据，不删除原始包
信任库Runner 内置的公钥集合与吊销状态只读，随 Runner 升级；不放在货架目录
台架锁定某测试台固定使用某个 key 的精确版本生产默认；开发/仿真可放宽
索引描述可用包版本、哈希、型号与下载地址的静态清单可选；不是运行时依赖

现状判定

现有 SDK 已经完成“扫描目录、读取清单、合并注册表、按型号派发”的骨架，因此本方案不重新设计包格式，而是在 ate.driver.manifest.v1 之上补齐供应链能力。需要特别修正三点：

问题当前行为目标行为
同 key 覆盖merge_specs 中已装包直接替换内置项，不比较版本只有“版本更高 + 签名有效 + 兼容”才允许覆盖；低版本仅用于显式回滚
最低平台版本min_platform 被读入清单，但加载时未比较 Runner 版本安装/激活前比较，不满足直接拒绝
模块加载resolve_entry 把包目录插入 sys.path使用唯一命名空间与受控 loader；禁止包间模块名冲突
02

逻辑视图

逻辑视图分为“供应链”和“运行时”两个域。供应链负责把可信包放到正确位置；运行时只读取 active 状态与合并后的注册表。两者之间没有隐式调用，所有状态变化都落在 .state 与审计日志中。

2.1 角色与职责

角色职责输入输出
驱动作者实现型号差异、命令表、仿真模型家族契约、型号手册驱动源码、README
构建与门禁脚手架、19 项一致性检查、打包源码、`driver.json`候选包、检查报告
签名服务对包内哈希清单签名候选包、私钥`.atepkg`、签名、发布说明
货架来源存放包与索引；不执行代码签名包可下载的包与索引
Driver Manager检查、验签、暂存、探测、激活、回滚包、信任库、平台版本active 状态、审计记录
内核注册表合并内置与 active 规格，按型号派发active 清单、内置规格DriverSpec、驱动类

2.2 生命周期状态

状态含义进入条件允许的下一步
AVAILABLE包已到达机器，尚未读取文件出现在导入入口或索引命中INSPECTED / REJECTED
INSPECTED清单、布局、文件类型已解析zip 结构合法，`driver.json` 可解析VERIFIED / QUARANTINED
VERIFIED哈希、签名、兼容性均通过信任库命中，`api` 与 `min_platform` 满足STAGED / REJECTED
STAGED已解压到隔离暂存目录并通过探测导入、实例化、仿真冒烟成功ACTIVE / FAILED
ACTIVE当前 key 的派发版本active 指针原子切换成功SUPERSEDED / ROLLED_BACK
SUPERSEDED被更高版本替代，保留用于回滚新版本激活ACTIVE（回滚） / 清理
QUARANTINED校验失败或探测失败，禁止加载哈希/签名/路径/探测异常人工处理；不自动激活
ROLLED_BACK已显式退回旧版本回滚操作成功ACTIVE（再次升级）

状态只描述包的生命周期，不描述仪器会话。仪器会话状态由内核维护；货架不得因为包状态变化而关闭正在运行的会话。

03

版本与信任规则

3.1 合并优先级

场景规则失败行为
同 key，货架版本高于内置签名有效、API 兼容、`min_platform` 满足时允许覆盖否则保留内置，记录拒绝原因
同 key，货架版本等于内置不覆盖；视为重复包安装成功但不改变 active
同 key，货架版本低于内置禁止普通安装；仅允许显式回滚到已安装旧版`E_PKG_VERSION`，当前 active 不变
不同 key，声明同一型号拒绝激活；保留当前 active，列出冲突双方`E_PKG_CONFLICT`
同 key 多版本并存仅一个 active；其余为 SUPERSEDED，可回滚不允许同时参与派发
台架锁定版本缺失拒绝运行该台架，不回落到最新版`E_PKG_PINNED_MISSING`

3.2 兼容性判定

# 安装/激活前必须全部通过
manifest.schema == "ate.driver.manifest.v1"
api.major == platform.API_VERSION.major
api.minor <= platform.API_VERSION.minor
manifest.min_platform <= runner.version
all(model in manifest.models for model in required_by_bench)
manifest.models 无重复（归一化后）
entry 可解析，且类继承对应 family 契约
manifest.interfaces ⊆ {LAN, SERIAL}
manifest.backends  ⊆ {native, visa}

兼容性检查必须在解压前和激活前各执行一次：前者防止坏包进入暂存区，后者防止平台在安装后被降级或替换。两次检查使用同一份规则实现，不允许 UI 与后端各自判断。

3.3 信任链

环节校验对象算法 / 规则失败处理
包完整性包内每个文件SHA-256，路径规范化，排序后写入 `SHA256SUMS``E_PKG_HASH`，隔离
发布者身份`SHA256SUMS` 的字节Ed25519；`signature.ed25519` 为 base64；`key_id` 指定信任库条目`E_PKG_SIGNATURE`，隔离
信任库公钥、吊销状态、有效期Runner 内置只读；升级时整体替换；支持双 key 轮换未命中即拒绝；不得现场导入私钥
索引`index.json` 自身与包相同的签名流程；记录包哈希与大小索引不可信时仍可手工导入，但包仍需验签
运行时加载模块命名空间与入口每个包使用唯一包名；loader 不修改全局 `sys.path``E_PKG_LOAD`，不激活
信任边界签名包被视为受信代码，仍应在独立子进程中完成导入与仿真探测；一期不以操作系统级沙箱为前提，但必须限制导入时间、文件访问范围与网络调用，并把探测失败与运行时失败分开记录。

3.4 版本锁定

生产台架使用 `driver_lock` 固定 `key → version`。运行时解析规格时，先读取台架锁，再在 active 集合中查找；锁定的版本不存在时直接失败，不回落到更高版本或 `generic-scpi`。开发/仿真环境可以不锁定，但必须在运行记录中标记 `unlocked`。

4.3 `driver.json` 字段

字段类型必填约束 / 说明
schemastr是固定 `ate.driver.manifest.v1`
keystr是`^[a-z0-9][a-z0-9._-]*$`；同 key 单 active
versionstr是语义化 `x.y.z`；写入运行记录
familystr是`scope/dmm/psu/eload/awg/motion/passive/generic`
apistr是`1.2`；major 必须相等，minor 不得高于平台
min_platformstr建议Runner 最低版本；安装前比较
entrystr是`包.模块:类名`；类必须继承对应家族
label / vendorstr建议UI、报告、审计显示
modelslist[str]是归一化后唯一；不可为空；型号派发唯一依据
interfaceslist[str]是`LAN` / `SERIAL` 的非空组合
backendslist[str]是`native` / `visa` 的非空组合；不得写 `auto`
capabilitieslist[str]建议与类声明一致；UI 与能力过滤使用
simulatebool是上架要求 `true`；离线验收依赖
dependslist[str]否其它 key 的精确版本约束；一期仅允许同家族
key_idstr是信任库公钥标识；用于轮换与吊销
signaturestr否兼容旧清单；正式包以 `signature.ed25519` 为准

05

安装与回滚

5.1 安装事务

  1. 01

    获取互斥锁

    锁定 `.state/.lock`；同一时刻只允许一个安装、激活或回滚事务。锁超时返回 `E_PKG_BUSY`，不排队阻塞 Runner。

  2. 02

    结构检查

    检查 zip 条目数量、单文件与总解压大小、路径分隔符、绝对路径、`..`、符号链接、可执行文件类型；拒绝路径穿越与 zip bomb。

  3. 03

    清单检查

    读取 `driver.json`，校验 schema、必填字段、key/version 格式、models 去重、interfaces/backends 合法、entry 形状。

  4. 04

    信任与兼容

    校验 `SHA256SUMS` 与 `signature.ed25519`；检查 `api`、`min_platform`、Runner 版本、目标台架锁定；任一失败即拒绝。

  5. 05

    冲突检查

    把候选包与当前注册表合并，执行 `model_conflicts`；同型号不同 key、同 key 低版本普通安装均拒绝。

  6. 06

    暂存解压

    解压到 `.incoming/<key>-<version>-<nonce>/`；不直接写入最终目录，不覆盖现有版本。

  7. 07

    子进程探测

    在独立进程中导入入口类，构造仿真驱动，执行 `identify` 与全部声明能力；设置超时与内存上限。探测失败则隔离，不激活。

  8. 08

    原子落位

    把暂存目录重命名为 `drivers/<key>/<version>`；更新 `installed.json`；按需切换 `active.json`；写审计。

  9. 09

    失败清理

    任何步骤失败：删除暂存目录，保留原 active；坏包移入 `.quarantine/` 并记录原因。不得留下可被扫描到的半包。

5.2 激活与回滚

# 激活：只改指针，不复制文件
candidate = installed[key][version]
assert candidate.status in ("staged", "superseded")
assert verify(candidate)                       # 激活前再次验签/哈希
new = dict(active)
new[key] = {"version": version, "digest": candidate.digest}
atomic_write(active_json, new)                 # temp + os.replace
audit("activate", key, version, digest)

# 回滚：只能回到仍在本地的上一版
previous = installed[key].previous_active
assert previous.exists and verify(previous)
atomic_write(active_json, {**active, key: previous.ref})
audit("rollback", key, previous.version, previous.digest)

激活失败时，旧 `active.json` 保持不变；如果 `os.replace()` 成功但运行时加载失败，下一次启动应回退到上一个可用版本，并记录 `activation_failed`。保留版本数建议为 2（当前 + 上一版），磁盘占用与回滚能力平衡。

5.3 离线与多台分发

方式流程适用约束
手动拉取在驱动管理中检查仓库 → 选版本 → install单台工位包仍需验签；私钥不进入现场
静态索引读取签名 `index.json` → 下载/复制包 → 同一安装事务车间内多台 Runner索引与包分离签名；不要求常驻服务
MES 推送运维平台下发包与目标台架清单多产线统一版本需要资产台账、审批、回滚窗口

三种方式共用同一包格式、同一验签实现、同一状态机。差异只在“包如何到达机器”，不得为离线与在线各维护一套安装逻辑。

安全与测试

6.1 安全控制

控制点要求对应风险
签名Ed25519 对规范化 `SHA256SUMS` 签名；信任库只读；支持 key_id 轮换与吊销包被替换、内网仓库被篡改
哈希逐文件 SHA-256；解压前校验；拒绝未列出的文件半包、夹带文件
路径拒绝绝对路径、`..`、符号链接、NTFS ADS、保留设备名zip slip、覆盖系统文件
资源限制包大小、条目数、解压后总大小、单文件大小、探测超时zip bomb、导入卡死
权限`app/`、`runtime/` 只读；`drivers/` 仅管理员/服务账号可写；`.state` 与包目录分离普通用户替换驱动
代码执行禁止安装脚本；入口只在探测与激活后导入；子进程隔离与超时恶意包获得 Runner 权限
审计记录操作者、来源、包哈希、key_id、结果、时间无法追溯现场变更

6.2 错误码

错误码场景处置
`E_PKG_LAYOUT`zip 结构非法、路径穿越、符号链接、超限拒绝并隔离
`E_PKG_MANIFEST`清单缺字段、格式非法、models 为空或重复拒绝，提示字段
`E_PKG_HASH`文件哈希不匹配、缺失文件、额外文件隔离，保留证据
`E_PKG_SIGNATURE`签名无效、key_id 未授信、证书吊销隔离，提示信任库
`E_PKG_COMPAT`api 不兼容、min_platform 不满足拒绝，提示升级方向
`E_PKG_VERSION`同 key 低版本被当作普通安装拒绝；仅显式回滚可用
`E_PKG_CONFLICT`同型号被不同 key 声明拒绝，保留当前 active
`E_PKG_PROBE`入口导入失败、仿真冒烟失败、超时隔离，记录堆栈
`E_PKG_LOAD`入口命名空间冲突、受控加载器拒绝导入拒绝激活，保留当前 active
`E_PKG_BUSY`安装/激活锁超时事务终止，可重试
`E_PKG_STATE`状态文件损坏、锁超时、原子替换失败停止事务，人工恢复
`E_PKG_PINNED_MISSING`台架锁定版本不在本地拒绝运行该台架

6.4 与内核的边界测试

货架测试不得只验证“文件复制成功”。必须把安装后的包交给内核注册表，验证 merge_specs 的覆盖规则、resolve_spec 的型号命中、model_conflicts 的冲突检测和 resolve_entry 的导入结果。安装成功但内核无法派发，视为安装失败。

07

演进与验收

7.1 分阶段落地

阶段范围行为变化退出条件
S0 目录与状态创建 `drivers/`、`.state/active.json`、安装台账；扫描器排除临时目录Runner 可识别货架；升级保留空货架启动正常；升级不丢状态
S1 安装事务inspect / install / activate / rollback；哈希与清单校验现场可导入包，不再手工拷贝正常包可激活；坏包被隔离
S2 签名与信任Ed25519、信任库、key_id、索引签名安装必须验签；私有包走审批篡改包全部拒绝
S3 版本治理同 key 版本门槛、台架锁定、冲突拒绝、回滚窗口生产版本可复现低版本/冲突/锁定缺失均按预期失败
S4 多台分发静态索引、MES 推送、审计汇总多产线统一版本离线与在线共用同一包格式

7.2 验收判据

  • 包可验证：签名、哈希、清单、入口四类检查均有独立错误码。
  • 安装原子：失败不留下可扫描的半包，当前 active 不变。
  • 激活可控：同 key 单 active；旧版本保留且可回滚。
  • 冲突拒绝：同型号不同 key 在激活前失败，并列出双方。
  • 契约前置：api 与 min_platform 在安装阶段判定。
  • 内核可派发：安装后的包能被注册表解析到正确型号。
  • 升级保留：Runner 升级后货架与状态不丢失。
  • 在线可用：工位直连、车间镜像、MES 推送使用同一验签逻辑。
  • 审计完整：可回答谁在何时安装/激活/回滚了哪个哈希。
  • 权限隔离：代码目录只读，货架目录仅管理员可写。

7.3 关键风险

风险影响控制
把货架做成第二个包管理器依赖、卸载、注册表污染，难以回滚只管理 `.atepkg` 与状态；不执行任意安装脚本
签名实现与清单实现分叉同一包在不同入口判断不一致单一 `trust.py` 与 `load_manifest` 实现；UI 不重复判断
同 key 无条件覆盖现场旧版覆盖官方修复版本门槛；低版本仅显式回滚
包目录污染模块命名空间不同厂商同名模块互相遮蔽包名带 key 前缀；受控 loader；禁止全局 `sys.path` 注入
探测阶段执行恶意代码Runner 权限被滥用签名信任 + 子进程 + 超时 + 最小环境；后续再评估 OS 沙箱
