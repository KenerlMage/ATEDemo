ATE Runner · 驱动战略 · 决策备忘 04

共享包怎么开发、怎么部署

一句话：包是带清单的 zip，开发走「一个代码库、路径触发、契约门禁」，部署走「离线介质 + 每台一份 lock 文件」。不引入 pip、不在现场构建、不做运行时热插拔 —— 因为产线离线，任何需要联网的环节都会变成事故。

前置 · 备忘 03 的三层发布物 现状 · 驱动随 Runner 一体发布 日期 · 2026-11-08
Verdict

开发侧：所有包放一个私有代码库，按目录切包、按路径触发 CI；每个包必须过「契约一致性 + 仿真回归 + 双台型用例」三道门禁才能出包。

部署侧：包以 zip 形态落在 packages/<name>/<version>/，同机多版本共存；每台测试台有一份 bench.lock.json 锁定解析结果，安装与回滚都只动这份文件，从不重装平台。

01包的形态：带清单的 zip，自带私有依赖

不用 wheel + pip。原因很实际：内嵌 Python 运行时装 pip 要多一层引导，离线 wheelhouse 要同步维护，多版本共存还得靠 --target 各装一份 —— 换来的好处在 ATE 场景里几乎没有。

# 一个共享包解压后的样子
optical-power-meter__exfo-pm-100/1.4.2/
├── manifest.json          # 身份 + 契约 + 兼容 + 依赖 + 签名
├── pkg/
│   └── exfo_pm100/        # 驱动实现，实现 L1 能力契约
│       ├── __init__.py
│       └── driver.py
├── vendor/                # 该包私有的第三方依赖（自带的，不共享）
│   └── pyvisa/ ...
├── conformance/           # 随包发布的契约测试，安装后可本地跑
│   └── test_contract.py
└── CHANGELOG.md
// manifest.json
{
  "name": "exfo-pm-100",
  "version": "1.4.2",
  "capability": "optical-power-meter",
  "contract": "2.3",                 // 实现的能力契约版本
  "runtime": { "runner": ">=1.6 <2.0", "python": "3.13" },
  "owner": "光测组",
  "entry": "pkg.exfo_pm100:Driver",
  "vendor_deps": ["pyvisa==1.15.0"],
  "simulate": true,                  // 无硬件可跑，CI 依赖这一条
  "sha256": "…",
  "signature": "ed25519:…"
}

清单里三个字段决定了整套机制能不能运转：capability（台型按它解析）、contract（和平台的契约版本对不对得上）、simulate（没有硬件能不能回归）。缺任何一个，这个包在几百台上就是不可验证的。

02开发：一个库、路径触发、三道门禁

包多了不要拆成几十个仓库 —— 共享契约测试、共享 CI、共享依赖基线，拆开就享受不到了。用 monorepo，按目录切包，按路径触发流水线。

# 代码库结构
ate-drivers/
├── contracts/               # L1 能力契约（平台发版物，包只依赖不修改）
│   ├── optical_power_meter.py
│   └── camera.py
├── packages/
│   ├── exfo-pm-100/         # 每个目录 = 一个包 = 独立版本
│   ├── keysight-34461a/
│   └── basler-pylon/
├── kit/                     # 契约一致性测试、仿真替身、用例回归夹具
└── ci/
流水线五段，后两段是硬门禁
阶段做什么失败即阻断耗时量级
1 · 静态lint、类型、禁止 import 平台内部私有模块是秒级
2 · 契约跑 kit/conformance：方法签名、返回体、异常语义是否满足能力契约是秒级
3 · 仿真在 simulate=true 下跑包内自测与行为断言是分钟级
4 · 双台型回归拉两个真实使用该包的台型用例集，用仿真硬件跑通是十分钟级
5 · 出包打 zip、算 sha256、签名、写 CHANGELOG、更新私有索引是分钟级

第 4 段是共享包和普通驱动包的分水岭。只跑自己那份单测的包，改一次就可能踩坏另一个台型 —— 这是几百台规模下最贵的错误，代价是产线停机而不是 CI 红一次。

03部署：离线介质 + 每台一份 lock

产线没有外网，所以「安装」这件事必须能在断网、无管理员、无 pip 的前提下完成。设计上把它拆成三个动作：放文件、改 lock、重启服务。

# Runner 安装目录
ATERunner/
├── app/backend/            # 平台基线（含基线驱动包）
├── packages/               # 共享包，多版本并存
│   ├── exfo-pm-100/
│   │   ├── 1.3.9/
│   │   └── 1.4.2/
│   └── basler-pylon/
│       └── 8.1.2/
├── benches/
│   └── BENCH-017/
│       └── bench.lock.json   # 这台测试台的确定解析结果
└── var/packages.index.json # 私有索引的本地快照（离线可用）
// bench.lock.json —— 安装与回滚只动这个文件
{
  "bench": "BENCH-017",
  "station_type": "optical-coupling-01",
  "runner": "1.7.3",
  "resolved": [
    { "capability": "dmm", "package": "keysight-34461a", "version": "2.3.1", "sha256": "…" },
    { "capability": "optical-power-meter", "package": "exfo-pm-100", "version": "1.4.2", "sha256": "…" },
    { "capability": "camera", "package": "basler-pylon", "version": "8.1.2", "sha256": "…" }
  ],
  "locked_at": "2026-11-08T12:00:00+08:00"
}
三种安装通道，主路径是第二种
通道怎么做适用校验
随平台预置基线包打进安装包，装完即用每个柜都有的设备安装包签名
离线包导入U 盘或内网共享放 zip → 界面「导入驱动包」→ 解压校验 → 重算 lock → 重启服务共享包（主路径）ed25519 签名 + sha256 + 索引比对
内网索引同步Runner 定时拉 packages.index.json，只提示可用更新，仍需人工确认有内网文件服务的厂区同左，且需索引签名

关键约束写死两条：安装过程中不编译、不联网、不装 pip；解析结果一旦写入 lock 就固定，运行期不再自动升级。自动升级在产线上不是便利，是不可控变量。

04版本与共存规则

共享包最常见的翻车不是写错代码，是版本语义混乱导致「升级一个、坏三个」。规则要少，但要硬。

  • 版本语义MAJOR 跟着能力契约走（契约不兼容才跳）；MINOR 是新增能力或行为变化（需要双台型回归）；PATCH 是修 bug 不改行为（仍需回归，但可灰度更快）。
  • 共存策略同机可共存多个版本，但一个 Runner 进程只加载 lock 里指定的那一版：只把解析结果目录加入 sys.path，不加整个 packages/。多台架并发就跑多进程，不要在一个进程里塞两套解析结果。
  • 兼容矩阵manifest 声明 runner 与 contract 范围；安装时校验，不满足直接拒绝并打印「该包要求 Runner ≥ 1.6，当前 1.5.2」这类可执行提示。
  • 撤销机制索引里可把某版本标 revoked 并附原因。启动时命中撤销版本 → 拒绝加载并提示回滚到 lock 中上一版，而不是静默使用。

05升级、灰度、回滚

  1. 出包即入索引，不直接推现场新版本先进私有索引并标记为 candidate，只有被某个台型的 lock 引用后才算真在用。
  2. 先灰度一台选该包复用台型里最不敏感的一台，改 lock 指向新版本，跑完整产线用例 + 连跑至少一个班次。有问题当场回滚，影响面 = 1 台。
  3. 扩到同台型的 1–2 台同台型不同台架再验证一轮，覆盖硬件个体差异（不同固件小版本、不同夹具）。
  4. 按台型批量下发以「台型模板」为单位更新 lock，而不是逐台点。批次之间留 ≥3 天观察窗。
  5. 回滚 = 改回 lock旧版本目录仍在，回滚只改 lock 的 version 与 sha256，重启服务生效，通常一分钟内完成。不需要重装平台，不需要联网。

回滚速度是这套方案唯一值得炫耀的指标：从发现问题到恢复生产，代价应该是「改一个 JSON 字段 + 重启」，而不是「等研发发个安装包」。

06与现状的差距：只差一个发布单元

你们现在「驱动随 Runner 一体发布、现场不做版本选择」——这套在纯基线场景是成立的，共享包正好是它唯一撑不住的地方。

迁移三步，不必推翻现有结构
现状要加什么不动什么
驱动在 backend/drivers/，随安装包发 引入 packages/ 目录与 manifest.json，注册表增加「按 lock 解析」这一条路径 能力契约、设备档案、别名解析、用例写法全部不动
驱动类型表在 factory.py 硬编码 改为「基线表 + 包清单合并」，合并结果启动时打印一次，便于排障 「精确查表、不回退相似驱动」这条原则保留
构建期跑 check_drivers.py 扩展成对每个包跑 conformance + 仿真回归，作为出包门禁 现有构建脚本与安装包流程保留，基线包仍随包发

换句话说：共享包不是新建一套体系，是给现有体系加一个「包」的发布单元。基线包继续随 Runner 发，只是从「唯一的发布方式」变成「三种发布方式里的一种」。

结论：包 = zip + manifest；开发 monorepo + 三道门禁；部署离线导入 + lock 锁定 ATE Runner · 驱动战略
