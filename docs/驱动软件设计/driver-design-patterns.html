驱动软件设计模式说明

这份文档不罗列 GoF 目录，只说明 ATE 驱动层实际使用了哪些模式、它们各自解决了哪一个具体问题、以及在什么情况下会被用坏。模式在这里是约束语言，不是装饰。

01

模式在这里的用法

ATE 驱动层的复杂度不在算法，而在边界：谁决定用哪个驱动、谁来保证换型号不动用例、谁能在现场把驱动换回去。模式的价值就是把这几个边界固定下来，让后来的人不能随手绕过。

判断标准

一个模式只有同时给出"允许什么"和"禁止什么"，才算真正落地。

本文对每个模式都写两栏：约束（必须成立的条件）与误用（看起来像但会出事的写法）。只写意图不写误用的模式说明，没有评审价值。

范围模式描述的是当前代码（backend/drivers 与 sdk/ate_drivers），不是理想架构。标"待建"的条目明确说明尚未接入运行时。
02

模式总览

九个在用模式，按职责分为三组。分组不是为了整齐，而是为了在评审时能定位问题：结构问题查第一组，行为问题查第二组，数据与一致性问题查第三组。

模式解决的问题落点状态
端口与适配器用例只依赖动作契约，不依赖具体仪器drivers/base.py · contract.py在用
工厂 + 注册表把类型键稳定映射到实现类drivers/factory.py在用
门面把别名、连接、判定收成三个调用AteContext在用
策略传输后端与仿真/真机可替换transport.py · mode在用
模板方法动作分发与结果包装统一，子类只写协议Driver.do / resolve在用
状态会话生命周期与包生命周期可控Driver.open/close · 货架状态文件部分在用
值对象设备配置与结果结构不可变、可比较DeviceConfig · do() 返回体在用
备忘录版本快照支撑回滚installed.json待建
事务脚本安装要么全成要么全撤shelf/manager.py待建
状态口径"部分在用"指会话状态机已在运行，但包状态机还没有运行时载体；"待建"指设计已定、代码未接通。
03

结构：契约、工厂、门面

端口与适配器

意图：用例面向"动作"编程，驱动面向"协议"编程，两者之间只有一层薄契约。换一台同族仪器，TPS 一行不改。

落点

Driver 定义 open / close / do / supports；do() 统一返回 {ok, device_id, alias, driver, action, value, detail, simulated}。

约束

返回值只允许结构化数据；错误只允许抛 DriverError 子类并带稳定 code。上层按码分支，不解析中文消息。

误用在驱动里返回"已设置 3.3V"这类给人看的句子。一旦有人开始 if "3.3" in msg，契约就废了。

工厂 + 注册表

意图：把"设备类型 → 实现类"固定成一张显式表，让未知类型立即失败，而不是猜一个最像的。

# backend/drivers/factory.py
DRIVER_TYPE_MAP = {item["key"]: item for item in DRIVER_TYPES}

def resolve_driver_key(dev) -> str:
    key = str(dev.device_type or "").strip()
    if not key:
        raise DriverNotFound("设备未指定 device_type", device_id=dev.device_id)
    if key not in DRIVER_TYPE_MAP:
        raise DriverNotFound(f"未知设备类型: {key}", detail="可选: ...")
    return key

约束

类型键是外部数据（存在 JSON 与 SQLite 里），只能追加不能改名；改名等于让现场历史记录全部失效。

误用

给类型加 priority 并按关键词打分。这正是本次改造删除的东西：打分会让同一份档案在不同版本下选到不同驱动。

门面

意图：TPS 不该知道注册表在哪、连接怎么建、结果怎么落盘。AteContext 把这三件事收成 driver(alias)、command(alias, action)、expect(key, value)。

门面方法隐藏了什么暴露了什么
driver(alias)表查询、连接参数拼装、握手、实例复用一个已连接的驱动对象
command(alias, action, **p)错误包装、日志动作返回值
expect(key, value)阈值查找、区间比较、明细构造通过后的实测值，或抛 LimitError
device(alias)SQLite 行结构设备信息副本
误用门面变成"万能上下文"：把日志、报告、邮件、MES 上传都塞进 AteContext。门面只应聚合一次运行需要的东西。
04

行为：策略与模板方法

策略

意图：同一份驱动逻辑，既能走真机传输，也能走仿真应答；既能走原生 socket，也能走 VISA。切换只改配置，不改调用方。

策略维度可选值选择方式影响面
运行模式simulate / realdevice_config[alias].mode是否真正打开链路
传输后端native / visa端点声明与平台能力读写实现，不影响动作语义
链路类型LAN / SERIAL设备档案 interface资源串与超时策略

约束

策略只能改变"怎么连"，不能改变"返回什么"。仿真与真机的结果结构必须一致，否则测试结论不可迁移。

误用

在用例里写 if ctx.mode == "simulate": return 3.3。这会让仿真通过、真机失败，而且失败点被藏起来。

模板方法

意图：do() 固定"解析动作名 → 调用方法 → 包装结果"的骨架，子类只实现具体动作方法。新增型号不需要重写分发逻辑。

# 骨架固定，子类只写协议
def do(self, action, **params):
    method = self.resolve(action)          # ACTIONS 别名 → 方法名
    result = getattr(self, method)(**params)
    return {"ok": True, "value": ..., "detail": ..., "simulated": self.simulate}
误用子类重写 do() 以"顺手加个判断"。骨架一旦被绕开，结果结构就不再统一，上层要开始处理两种返回形态。
05

状态、值对象与一致性

状态

意图：把"能不能调用"变成显式判断，而不是靠调用方自觉。会话五态（new / ready / busy / error / closed）与货架包五态（incoming / installed / active / superseded / quarantine）都是这个模式。

非法迁移系统行为为什么必须拒绝
closed → ready拒绝，要求重新 open已释放的 socket 不能复用
busy → busy拒绝重入同一链路并发读写会串包
quarantine → active拒绝校验失败的包不允许被"手动放行"
active → installed仅通过 activate 其他版本避免"取消激活"导致空档

值对象

意图：DeviceConfig 是注册信息的唯一形态，from_dict 负责兼容旧字段，to_dict 负责输出。任何层都不直接改字典。

约束

字段缺失用默认值补齐，字段非法在构造时就报错；device_type 与旧 driver 字段的兼容只发生在 from_dict 一处。

误用

在三个地方各自写 d.get("device_type") or d.get("driver")。兼容逻辑一分散，就会有一处忘了改。

备忘录

意图：货架每次安装都把清单快照写进 installed.json，回滚时不需要重新解包，也不需要网络。

约束快照必须包含 key / version / api / entry / models 与包哈希；只有目录没有快照，回滚后无法解释"当时装的是什么"。

事务脚本

意图：安装是一个有明确提交点的过程，不是一堆文件操作的集合。顺序固定为：验布局 → 验清单 → 验哈希 → 验签名 → 验兼容 → 验冲突 → 解包到暂存 → 原子替换 → 写状态 → 审计。

阶段失败后果回滚动作
校验阶段（前六步）不写任何文件无需回滚，直接报错码
暂存阶段只污染 .incoming/删除暂存目录
提交阶段目录已就位、状态未写启动时以目录与状态不一致告警并重建
状态阶段状态已写、审计未写审计缺失可补写，不影响派发
误用边解压边校验。用户看到"安装到 80% 失败"，磁盘上留下半个包，下次扫描把它当有效包加载。
06

组合：一次调用里出现几个模式

模式不是孤立使用的。一次 ctx.expect("TC_VDD", ctx.command("dmm", "measure_dc_voltage")) 会依次穿过门面、工厂、模板方法、策略与值对象。

  1. 1

    门面拆别名

    AteContext.command 把别名换成设备行，交给工厂；调用方看不到 SQLite。

  2. 2

    工厂查表

    device_type 精确命中 generic-dmm，拿到实现类；未命中立即失败。

  3. 3

    策略决定链路

    按档案的 interface 与运行模式选择 LAN/串口、仿真/真机。

  4. 4

    模板方法执行

    do("measure_dc_voltage") 经 ACTIONS 解析到方法，包装成统一结果。

  5. 5

    值对象承载

    返回体是纯数据，不含连接、不含日志句柄，可被序列化进结果文件。

  6. 6

    阈值在门面外

    expect 读取 testconfig 做区间判定，驱动全程不知道阈值存在。

07

禁用模式：看起来合理，实际会坏

下面五种写法在本项目里明令禁止。它们都曾经出现过，或者很容易被新同学写出来。

写法短期好处长期代价替代做法
关键词打分选驱动新设备不改代码也能"跑起来"同型号在不同版本选到不同驱动，故障无法复现注册时显式选 device_type
未知类型回退 generic-scpi不会报错用错协议读写，可能给出看似正常的错值直接抛 E_NOT_FOUND
驱动内做阈值判断用例少写两行同一仪器在不同 TPS 上判定口径不一致判定留在 ctx.expect
单例持有仪器连接省一次握手并行测试互相踩链路，异常后无法恢复按别名在会话内复用，结束即关
用继承表达型号差异结构直观型号一多就爆炸，且无法外挂发布用清单 models + 少量分支
注意第一、二条不是"风格问题"，是本次改造已经删掉的代码。恢复它们等于回退整次改造。
08

评审清单

评审一个驱动改动时，按下面八条逐项确认。任何一条不成立，都不应该合入。

  • 契约未被绕过：没有子类重写 do() 改变返回结构
  • 类型有出处：新增类型键同时进了 DRIVER_TYPES 与前端下拉
  • 失败可判定：错误都带稳定 code，不靠中文匹配
  • 无隐式回退：查不到类型就是报错，没有"默认驱动"
  • 判定在外层：驱动只返回值，不返回"合格/不合格"
  • 状态有出口：异常后能 close 并重新 open
  • 仿真等价：仿真与真机返回同一结构
  • 可回滚：清单快照足以还原上一版本行为
