ATE Runner · 驱动战略 · 决策备忘 02

几百个测试台收敛到标准柜之后，驱动还该怎么分层、怎么装

两个问题分开答：分层要，但分层的切法要换 —— 按「变化频率」切，不按「协议栈」切；驱动不该全部塞进平台 —— 平台只装契约、注册表和稳定集，长尾设备以独立包分发。这两条合起来，才能让几百台设备的维护成本跟台数脱钩。

问题域 · 标准化主控柜 × 数百测试台 版本 · v2（推翻按传输层分层的旧结论） 日期 · 2026-11-08
Verdict

驱动必须分层，但分层的轴换成「谁在变、多久变一次」：能力契约（极少变）、厂商实现（半年变）、站点绑定（每台都变）、运行时（随运行时变）。

驱动不应全部集成进平台。平台内置的是契约、注册表、仿真与柜内固定设备的稳定集；其余按设备族做成独立版本、独立发布的包。否则每加一款仪器就要发一次主程序，几百台现场没法只回滚一个驱动。

01先算规模：几百台不等于几百个驱动

「几百个功能不同的测试台」听起来是几百倍的驱动工作量，实际不是。复杂度分布极不均匀，认清这一点，后面的设计才有依据。

6–12 台/柜
标准柜内的仪器与板卡
20–40 个
覆盖多数测试台的设备家族
N × M → N + M
按台定制 vs 按能力组合

量级为按行业经验的估算区间，具体数字要靠设备清单盘点后替换。结论方向不依赖精确值：设备种类增长慢，测试台数量增长快，所以复杂度必须压在「台」这一侧（配置），不能压在「驱动」那一侧（代码）。

复杂度到底长在哪
变化源几百台下的量级变化频率应该装进哪一层
设备种类 几十个家族，几年内缓慢增加 低频 驱动包（可版本化、可灰度）
测试台配置 几百套，且持续新增与改版 高频 设备档案 / 站点绑定（数据，不是代码）
测试程序（TPS） 上千个用例，随产品迭代 最高频 用例层，只认能力契约
连接与协议 基本由厂商 SDK 提供 极低频 适配器，SDK 只准出现在这里

推论很直接：如果把「测试台差异」写进驱动，等于让最低频的层去承载最高频的变化 —— 这是几百台规模下最常见的死法，也是「每台测试台都在改驱动」的根源。

02分层的正确切法：按变化频率切四层

不是传输层 / 家族层 / 厂商层那种按「技术栈」切。技术栈切法只回答「代码放哪」，回答不了「谁改它、多久改一次、改坏了影响几台」。

L1 · 能力契约
上层只认能力，不认型号：DcPower、Dmm、Scope、SignalSource、Camera、RelayMatrix、Load。契约里写的是「设电压/读电流/触发采集/取帧」，不是「某型号的第几条命令」。
变更：年级 · 全公司统一
影响面：全部测试台
L2 · 厂商实现
一个型号一个适配器，把厂商 SDK（RsInstrument / pypylon / VISA / 厂商 DLL）翻成 L1 的语义。型号特性、命令方言、错误码映射全部封在这里。
变更：半年级 · 按设备族
影响面：用该型号的测试台
L3 · 站点绑定
每台测试台的差异都在这里，而且是数据不是代码：设备档案（型号、地址、超时）、通道映射（继电器矩阵到 UUT 引脚）、量程与校准系数、夹具补偿。
变更：每次建台 / 换夹具
影响面：单台测试台
L4 · 运行时
标准柜特有的那一层：会话生命周期、资源独占与仲裁（一柜多站争用同一台仪器）、超时与重试、连接拓扑可视化、故障隔离。
变更：随平台版本
影响面：全柜所有站

检验切法对不对，问一句：某个测试台临时换了一台同能力不同型号的仪器，需要改代码吗？改 L3 的档案就行 —— 说明分层成立；要动 L2 甚至 L1 —— 说明契约没抽对。

03标准柜带来的三个新约束

这三件事在单台设备、单台测试台的场景里不存在，但一到「几百台 + 统一柜」就变成硬约束，也是分层必须回答的问题。

规模带来的是什么问题
约束具体表现对分层的要求
柜内仪器共享 一个柜挂多个测试站，共用电源、DMM、矩阵；两个站同时下发命令会互相打断量程与触发状态 资源仲裁必须在 L4，不能每个驱动自己 open() 一条连接
备件与替代 某型号停产或现场只有替代型号，功能等价但命令方言不同 L1 契约必须按能力定义，替代型号只需新增 L2 适配器 + 改 L3 档案
现场无开发环境 产线不能装 IDE、不能编译，故障要在十分钟内定位到「线 / 驱动 / 档案 / 用例」 驱动要自带自检与连接拓扑（describe() 类），诊断信息必须能被现场读懂

第三条最容易被忽略：几百台的运维成本，八成不在写驱动，而在「现场定位一个问题要多久」。分层如果没让排障变快，它在规模下就是负资产。

04驱动要不要全部集成进平台

这是分发问题，不是架构问题。三个选项的差别不在「优雅」，在「加一款设备要发多少次版本、现场能回滚到什么粒度」。

分发模型对比
模型加一款新仪器的动作代价结论
全部集成进平台 改主程序 → 全平台回归 → 发一个大版本 → 几百台逐台升级 发布节奏被最不稳定的设备绑架；单个驱动 bug 要停整条线；装机包越来越大 不可取
全部外挂，平台只留契约 只发一个驱动包 版本矩阵复杂（平台 × 驱动 × 固件），现场可能出现「驱动不匹配」，需要签名与兼容清单兜底 过于激进
稳定集内置 + 长尾外挂 柜内固定设备（电源、DMM、矩阵、相机、程控负载）随平台发；新品与专用设备走独立包 需要一套包规范：版本、签名、兼容矩阵、按测试台类型锁定 推荐

切分依据不是技术，是「这台设备会不会出现在每一个柜子里」。每个柜都有的，内置，省一次部署；只有少数台用的，外挂，避免污染基线。经验上内置集稳定在十来个设备族，其余全部外挂。

三个模型共用一套硬前提，缺一个就退化成「各自为政」：统一契约（外挂包也实现同一组接口）、统一注册表（平台启动时按档案解析到具体实现）、兼容矩阵（平台版本 × 驱动包版本 × 设备固件，装错要在启动时报错而不是运行中炸）。

05几百台规模下会致命的五个反模式

结构上的

  • 按测试台定制驱动：driver_for_station_37.py。台数一涨就爆炸，等价于放弃标准化。
  • 契约里写型号：set_voltage_34461a()。换型号即改用例，TPS 与硬件再次耦合。
  • 校准与通道映射写进代码：换夹具要改驱动、要发版，现场只能等研发。

运行上的

  • 驱动自己管连接：柜内多站抢同一台仪器，量程与触发状态互相踩，故障表现为「偶发读数异常」。
  • 平台里堆型号分支：if model == ...，每来一款仪器改一次平台核心，回归范围永远说不清。

这五条的共同点：都把「高频变化」放进了「低频层」。判断任何设计提案，先看它把变化放在了哪一层。

06落地顺序

不要先做框架。先做盘点与契约，因为契约抽错了，后面每一行代码都是负债。

  1. 设备盘点，出一张能力地图把几百台用到的仪器按「能力」聚类，而不是按型号列清单。目标是压到二十来个能力族，并标出每个族里的主力型号与替代型号。
  2. 定 L1 契约与 L3 档案格式契约只写用例真正会用的操作；档案要能表达型号、地址、通道映射、量程与校准系数。这两个定完，剩下的都是填充。
  3. 选两个差异最大的测试台做标杆柜一个偏电测、一个偏光测或视觉。两台都能用同一套契约跑通，说明抽象站得住；跑不通就趁早改契约，别等铺开。
  4. 建包规范与兼容矩阵驱动包独立版本、独立签名、声明支持的平台版本与固件范围。现场装错在启动时就报错，而不是跑到一半出怪值。
  5. 按测试台类型分批迁移每批做等价性回归（老台与新台跑同一组用例，读数与判据一致），而不是「装上去能跑就算过」。批与批之间留回滚点。
  6. 收敛长尾迁移后期把只有少数台用的设备移出内置集，主平台只保留稳定集。这一步决定三年后升级是「发一次包」还是「排三个月窗口」。
结论：分层按变化频率切；驱动以「稳定集内置 + 长尾外挂」分发 ATE Runner · 驱动战略
