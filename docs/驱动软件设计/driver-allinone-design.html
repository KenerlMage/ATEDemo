驱动全量随包方案

核心驱动只有八类，台架却有很多台。这个规模下，让驱动单独发版带来的复杂度，超过了它换来的灵活性——所以驱动全部随 Runner 包发布，版本只有一个。

01

结论与适用规模

核心驱动只有八类、型号数量有限，而企业内部核心测试台数量多。这个规模下，按需外挂带来的收益抵不过它引入的复杂度：每多一条"驱动可以单独换版本"的路径，就多一种"同一版 Runner 在不同台架上行为不同"的可能。

方案结论

所有驱动随 ATE Runner 安装包发布，不单独安装、不单独升级。Runner 版本号即驱动集合版本。

升级只有一种形态：整包替换程序目录 + 保留现场数据 + 失败整包回滚。不再有驱动级版本、外挂目录、签名包与在线仓库。

判断依据现状对方案的含义
核心驱动数量8 类，动作合计 64 个体积与维护量都可控，随包不构成负担
型号扩展频率低，按项目引入不需要"不发版就能加型号"的能力
台架数量企业内部多台、同构版本一致性优先于灵活性
升级痛点怕升级冲掉现场配置与驱动差异要解决的是数据边界，不是驱动分发
一句话驱动不再是"可独立演进的第三方组件"，而是 Runner 的一部分——和 tps_runtime 一样，随版本走。
02

与货架方案的取舍

前一版方案假设"驱动会比平台更频繁地变"，因此做了外挂目录、签名包、版本锁定与回滚。现在的前提相反：平台发布节奏才是主变量。前提变了，机制就该删掉而不是保留。

能力货架方案全量随包处置
驱动来源<RUNNER_HOME>/drivers 外挂扫描app/drivers 单一路径删除外挂
发布单元签名 .atepkgRunner 安装包删除打包器
版本治理驱动级 key + version 锁定Runner 版本统一标识删除驱动版本
回滚切 active.json 指针整包回滚到上一版 Runner改粒度
分发内网仓库 / MES 推送 index.json随安装包，沿用现有升级通道删除仓库
签名与信任Ed25519 包签名 + 信任库安装包自身完整性校验删除驱动签名
型号派发按 device_type 精确查表同左保留
旧记录兼容类别精确映射，仅补空同左保留
不是退步删掉的是"驱动独立发布"这条链路，保留的是"设备类型精确派发"这条链路。前者是分发机制，后者是运行时正确性——两者无关。
03

逻辑视图：单一版本流

全量随包后，逻辑视图从"内置 + 外挂两个来源"收敛为一条线：包内驱动表是唯一事实源，工厂按设备类型查表，会话复用实例，TPS 只认别名。

层职责全量随包后的变化
L0 传输TCP / 串口 / VISA 读写无变化
L1 驱动型号协议翻译只在包内，无外部来源
L2 工厂device_type → 驱动类只需查一张表，不再合并外部清单
L3 会话实例复用与释放无变化
L4 TPS别名与阈值无变化
04

包内结构

安装包里 app/drivers 是驱动唯一位置。打包脚本已经把 drivers 列入复制清单，全量随包在这一点上不需要改结构，只需要把"其余链路删掉、门禁补上"。

05

升级模型

台架多、版本必须一致，所以升级按"整包替换 + 数据保留 + 失败回滚"三步走。驱动跟着程序目录一起换，不需要也不允许单独处理。

1
空闲校验
有测试任务在跑时拒绝升级（现有 UpdateBusy 已实现）。
  1. 1

    下载与校验

    取安装包，校验 SHA256；不通过直接丢弃，不进入暂存。

  2. 2

    驱动门禁

    在暂存目录跑 check_drivers.py：八类可实例化、动作有实现、注册库引用的类型都在包内。失败即中止升级。

  3. 3

    数据指纹

    对 logs / workspace / ate.db / testresource 记录数量、体积与时间戳，作为升级后"数据未丢"的证据。

  4. 4

    整体替换

    替换 app / web / runtime，其余目录不动；写 pending_swap.json 供下次启动前完成切换。

  5. 5

    指纹比对

    升级后重算指纹，与升级前对比；不一致要显式告警，不静默放过。

  6. 6

    冒烟

    启动后跑一次驱动门禁 + /api/health + 任一台架仿真用例；失败则回退到上一版整包。

回滚粒度回滚单位是整包，不是单个驱动。这正是要的：不存在"驱动退回了、平台没退回"的半吊子状态。
06

代码与数据边界

全量随包真正的风险点不在驱动，而在"现场改过的数据是否会被程序目录一起换掉"。核查发现：数据库与注册库都在 app/ 下，而升级保留清单是按安装根目录解析的——指纹会把它们记成"不存在"。

数据实际路径保留清单解析位置后果
历史记录 ate.dbapp/ate.db<RUNNER_HOME>/ate.db记成 absent，校验空转
注册库 testbenches.jsonapp/testresource/<RUNNER_HOME>/testresource同上
日志 / 运行目录logs/ workspace/根目录解析正确

已修（本次）

指纹解析增加 app/ 回退：根目录找不到时再看 app/<name>，使现有部署立刻具备真实的数据校验能力。

待做（P1）

把 ate.db 与可写注册库迁到 <RUNNER_HOME>/data，用 ATE_DATA_DIR 指向；程序目录变成纯只读代码。

判定标准升级后 app/ 里不应存在任何"只有现场才会产生"的文件。满足这条，全量替换才是安全的。
07

发布门禁

驱动在包里，就没法靠"装不上就不装"来兜底，只能在打包时拦住。新增门禁脚本 packaging/check_drivers.py，接在打包流程第 2.5 步，直接校验已经复制好的 payload/app。

# 打包时自动执行（build_package.ps1 第 2.5 步）
python packaging/check_drivers.py --backend <dist>\payload\ATERunner\app
# 失败即中止打包，不会产出装不起来的安装包

# 升级后在现场也可单独跑
python app\..\packaging\check_drivers.py --backend app
检查项判定不通过意味着
类型可实例化8/8 成功构造参数或导入路径有问题
动作有实现ACTIONS 全部可解析命令表指向了不存在的方法
仿真可握手identify() 返回字符串驱动在无仪器时直接崩
注册库自洽所有 device_type 在包内删了类型但现场还在用
安全退出close() 不抛异常会话泄漏、端口占用
本次实际输出8 类全部 OK，动作合计 64；注册库 7 台设备、0 个未解析类型，门禁 PASSED。
08

派发与变更管理

派发规则不变：注册时选设备类型，运行时按该字段精确取驱动，缺失或非法直接报错，不回退到通用 SCPI。变的是"类型从哪来"——只从包内来。

场景做法版本影响
新型号接入在 DRIVER_TYPES 增加条目 + 实现类，随下个 Runner 版本发布发版
协议修正改包内驱动，过 19 项门禁后发版发版
客户定制驱动不进现场安装，回到主线或走客户分支构建发版
台架差异（IP/端口/型号）改注册记录，不改驱动不发版
阈值差异改 TPS 的 testconfig不发版

版本号

Runner 版本即驱动集合版本。驱动内部不再单独维护对外版本号。

记录口径

测试结果记录写 runner_version 与 driver_key，不再写驱动版本。

灰度

先在一台非生产台架升级并跑首件，再批量推送同版本。

09

落地清单

按"必须做 / 建议做 / 可以不做"分档。第一档不做完，全量随包就是有风险的。

优先级事项状态

10

风险与边界

这个方案不是没有代价，只是代价换到了更容易管理的地方：从"版本组合爆炸"换成"发布节奏绑定"。

风险影响缓解
加型号必须发版项目紧急接入时等版本按月固定发布窗口 + 紧急补丁通道
单点故障面变大一个驱动崩溃影响整包打包门禁 + 仿真冒烟 + 升级后自动回滚
客户定制无出口不能现场装私有驱动客户分支构建，产物仍是完整包
包体积增长下载与安装变慢驱动为纯 Python，增量在百 KB 级
台架不同步同一车间存在两个版本升级看板按台架登记版本，未升级可查
明确不做不做驱动级热插拔、不做现场侧载、不做驱动独立版本号、不做驱动市场。这些能力在当前规模下只增加故障面。
