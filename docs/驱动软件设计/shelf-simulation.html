01

仿真目标与边界

货架的价值不在"能装包"，而在装错、装坏、装重时会不会把产线带偏。所以仿真只验证四类判断：能不能拒收、能不能切版本、能不能锁版本、能不能退回去。

仿真的判定标准

十个场景里，四个必须成功、六个必须失败，且失败要落在明确的错误码上。

只演示成功路径的仿真没有意义——真实事故都发生在拒收和回滚这两段。

口径说明本文是设计推演：场景、状态变化与错误码按已定设计给出，用于评审；包结构与校验逻辑已在 SDK 中实现，安装管理器尚未接入运行时，差距见第 05 节。
02

场景推演：十个动作

被测对象是一台虚构的 600W 电源驱动 acme-psu-600，两个版本 1.0.0 与 1.1.0。测试台 SPM-RH-DYN-01 上有三台设备：内置类型电源、货架类型电源、以及一台类型写错的设备。

#动作预期结果判定码
01装 1.0.0 并激活落盘 drivers/acme-psu-600/1.0.0/，active 指向 1.0.0成功
02派发 acme-psu-600 设备返回版本 1.0.0、entry、接口类型成功
03装 1.1.0 但不激活两版本并存，active 仍为 1.0.0成功
04激活 1.1.0active 切到 1.1.0，1.0.0 转 superseded成功
05回滚active 回到 1.0.0，目录与包均不变成功
06装被篡改的包拒绝落盘，暂存目录清空E_PKG_HASH
07装 api=9.0 的包清单阶段拒绝，不解压E_PKG_COMPAT
08装声明同型号的另一个 key拒绝，提示型号已归属E_PKG_CONFLICT
09用未安装的类型派发直接报错，不回退通用驱动E_NOT_FOUND
10台架锁定 9.9.9 后派发拒绝改用其他版本E_PKG_PINNED_MISSING
关键点场景 05 的"目录与包均不变"是设计约束：回滚只切指针，不重新解包。否则回滚本身会成为新的失败点。

安装

写入两份东西：目录里的包内容 + 状态里的清单快照。缺快照就无法解释历史。

激活

只改一个字符串。改名之外什么都不动，所以切换是原子的。

回滚

取比当前低的最高版本。没有更低版本时报错，而不是"随便挑一个"。

05

与真实实现的差距

仿真不是实现。下表说明哪些能力已经有代码、哪些还停在设计，避免把推演当成已上线。

能力代码状态说明
包结构、哈希、签名已实现sdk/ate_drivers/shelf/package.py、trust.py
状态文件读写与审计已实现shelf/state.py，原子写入
安装事务与版本切换设计完成管理器实现受本机安全策略限制未落地
运行时扫描货架未接通Runner 仍只查内置 DRIVER_TYPES
升级保留 drivers/未修PRESERVED_PATHS 目前不含该目录
结论仿真证明的是"判定规则成立"，不是"货架已经可用"。要变成可用，须先完成管理器与运行时扫描两处接线。
