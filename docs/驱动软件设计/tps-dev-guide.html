TPS 开发说明

TPS 是测试程序集，不是脚本堆：它用一份清单声明测试台、设备别名、阈值与执行顺序，用 Python 函数实现单条用例，由 Runner 在隔离的运行目录里逐条执行并落盘。

01

TPS 的边界

TPS（Test Program Set）是一套可执行的测试程序：它声明这次测试用哪台测试台、每台设备扮演什么角色、合格区间是多少、按什么顺序执行。它不是"一堆 pytest 文件"，也不是"一个 Python 脚本"。

职责划分

TPS 决定测什么、按什么顺序测、多少算合格；运行时决定怎么隔离、怎么执行、怎么记录。

把隔离、日志、结果落盘写进用例，等于把运行时该做的事重复一遍，而且每个 TPS 做得都不一样。

属于 TPS不属于 TPS
测试顺序与依赖进程管理与目录隔离
合格区间（阈值）结果文件格式与命名
设备别名与角色驱动连接与协议细节
单条用例的测量逻辑测试台注册信息维护
02

工程结构

workspace/
└── SPM读头动态测试/            # 一个 TPS 一个目录
    ├── tps.json               # 清单：结构、顺序、阈值
    ├── conftest.py            # 运行时部署的公共夹具（勿手改）
    ├── testcase/              # 用例实现包
    │   ├── __init__.py
    │   ├── env_setup.py       # setup / teardown
    │   ├── power.py
    │   └── signal.py
    └── resource/              # 人工步骤说明（.md / .txt）
        └── fixture_check.md

运行目录

每次运行，Runner 把 TPS 复制到隔离目录，注入 env.json 与生成的清单副本，再逐条跑 pytest 节点。原始工程不被写入。

可移植性

TPS 目录可以整体拷贝到另一台 Runner；只要测试台注册信息对得上，不需要改代码。

03

清单字段

清单顶层字段固定。校验在保存与运行前各做一次，错误信息会指出具体条目序号。

字段必填规则作用
schema是固定 tps.v2区分旧版 steps 结构
id是1–64 位，仅字母数字与 _ . -运行记录主键
name / version建议自由文本 / 语义版本报告与追溯
project / dut建议自由文本结果归类
workspace_dir否目录名运行目录命名，默认取 id
bench否preset_id 或 bench_id绑定测试台与设备
environment否对象展示用环境描述
device_config是非空对象别名 → 设备
testconfig是非空对象，每项至少一个边界阈值定义
setup否数组前置步骤
cmd_suit是非空数组主测试序列
teardown否数组收尾步骤，失败也执行
兼容旧版用 steps 数组；同时出现 steps 与 cmd_suit 会直接报错，必须只保留一种。
04

设备别名与类型

device_config 的键是别名，值是设备定位信息。别名是 TPS 内部概念，与设备类型无关；类型来自测试台注册记录。

"device_config": {
  "psu":  {"device_id": "rh-psu",   "role": "psu",   "note": "读头供电"},
  "dmm":  {"device_id": "rh-dmm",   "role": "dmm"},
  "spin": {"device_id": "rh-spin",  "role": "motion"}
}
定位方式写法适用注意
精确设备编号{"device_id": "rh-psu"}推荐跨台架复用时需保证编号一致
按角色{"role": "dmm"}同型台架通用 TPS一台台架只能有一个该角色设备
按类别 / 型号{"category": "电源"}临时排查生产 TPS 不建议，易选错
字符串简写"psu": "rh-psu"快速原型等价于只给 device_id
与 device_type 的关系TPS 不声明设备类型。类型记在注册记录上，运行时按该字段精确取驱动；TPS 只声明"我要用哪台设备、叫它什么"。
05

阈值定义

testconfig 的每个键是一组判定边界。键名在用例的 checks 或 config 中被引用，引用未定义的键会直接报错。

"testconfig": {
  "TC_VDD": {"label": "读头上电电压", "min": 3.135, "max": 3.465, "unit": "V", "nominal": 3.3},
  "TC_IDD": {"label": "读头工作电流", "min": 150, "max": 250, "unit": "mA"}
}
规则说明
至少一个边界min 与 max 至少有其一，否则无法判定
必须为数字布尔值与字符串都不接受
下限不大于上限min > max 在保存阶段就报错
单位必填缺单位会导致报告无法比对，评审不通过
单边判定只给 max 表示"不得超过"，只给 min 表示"不得低于"
命名习惯阈值键用 TC_ 前缀，与用例编号区分：键描述物理量，用例描述测法。
06

用例实现

一条用例就是一个普通函数，签名为 def case(ctx, **params)。它可以直接返回数值，由清单里的 checks 自动判定；也可以自己调 ctx.expect 主动断言。

# testcase/power.py
def power_on_voltage(ctx, psu_alias: str, dmm_alias: str, voltage: float) -> float:
    """上电后测量读头电压，返回实测值（由 checks 判定）"""
    ctx.command(psu_alias, "set_voltage", volts=voltage)
    ctx.command(psu_alias, "output_on")
    return ctx.command(dmm_alias, "measure_dc_voltage")["value"]
ctx 方法用途返回值
driver(alias)取已连接驱动实例（会话内复用）驱动对象
command(alias, action, **p)执行动作，自动处理驱动错误动作返回体
device(alias)读取设备注册信息字典副本
limit(key)取阈值定义{min,max,unit,label}
check(key, value)判定但不抛异常(ok, detail)
expect(key, value)判定并在超限时抛 LimitError实测浮点值
log(message)写运行日志无

返回值约定

返回数字 → 与 checks 声明的阈值比较；返回字典 → 按 checks 的键逐项取子值判定；返回 None → 视为已自行判定。

异常约定

AssertionError / LimitError 记为失败；其他异常记为错误并带上堆栈。optional=true 的条目失败不阻断后续。

07

步骤类型

三类条目共用同一套字段，区别只在 case 与 type。setup、cmd_suit、teardown 的条目结构一致。

类型声明执行方式典型用途
自动用例case: "testcase.power::power_on_voltage"Runner 拉起 pytest 节点测量、设置、判定
人工步骤type: "manual" + resource弹窗展示 Markdown，等操作员确认装夹、外观检查、换料
单步暂停step: true该条跑完后暂停，等"下一步"调试、首件确认
 
{
  "no": 2,
  "id": "M-01",
  "type": "manual",
  "name": "读头装夹与外观确认",
  "resource": "fixture_check.md",
  "description": "人工确认装夹到位后继续"
}
校验人工步骤必须有 resource，且只能是 resource/ 下的 .md 或 .txt；路径穿越与绝对路径都会被拒。
08

运行与调试

Runner 不直接在工程目录里跑。每次运行先暂存（stage），再在暂存目录执行，所以用例里读写相对路径不会污染源工程。

  1. 1

    暂存

    复制 TPS 工程到运行目录，部署 conftest.py，写入 env.json（测试台、运行模式、任务号）。

  2. 2

    解析测试台

    按 bench.preset_id 或 bench_id 找到台架，把设备注册信息投影成别名表。

  3. 3

    逐条执行

    每条生成一个 pytest 节点 test_generated.py::test_case_TC001，单独进程执行，超时按条目设置。

  4. 4

    判定与记录

    返回值交给 checks 判定；结果写入运行目录的 JSON，含实测值、区间、耗时。

  5. 5

    收尾

    无论成败执行 teardown，关闭输出、释放串口、汇总报告。

调试场景做法注意
只跑一条单步执行该条目前置依赖不会自动补跑
无仪器把运行模式切到 simulate仿真值不能当验收依据
复现历史问题复用同一运行目录的 env.json不要手工改结果文件
看驱动实际命令运行日志中的 driver.log_lines()日志含敏感 IP，外发前脱敏
09

校验规则与常见错误

清单校验发生在保存与运行前。下面是最常撞到的八条，报错信息会带条目序号，按序号定位即可。

报错原因修正
缺少必填字段: testconfig只写了用例，没有阈值补阈值对象，至少一项
testconfig[TC_X] 至少要给 min 或 max写了 label 没写边界补上下限之一
cmd_suit[3] 缺少 case条目只有 name补 module::function
case 格式应为 module::function写成文件路径或函数名改为 testcase.power::fn
引用了未定义的阈值checks 里的键拼错与 testconfig 对齐
id 重复复制条目未改编号同段内编号唯一
人工操作条目缺少 resourcetype=manual 没给说明文件在 resource/ 下建 Markdown
同时包含 steps 与 cmd_suit旧版结构未清理删除 steps
运行期错误E_NOT_FOUND 表示设备类型未注册或未安装；E_CONFIG 表示连接参数不全；E_TRANSPORT 表示链路不通。三者处置完全不同，不要统一按"仪器坏了"处理。
10

交付检查

TPS 提交评审前，确认下面八项。前四项是结构，后四项是行为。

  • 清单可解析：保存无报错，schema=tps.v2
  • 别名闭环：每个 params 用到的别名都在 device_config 中
  • 阈值闭环：每个 checks 键都在 testconfig 中
  • 人工步骤有说明：resource/ 下文件存在且可读
  • 仿真可跑通：simulate 模式全绿，无异常
  • 真机首件通过：至少一台真实台架跑通并留存结果
  • 收尾可靠：中途失败后输出关闭、串口释放
  • 结果可追溯：报告含 TPS 版本、台架编号、驱动版本
