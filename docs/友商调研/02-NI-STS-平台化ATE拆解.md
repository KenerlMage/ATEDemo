# 02 · NI STS：平台化 ATE 的完整拆解

> 来源：NI 官方产品页与文档、Apex Waves 技术博客、Emerson 公告，见 `README.md` 引用清单 R1–R8。

## 一、产品谱系：一套软件，三种机箱规模

STS（Semiconductor Test System）不是一台机器，而是**一套参考配置**：PXI 机箱 + 模块仪器 + 电源与接口面板 + 预装软件。

| 型号 | 容纳机箱 | 典型场景 |
| --- | --- | --- |
| STS T1 | 1 × 18 槽 PXI 机箱 | 实验室、单站验证 |
| STS T2 | 2 × 18 槽 PXI 机箱 | 中等并行、多工位 |
| STS T4 | 4 × 18 槽 PXI 机箱 | 产线，多 site 并行 |

关键点：**T1 到 T4 的软件是同一套**，扩产只是加机箱与模块。这是平台化路线最大的商业优势——工程量不随产能线性增长。

## 二、四层软件栈

| 层 | 组成 | 职责 | 类比到我们 |
| --- | --- | --- | --- |
| L4 应用/报告 | 报告生成、数据库记录、MES 对接 | 结果标准化与追溯 | 后端结果标准化 + MES 回传 |
| L3 执行器 | TestStand（序列编辑、步骤类型、流程模型、并行执行） | 决定「按什么顺序跑什么」 | TPS 编排 + pytest 执行 |
| L3.5 半导体扩件 | TestStand Semiconductor Module（TSM）：多 site、引脚映射、半导体专用步骤 | 让通用执行器懂「site 与 pin」 | **我们缺这一层** |
| L2 驱动 | NI-Digital、DMM、示波器、RF 等模块驱动（多为 IVI 风格） | 把「测量」抽象成函数调用 | `drivers/` 适配层 |
| L1 硬件 | PXIe 机箱、背板时钟、模块仪器、DUT 接口板 | 提供确定性时序与通道 | 现有测试台里的仪器 |

注意 L3 与 L3.5 的分工：**TestStand 本身并不知道什么叫 site，是 TSM 把 site/pin 概念注入进去的。** 这条设计非常值得抄——通用执行器保持通用，行业语义用扩展模块挂在上面。

## 三、五个关键抽象

1. **Step（步骤）**：最小执行单元，有类型（数值测量、字符串、序列调用、判限）、有前后置动作、有超时。
2. **Sequence（序列）**：步骤的有序集合，可嵌套调用，构成测试流程。
3. **Process Model（流程模型）**：固化「一批被测件的生命周期」——预检 → 逐件测试 → 判定 → 报告 → 清理。TestStand 自带 Test UUTs / Single Pass 两种模型，用户可改但不能绕过。
4. **Site（工位）**：同一台仪器上并行测试的多个被测件实例。TSM 提供**动态多 site 编程**：同一份测试代码在可扩展的 site 数量上复用，site 数量变化不需要重写代码。
5. **Pin Map（引脚映射）**：把「逻辑引脚名」映射到「物理通道号」。测试代码只写逻辑名，换硬件只改映射表。

这五个抽象解决了平台化路线最痛的问题：**代码与硬件解耦、逻辑与物理分离。**

## 四、并行是怎么做到的

- **机箱内**：背板提供统一参考时钟与触发线，模块间的同步由硬件保证，软件只负责下发参数。
- **机箱间**：多机箱通过同步模块对齐，T2/T4 由此获得跨机箱的向量同步。
- **site 级**：执行器按 site 复制执行上下文，测试代码按 site 并行跑；硬件资源由 pin map 保证不冲突。
- **产线级**：多台 STS 由工厂的 MES 统一派工，STS 自己不负责排产。

## 五、指标示例（说明「平台化能到什么水平」）

以数字通道模块 PXIe-6570 为例：

| 指标 | 数值 |
| --- | --- |
| 通道数 | 32 通道 / 模块，2 槽宽 |
| 向量速率 | 100 MVector/s |
| 边沿放置分辨率 | 39.0625 ps |
| 同步规模 | 单子系统最多 256 通道 |
| 电平范围 | 数字 -2 V ~ 6 V；PPMU 强制电压 -2 V ~ 7 V |
| 数据速率 | 最高 200 Mb/s |

**判断**：这个水平足够覆盖 MCU、电源管理、混合信号、RF 前端，但离 CPU/GPU 级 SoC 的 per-pin 需求仍有代差——这正是平台化路线的边界，也是它与路线 A 的分工线。

## 六、商业模式与组织变化

- 卖法：硬件模块（一次性）+ 软件许可（TestStand、TSM、LabVIEW 按席位或按版本）+ 服务与校准。
- 2023-10-11，Emerson 以 **82 亿美元**（每股 60 美元）完成对 NI 的收购，NI 并入 Emerson 的测试与测量业务。**判断**：平台化 ATE 的商业价值被工业自动化巨头认可，因为它的客户群横跨半导体、汽车、航空航天，不押注单一行业周期。

## 七、映射到 ATE Runner（逐条对照）

| NI 概念 | 我们的现状 | 差距与建议 |
| --- | --- | --- |
| TestStand 执行器 | `tps.json` + pytest 运行时 | 形态接近，但我们把「流程」和「用例」混在 pytest 里，缺显式 process model |
| TSM 的 site 抽象 | 无 | **最大缺口**。一台 Runner 管多个台位时，没有逻辑 site 隔离，资源冲突只能靠人工约定 |
| Pin Map | 驱动里写死 `host/port/channel` | 建议引入「逻辑资源名 → 物理地址」映射表，随 TPS 走而不是随代码走 |
| Step 超时 | 每用例 pytest 超时（方案 C） | 方向一致，但缺「硬超时 + 看门狗」双保险 |
| 流程模型 | 无固定生命周期 | 建议固化：预检 → 建连 → 执行 → 判定 → 释放 → 归档，六段不可跳过 |
| 报告与数据 | 结果标准化 + MES 回传 | 已经做了，可补「原始波形/截图的留存策略」 |
| 模块化扩展 | `drivers/` + vendor 插件 | 方向正确，可补「驱动能力声明 + 一致性自检」（已有 conformance 雏形） |

## 八、该学与不该学

**该学**

1. 通用执行器 + 行业扩展模块的分层（通用保持通用，语义靠插件注入）。
2. site / pin map 两个抽象——它们是「一拖多」在软件上的正解。
3. 流程模型固化：生命周期不允许被用例作者绕过。
4. 同一套软件覆盖 T1 到 T4：**规模变化不引起架构变化**。

**不该学**

1. 不要照搬 PXI 硬件形态：我们的测试台是既有资产，改造硬件不现实。
2. 不要引入商业执行器的许可模型：我们开源栈的优势就是零许可成本。
3. 不要追求 256 通道级同步：我们的被测对象是装备与板卡，不是高引脚数 SoC。
