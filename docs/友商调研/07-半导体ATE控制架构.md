# 07 · 半导体 ATE 的控制架构：中心下发，还是分布式机箱

## 一、先把问题拆成两个

「半导体 ATE 是用几台分布式工控机箱为主，还是中心下发任务为主」——这个提问把两件不同的事放进了一个选择题里：

| 层面 | 管什么 | 时间尺度 | 放在哪 |
| --- | --- | --- | --- |
| 控制面（调度） | 测什么、用哪版程序、结果收到哪、谁先谁后 | 秒到小时 | 中心服务 / MES |
| 数据面（执行） | 每一条指令、每一个仪器动作、超时与联锁 | 微秒到毫秒 | 工控机箱 / 测试头 |

所以答案是：**控制面集中，数据面本地**。这不是折中，而是量产线的事实形态——NI STS、Advantest 的机台、OSAT 的产线，机台内部都做实时，任务与程序版本都由外部下发。

## 二、三种控制形态

| 形态 | 调度在哪 | 实时在哪 | 故障域 | 扩展粒度 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| A 单站集中 | 同一台工控机 | 同进程 | 整站停 | 加机箱 | 实验室、单工位设备 |
| **B 中心下发 + 多站实时** | 中心服务 / MES | 各站工控机 | **单站停，其余继续** | 加站点 | **量产线主流** |
| C 站点自治 | 无 | 各站自身 | 互不影响 | 加设备 / 加人 | 分散车间、旧线改造 |

形态 B 之所以成为主流，是因为它把两个失效模式分开了：中心挂掉不影响已经排产的单站继续跑；单站挂掉不拖累其它站。

## 三、NI 的实现：TestStand 调度，LabVIEW 测量

| 组件 | 角色 | 在多站里的位置 |
| --- | --- | --- |
| TestStand | 序列引擎：解释执行 step、管理流程与结果容器 | 每站一份；主线程 + 每 site 一条线程 |
| Process Model | Test UUTs / Batch / Parallel：初始化、UUT 循环、收尾、binning | 决定并发模型；Batch 要求各 site 同步 |
| TSM（半导体模块） | site 与 pin map 抽象、多工位程序复用、STDF 输出 | 把通用引擎接上半导体语义 |
| LabVIEW | 测量代码，一个 step 对应一个 VI | 被引擎调用，自己不调度 |
| Switch Executive | 开关/矩阵布线与路径互斥 | 共享资源仲裁 |
| Operator Interface | 界面、结果查询、权限 | 独立进程 |

**最关键的一条机制**：TestStand 的 Batch 与 Parallel 模型在跑多工位时，会**为每个 site 复制一份序列到新的线程**（creating a test socket that runs a copy of the sequence in a new thread）。这意味着多工位不是「一个程序轮流跑几个 DUT」，而是「同一程序并行执行几份，各自有独立变量空间」。这是 TSM 多工位能力的底座。

### 一次执行的时序

1. 主线程加载 `.seq`，选 Process Model，进入 PreUUT；
2. 对每个 site 建 socket 与线程，DUT 上电、识别、载入各自的 pin map；
3. 各 site 并行执行 Test Steps，每个 step 调一个 VI，VI 内调仪器驱动（IVI/VISA）；
4. 共享仪器（电源、开关矩阵）必须分时或互斥，否则测值互相污染；
5. 各 site 独立判 bin，PostUUT 汇总，写入结果库与 STDF。

## 四、其他厂商怎么组织

| 厂商 / 场景 | 控制形态 | 程序与执行 | 多站方式 | 对外接口 |
| --- | --- | --- | --- | --- |
| Advantest V93000 | 测试头 + 工作站，每引脚自带测试处理器，计算与接口随卡走 | SmarTest 程序，编译后下发到卡执行 | 同测数由卡与通道数决定 | SECS/GEM、STDF |
| Teradyne UltraFLEX | 测试头 + 控制器，通用插槽 | IG-XL 表格驱动，单站程序可自动转多站 | UltraFLEXplus 提升同测数 | SECS/GEM、STDF |
| NI STS T1/T2/T4 | 1/2/4 个 18 槽 PXI 机箱，各带嵌入式控制器 | TestStand + TSM，同一程序按 site 数缩放 | Batch / Parallel 复制序列 | TestStand 结果库、STDF |
| OSAT 量产线 | Tester + Handler + 线控 EAP | 机台程序由 EAP 下发与管版本 | 由 Handler 决定，机台按 site 判 bin | SECS/GEM（E5/E30/E37/E40）、Map |

共同点：**实时在机台里，调度在机台外**。差别只在实时的实现深度——专用 ATE 把实时做到了每个引脚，平台化路线把实时留在序列引擎与驱动层。

## 五、四条设计约束（对我们）

1. **控制面集中**：任务令、程序版本、结果归档只从中心下发与回收；中心不参与任何实时步骤。
2. **数据面本地**：序列执行、仪器时序、超时与安全联锁全部在工控机；断网不得停线。
3. **站点身份**：中心只认 site id，不认机器名或 IP；换机不改任务定义。
4. **断网可运行**：中心不可达时按已缓存程序继续跑，结果本地排队补传，恢复后对账。
