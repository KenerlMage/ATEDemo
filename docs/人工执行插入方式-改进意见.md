# 测试用例中插入人工执行 · 现状与改进意见

对现网两套挂起点的复核：`type: manual`（人工操作环节）与 `step: true`（单步暂停）。先给代码级现状基线，再给 14 条改进意见（P0 5 条 / P1 6 条 / P2 3 条），最后是建议的清单形状与迁移路径。

## 一、现状基线（已逐条核对代码）

| 层次 | 现状 | 代码位置 |
| --- | --- | --- |
| 清单层 | `type: manual`（别名 `manual` / `人工` / `human`，读 `type` 或 `kind`）+ `resource`（`resource/` 下的 `.md` / `.markdown` / `.txt`，允许一层子目录）+ 可选 `timeout_s`；单步为 `step: true`（别名 `single_step` / `step_hold`）；条目没写 `name` 时用 `resource` 的文件名主干 | `manifest.py:26-45`、`154-178`、`210-252` |
| 运行层 | 主循环遇到人工条目 → 按「运行副本 `resource/` → 运行副本根 → 源 TPS 包 `resource/`」找提示文件 → 写任务快照 `task["manual"]` → `threading.Event` 阻塞等待；单步复用同一通道（靠 `kind` 区分）；两者默认超时都是 1800s | `main.py:739-747`、`950-1067`、`1130-1171` |
| 交互层 | 人工 = 模态弹窗（渲染 Markdown）；单步 = 顶部横幅 + 步骤行内按钮；提交 `POST /api/tps-tasks/{task_id}/manual {"decision": …}`；决定集合固定 `next` / `abort` | `ExecuteView.vue:85-96`、`583-620`、`688-707`；`main.py:1293-1320` |
| 记录层 | 步骤状态 `passed` / `aborted` / `failed`（中止后测试段记 `skipped`），日志文本 `[人工操作] [名称] -> next|abort`，报告类型列显示「人工操作」「测试用例 · 单步」 | `main.py:1144-1171`、`manifest.py:340-343` |

四条观察（都是代码事实，不是推断）：

- **中止后的跳过规则是隐式的**：主循环只按 `type == "test"` 跳过（`main.py:1135`），而人工条目的 `type` 取自所在段（`setup→init` / `test→test` / `teardown→teardown`，`manifest.py:45`）。于是：`cmd_suit` 里的人工条目中止后会被跳过，`teardown` 里的人工条目中止后仍会弹窗——符合"收尾照常执行"，但清单侧无法为单条声明例外。
- **决定集合不可声明**：快照里的 `manual.options` 是 `manifest.py:289` 写死的 `["next","abort"]`，接口也只接受这两个值；清单不能声明"本条允许判不合格后继续"或"允许跳过"。
- **超时与判定失败同码**：等待超时走 `step_status = "failed"` + `mark = "TIMEOUT"`（`main.py:1153`），报告里与"用例判定失败"共享同一状态值，只能靠 detail 文本区分。
- **提示内容随快照全量回传**：`_wait_operator` 把整篇 Markdown 塞进 `task["manual"]["markdown"]`（`main.py:987`），前端每次轮询任务都重收全文；内容在暂停那一刻才从运行副本读取，运行中改文件不留痕。

## 二、P0 · 五条最该先改

### P0-1 决定集合太窄：操作员只能「通过」或「中止整轮」

- **问题**：外观检查判不合格时，操作员只能中止整轮（丢掉后面本来能跑的用例），或者违心点「继续下一步」，把不合格结果记成通过。
- **建议**：清单可声明 `options`（默认 `["next","abort"]`，可选加 `fail`、`skip`）；`fail` = 本条记不合格但继续后续条目，`skip` = 本条跳过（不计不合格）。接口按 `options` 校验，报告按决定分列「人工判不合格」「操作员中止」「跳过」。
- **代价**：中等——`manifest` 校验 + `main.py` 决定分支 + 报告汇总口径（整轮结论要接纳"人工判不合格"）。

### P0-2 超时被记成「失败」，语义丢失，且无法按场景选策略

- **问题**：无人应答超时 → `failed` + `TIMEOUT`，与判定失败同码；生产模式下默认等 1800s 会把产线卡住。
- **建议**：① 步骤状态增设 `timeout`；② 条目可声明 `on_timeout`：`abort`（默认）/ `fail`（本条不合格、继续）/ `wait`（无限等，仅调试模式允许）；③ 前端显示剩余时间，临近超时变色，生产模式建议默认 300s 并推通知。
- **代价**：小到中等——后端分支调整 + 前端倒计时。

### P0-3 等待通道缺幂等键与操作员身份，决定可能串号且不可追溯

- **问题**：`MANUAL_WAITS[task_id]` 是单槽（`main.py:744`），接口只校验"当前是否 waiting"（`main.py:1309`），不校验这条决定属于哪一次暂停、也不校验谁提交的；前端若拿着上一轮弹窗提交，服务端分辨不出。另外非法 `decision` 在接口会被拒（`main.py:1301`），但后端兜底分支会把异常值折算成 `abort`（`main.py:1001`），属于静默降级。
- **建议**：接口体加 `hold_id`（即快照里的 `manual.id`）与 `operator`；`hold_id` 不匹配返回 409，重复提交返回幂等成功，非法值在日志里显式记录；`holds[]` 落 `operator` / `requested_at` / `answered_at` / `decision` / 耗时。
- **代价**：小——接口签名 + 快照校验，是对现有代码的收口。

### P0-4 提示内容走任务快照，轮询放大且判定依据不可复现

- **问题**：整篇 Markdown 随任务快照回传（`main.py:987`），大图 md 更明显；`tps-slot-source-match` 这类资源一旦超过几百 KB，轮询成本不可忽略。同时本次用到的提示内容没有 hash 留档，"当时看到的是什么"事后无法证明。
- **建议**：快照只留 `resource` + `sha256` + 字节数，正文按需走已有的 `GET /api/tps/{tps_id}/resource/{name:path}`；暂停时把该 md 的 hash 写进运行记录与报告。
- **代价**：小——后端快照瘦身 + 前端取正文；与 P0-3 的 `holds[]` 一起做最省。

### P0-5 中止后的行为不可声明（隐式规则 + 收尾人工动作）

- **问题**：跳过与否取决于条目所在段（见现状观察一）；生产线场景里"中止后仍需人工断电/卸料"和"中止后不必再确认"都真实存在，现在两种都改不了。
- **建议**：条目声明 `on_abort: "run" | "skip"`（默认沿用现状：测试段 `skip`、收尾段 `run`），并在界面与报告里明确标注"中止后安全处置"；收尾段的人工弹窗标题加前缀，避免操作员误以为是新一轮测试。
- **代价**：小——校验 + 主循环一处判断 + 报告文案。

## 三、P1 · 六条体验与可追溯

### P1-1 两套字段族合一：统一为 `hold`

- **问题**：`type: manual`（执行前停）与 `step: true`（执行后停）语义相反却共用通道，靠字段名和 `kind` 分辨；`step` 有 3 个别名，`manifest.py:251` 还得写 `and not manual` 来消歧。
- **建议**：合并为一个 `hold` 子对象，`phase` 显式说明停在执行前还是执行后；旧键保留双读一个发布周期。
- **代价**：中等——校验器、解析器、文档、模板四处同步，但有兼容层可平滑。

### P1-2 人工环节不能录入数据

- **问题**：人工条目没有 pytest 入口（`func` 留空），测得的值（间隙、力矩、目视结论）无处填写，只能写在备注里，无法参与判定。
- **建议**：支持 `fields`（number / text / select / bool，可带单位与上下限），录入结果进 `run_result.json` 与报告；可选让 `limits` 复用 `threshold` 的算法，形成"人工录入 + 自动判定"。
- **代价**：中等——需要新增注入通道（如 `hold_result`）与前端表单。

### P1-3 人工环节不能留证据

- **建议**：支持 `evidence: {photo: true, note: true}`，照片与备注落 `run_dir/evidence/`，报告附缩略图；工控机若带摄像头/扫码枪可直接接入。
- **代价**：中等——上传接口 + 存储 + 报告渲染。

### P1-4 无人值守与通知

- **建议**：暂停超过阈值推送（钉钉/企业微信）或桌面提醒；调试模式允许 `on_timeout: "wait"`；生产模式默认短超时 + 强提醒。
- **代价**：小到中等——通知渠道是现成的，主要是策略配置。

### P1-5 界面形态统一（模态 vs 横幅）与触屏可用性

- **问题**：人工用模态、单步用横幅，两种形态并存；模态期间步骤列表仍可操作；工控机常见触摸屏，按钮偏小。
- **建议**：统一为「顶部横幅 + 侧栏卡片」；模态期间禁用会改变运行状态的操作；补键盘/触屏：`Enter` = 下一步、`Esc` = 中止，按钮加大。
- **代价**：中等——前端重构一处组件。

### P1-6 连续多个同类暂停无法批量放行

- **建议**：提供"本类暂停此后自动通过"（仅调试模式，且记入记录），解决 10 个工位逐个点确认的机械操作。
- **代价**：小——前端开关 + 后端按 hold 名称记忆。

## 四、P2 · 三条工程化

### P2-1 载入期硬校验 resource

- **问题**：提示文件缺失只降级为一个"缺少提示文件"的弹窗（`main.py:1022`），生产模式照样启动。
- **建议**：载入期检查 `resource` 指向的文件是否存在：生产模式拒绝启动，调试模式告警——与 adaptation 白名单"未命中直接抛异常"同口径。
- **代价**：小。

### P2-2 等待可取消，不阻塞停机

- **问题**：`event.wait(timeout)` 一次性阻塞最长 1800s（`main.py:995`），任务被删除或服务停止时线程仍挂着。
- **建议**：分段等待（如 1s 一轮）并检查取消标记；任务删除时主动置位事件并按中止收尾。
- **代价**：小。

### P2-3 资源形态与语言

- **建议**：允许 `resource/` 下放图片、yaml 等附件（现在只允许 md/markdown/txt）；提示文件支持 `xxx.zh.md` / `xxx.en.md` 按界面语言选取；`parallel` 段落中出现人工条目时明确禁止并行（避免"停一条卡整段"）。
- **代价**：小到中等。

## 五、建议的清单形状（草案）

```jsonc
{
  "no": 3,
  "id": "M-01",
  "name": "装夹与外观确认",
  "hold": {
    "phase": "before",                  // before = 执行前等人（原 type: manual）；after = 跑完再停（原 step: true）
    "resource": "appearance_check.md",  // 提示与图片，来自包内 resource/
    "timeout_s": 1800,
    "on_timeout": "abort",              // abort | fail | wait
    "options": ["next", "fail", "abort"],
    "fields": [
      {"key": "gap_mm", "label": "装配间隙", "type": "number", "unit": "mm",
       "limits": {"min": 0.1, "max": 0.5}},
      {"key": "verdict", "label": "目视结论", "type": "select",
       "choices": ["合格", "返修"]}
    ],
    "evidence": {"photo": true, "note": true},
    "on_abort": "run"                   // 中止后本条是否仍执行（安全动作默认 run）
  }
}
```

## 六、迁移路径

| 阶段 | 动作 | 影响面 |
| --- | --- | --- |
| 1 · 兼容读 | 运行时同时接受旧键与 `hold`，`hold` 优先；校验器对两者都能定位报错 | `manifest.py`（校验 / 解析） |
| 2 · 合并通道 | `_await_manual` 与 `_await_step_hold` 合并为一个 `_await_hold`，靠 `phase` 分派 | `main.py:1007-1067` |
| 3 · 界面与记录 | 统一形态 + `fields` / `evidence` 表单；`holds[]` 进 `run_result.json` 与报告 | `ExecuteView.vue`、报告模板 |
| 4 · 切换模板与文档 | `tps-template.jsonc` 示例改 `hold`；文档 §9.1 / §9.3 合并为「挂起点」一节 | `docs/` |
| 5 · 收紧 | 旧键标 deprecated 并告警，一个发布周期后移除 | 校验器 |

## 七、需要你定的取舍

| 编号 | 取舍 | 我的倾向 |
| --- | --- | --- |
| 1 | `fail`（人工判不合格但继续）要不要 | 要，产线更常见的是"这条不合格、后面继续测" |
| 2 | 录入值是否参与阈值判定 | 先做记录，判定留到第二期，避免人工录入的口径争议 |
| 3 | 证据（照片 / 备注）是否必要 | 取决于工控机有无摄像头；没有就先只做备注 |
| 4 | `on_abort` 默认值 | 沿用现状（测试段跳过、收尾段执行），只补显式声明能力 |
| 5 | 双人签核 | 关键安全环节建议要，其余不要 |
| 6 | 旧键双读窗口 | 一个发布周期足够 |
