02

三条实测结论（不是推断）

实测 ① · 模板本身

去注释后合法，且过现网校验

16678 → 11269 字符（去注释后）；validate_v2 返回 0 错误； normalize_tps 得到 setup 1 / test 5 / teardown 1 = 7 步， 7 项阈值全部被 checks 引用（无孤儿阈值）。

实测 ② · 版本号陷阱

升成 tps.v3 会两头不一致

is_v2() 因「有 cmd_suit 且无 steps」的兜底判据，对 tps.v3 仍返回 True； 但 validate_v2 会直接报 schema 只支持 tps.v2（实际: tps.v3）。 结论：本次模板保持 "tps.v2"；真升 v3 必须同时改这两处，否则是"被当 v2 处理但不让通过"。

实测 ③ · 校验的空白

只查引用，不查孤儿，也不查跨表一致

现网校验拦得住的：未定义阈值被引用、id 重复、case 格式、min>max、缺 case/name。 拦不住的：定义了却没人用的阈值、device_id 是否真在测试台 BOM 里、 slot.fixture 是否存在于 BOM、threshold_overrides 的键是否是已定义阈值——这四条正是并行测试最容易错的地方。

现状 · 并发能力

现网是单 SN 串行

collect_cases() 里写死 uut="COLLECT00001"， stage(tps, source_dir, task_id, uut=…, bench_id=…) 收单个 SN 字符串； bench.serial 是空占位。多通道并行不是"加个字段"，而是任务模型要按 (SN × 通道) 扇出。

03

并行多 SN 的真实难点：不是通道数，是仪器资源互斥

这是我认为你这套设计里最需要先想清楚的一点。四个通道并行时，DUT 侧天然隔离（四个夹具、四个 SN）， 但仪器侧不是：示波器只有 8 个输入口、转速控制盒只有一个 DUT 接口、电源可能只有两路输出。 如果 pn.channels 只写一个 count: 4， 调度器无从判断"这几个通道能不能真的同时跑"，结果就是两路同时抢 COM6 拿转速 → 数据串台 → 误判，而 报告上看起来一切正常。

所以模板把通道拆成两层声明：resource_bindings 说明每通道占用哪些物理通道， shared_resources 说明哪些资源全局只有一份、必须排队。

// pn.channels.slots[i] —— 通道占用了什么，决定"能不能并行"
"resource_bindings": [
  { "alias": "scope", "instrument_channel": "CH1" },   // 8 通道机型：CH1..CH4 各喂一个 DUT，可并行
  { "alias": "psu",   "instrument_channel": "CH1" },   // IT6332A 双路：CH1/CH2 可并行，CH3、CH4 需排队
  { "alias": "spin",  "instrument_channel": ""    }    // 单 DUT 口 → 必须排队
],
"threshold_overrides": { "TC_SIG_VPP": { "min": 2.28, "max": 2.52 } }  // 通道间探头衰减差异就地修正

// pn.channels.shared_resources —— 全局唯一资源，调度器据此串行化
"shared_resources": [
  { "alias": "spin", "reason": "单台转速控制盒只有一个 DUT 接口", "queue": "fifo" }
]

对应地，每条用例用 parallel 声明自己的并发属性：per_channel 的（测电压、测波形）四通道可同时跑； shared 的（要动转速控制盒）先抢占资源再执行。这样调度器不用理解业务，只看声明就能排程。

04

改进意见：5 条 P0，4 条 P1，4 条 P2

按"不做会不会在产线上真出问题"排序。每条都标了影响面——决定改动落在 parser、前端还是报告。

级别建议理由 / 现状差距影响面
P0 声明式资源互斥
slots.resource_bindings + shared_resources + cmd_suit.resources		 并行时仪器是共享资源。没有声明，两通道抢同一串口会得到"看起来正常"的错误数据——比直接报错更危险。 调度器 / 任务模型
P0 阈值分级 severity
critical / warning / info		 现网只有 min/max，超限一律 fail。实际产线需要"超上限记警告但放行"（如握手响应 50ms）。目前只能塞进 case 内部硬编码，判定逻辑散落在 AW 里，报告不可复现。 parser + 报告 + 前端
P0 exec 超时/重试进 schema
timeout_s / retry.max / interval_s / on_fail		 你明确要"重试次数、超时时间"，但现网 schema 没有这两个键——写进 params 就没有统一语义，报告也读不到，前端更展示不了。目前唯一的超时是 collect_cases 里硬编码的 120s。 parser + runner + 报告
P0 teardown 强制回收
teardown[].always_run		 异常中断若不执行 teardown，3.3V 电源和转速控制盒会一直带电——这是安全事故而不只是数据问题。现在 teardown 存在，但 schema 不表达"必须执行"。 runner
P0 SN 只存规则不存值 + 记录加通道维度 SN 写死在 TPS 里，每换一批物料就要改受控文件。同时 records 表现在按 12 位 SN 查询，并行后必须加 channel，否则一份报告分不清哪个通道测的哪台。 DB schema + 报告 + 查询
P1 阈值双向校验 + 跨表一致校验 现网只查"引用未定义"。建议补：孤儿阈值、device_id 是否在测试台 BOM 的 items[].id 里、fixture 是否存在、threshold_overrides 键是否已定义。这四类错误现在要等到运行时才暴露。 manifest 校验
P1 容差表达式 tol
nominal ± 5% → 自动推导 min/max		 现在要手写 3.135 / 3.465，手算易错且改动标称值时要重算两个数。tol 保留表达意图，解析期推导上下限。 parser + 前端表单
P1 params 拆分设备引用与数值 现在 params 里 psu_alias 和 voltage 混放。并行时设备引用应由 slot.alias_suffix 自动注入（psu → psu_c1），人工拼别名在多通道下必错。 parser + AW 契约
P1 统一比较口径 decimal 浮点比较需要显式位数（3.4649999 判成超限是典型误判）。当前 _fmt() 只管显示格式，不管判定。 parser + 判定逻辑
P2 JSON Schema 落库 + VSCode 联动 现在是"导入时后端报错"。有了 schema，编辑器里边写边标红，且能自动补全 checks 里可引用的阈值键。 docs + .vscode
P2 checksum + 发布状态门禁 产线只接受 status=released 且校验和匹配的 TPS——否则改了文件不递版本，报告里的 version 与实际内容无关。 parser + 运行入口
P2 tags 选择性执行 ["smoke"] 子集能在换型/排障时几分钟拿到结论，不必跑满套。现在只能删用例或全跑。 前端 + runner
P2 登记 aw 库版本 uut.json 里 case 指向 module::function，AW 库升级会让同一个 uut.json 行为改变。建议 metadata 里锁定 aw_version，与 driver SDK 文档的做法一致。 metadata + 依赖校验
05

要改的三处代码（按最小改动）

1 · manifest.validate_v2：接住新键

新增 metadata / pn 的必填与内联校验；给 testconfig[*] 加 type / severity / decimal 的枚举与类型检查；给 cmd_suit[*] 加 exec 结构与 retry.max >= 0 一类数值约束。

# 建议插入位置：validate_v2 的 testconfig 段之后
pn = raw.get("pn") or {}
channels = (pn.get("channels") or {})
slots = channels.get("slots") or []
if channels.get("count") and len(slots) != int(channels["count"]):
    errors.append(f"pn.channels.count={channels['count']} 与 slots 数量 {len(slots)} 不一致")
seen_ch, seen_pair = set(), set()
for i, s in enumerate(slots, 1):
    ch = s.get("channel", i)
    if ch in seen_ch: errors.append(f"pn.channels.slots[{i}].channel 重复: {ch}")
    seen_ch.add(ch)
    for rb in (s.get("resource_bindings") or []):
        pair = (rb.get("alias"), rb.get("instrument_channel") or "-")
        if pair in seen_pair:      # 同一仪器同一通道被两个 slot 占用 = 并行必然串台
            errors.append(f"资源冲突: {pair[0]} 的 {pair[1]} 被多个通道占用")
        seen_pair.add(pair)

# 用例侧：retry / timeout 的边界
exec_spec = case.get("exec") or {}
if not isinstance(exec_spec, dict):
    errors.append(f"{prefix}[{index}].exec 必须是对象")
else:
    rt = exec_spec.get("retry") or {}
    if rt and (not isinstance(rt.get("max"), int) or rt["max"] < 0):
        errors.append(f"{prefix}[{index}].exec.retry.max 必须是非负整数")

2 · workspace.stage()：从单 SN 变成 (SN × 通道)

现在签名是 stage(tps, source_dir, task_id, uut, bench_id, mode)，单 SN 单跑。 并行需要按 slot 扇出：每个通道一个 run 目录、一份生成用例，别名按 alias_suffix 注入。建议保持单通道签名不变，新增 stage_channel(slot, uut, …) 由上层批量调用—— 这样单件场景零回归。

3 · 报告与 records：加 sn 与 channel 两个维度

并行后一份任务对应多台 UUT。records 表需要 (task_id, channel, sn) 维度， 报告里按通道分组并给出各自结论；否则"这次任务通过了吗"这个最基本的问题会变成"哪些通道通过"却答不上来。

06

建议的落地顺序

  1. 先加 P0 的两个字段并只做校验，不改执行

    exec.timeout_s/retry 与 teardown.always_run： 写进 schema、过校验、在报告里显示，但执行侧先沿用现有行为。这一步零风险，却能立刻暴露现有 TPS 里"超时靠猜"的地方。

  2. 阈值分级与 decimal

    把 severity 接进判定与报告着色。建议先只对 warning 级做"记录不拦"，跑两周看有多少原本 fail 的项其实是 warning，用数据验证分级标准。

  3. 单通道下的 pn + metadata

    先让 count: 1 的 pn 走通全链路（批次校验、SN 形态校验、metadata 进报告头）， 把 parser / 前端 / 报告三处改完，再谈并行。这样并行的复杂度落在已验证的地基上。

  4. 并行调度：资源互斥 + 任务扇出

    实现 shared_resources 队列与 stage_channel 扇出， 先用两个通道跑同一份 TPS 验证隔离性，再放到产线工位。

  5. 补 P1 校验与 P2 门禁

    跨表一致性校验、JSON Schema + VSCode 联动、checksum 与发布门禁——这些是长期护栏，前置成本高但一次投入长期有效。

07

取舍与风险

取舍 ①

为什么设备信息里不写 IP / 端口

你最初提到 uut.json 里含 device_info（设备 IP/端口），但现网把连接参数放在测试台注册库（SQLite）， TPS 只写别名引用。这个方向是对的：TPS 是受控文件、要跨台架复用；写死 IP 意味着换台架就改程序集。 模板沿用 device_config 别名引用，连接参数仍由注册库解析。

取舍 ②

为什么叫 device_config 而不是 device_info

现网 validate_v2、case_entries、前端计数都用这个名字，改名会打断已有 TPS。 如果想要 device_info 这个名字，建议 parser 同时接受两个键（别名映射），而不是重命名。

风险 ①

并行把"偶发问题"放大成"批量误判"

单通道时串扰只是偶发；四通道共用一台仪器时，资源冲突会稳定复现成数据串台。 这就是为什么我把资源互斥放在 P0 而不是放到实现阶段再说。

风险 ②

扩展键写了但没人读

最坏的情况不是校验失败，而是"写进模板 → 以为生效 → 实际被忽略"。 建议每加一组键，同步加一条校验或一处报告展示，做到"写了就一定有反馈"。
