01

判定准则：三层过滤

cmd_suit 的每一项与 testcase/ 下的一个 pytest 用例 1:1 对应， 这个前提决定了字段的归属。任何一个字段，问三个问题就能定性：

过滤器 A · 保留

py 用例不可能知道的信息

执行顺序、超时、重试、失败后是否继续、在哪个通道跑、要不要排队抢仪器、这次要不要跑（条件跳过）。 这些是"这次运行怎么组织"的事，用例代码无从得知，必须写在编排层。

过滤器 B · 删除

py 用例已经表达的信息

用例叫什么、干什么用的、默认参数是多少、属于哪一类（pytest marker）。已有 case 指向那个函数，再写一遍名字与描述，就等于同一事实有两个来源——改了一处忘了另一处，报告和代码就会对不上。

过滤器 C · 合并

字段之间语义重叠

同一件事有两种写法时，必然出现"两种写法行为不一致"的退化情况。典型：optional 与 on_fail / skip_when 都在表达"这条可以不过"； on_timeout 与 on_fail 在表达同一类策略。

边界 · 阈值归属

为什么 checks 不算重复

阈值（testconfig）需要测试工程师评审、按批次调整，不能埋进代码； 而 py 用例只能产出"VDD = 3.31 V"这样的测量值。所以"测量项名 → 阈值键"这个映射是代码与阈值的 join 契约，是编排层最有价值的字段之一，必须留。

02

逐字段判定

字段判定依据去向 / 替代
no删除 数组顺序即执行顺序。再写一个 no 就有了两个顺序来源——拖动排序后忘改 no，报告就与执行次序不符。 用数组下标；展示编号由前端生成
name删除 用例名就在 py 函数名与 docstring 里。实测：现网校验器把 name 当必填（见第 04 节），删它需同步把该校验降级。 collect 阶段从 docstring 注入显示名
description删除 同 name，属于用例自身的说明，重复写会漂移。 docstring；若要写"为什么纳入本测试套"，用 suite_note（可选，非重复语义）
tags删除 pytest marker 已经在做同一件事（@pytest.mark.smoke），两处写必然不一致。 读 py 的 marker；collect 时提取
optional删除 与 exec.on_fail=continue（失败不中断）和 skip_when（不满足则跳过）语义重叠，三者组合出多种行为组合，无法规约。 合并进 exec.on_fail + skip_when
depends_on删除 线性编排下顺序已由数组表达；"前置失败则跳过"由 on_fail: abort 表达。只有做 DAG 编排才有价值，而这套是顺序套。 数组顺序 + exec.on_fail
params改名瘦身 现在混了两类：设备别名（psu_alias）与数值。别名已由 pn.channels.slots 与 device_config 确定，再写一遍在多通道下必错。 改名 args，只放需要覆盖的数值；别名由 slot 绑定自动注入
id保留 报告主键、历史记录横向对比、pytest node id 的稳定锚。case 也能当锚，但函数重构改名会割断历史数据。 保留；若接受"函数名即 ID"，可与 case 二选一
case保留 1:1 映射的唯一锚点，编排层最不可替代的字段。 建议同时升级校验：确认该函数在 testcase/ 里真实存在
checks保留 代码产出与阈值的 join 契约，交给测试工程师评审的入口。现网已校验"引用了未定义阈值"。 若某用例只判一个值，可退化为单值键
exec.timeout_s保留 纯编排语义，用例自己不该管"跑多久算超时"。 —
exec.retry保留 同上。"重试几次"是运行策略，写进 py 会让用例不可复用。 合并 on_timeout 进 retry.on: ["error","timeout"]
exec.on_fail保留 失败传播策略：中断 / 继续 / 记警告。py 用例无法决定自己在整个套里的角色。 作为 optional 的替代
resources保留 并行调度的前提。理论上可从代码静态推导依赖，但推导不可靠（AW 内部调用看不到），显式声明更安全。 与 slots.resource_bindings 加一致性校验，避免又一处分叉
scope / parallel保留 多通道编排信息，py 用例不知道自己在哪个通道跑。 只在非默认值时写：默认 channels=all、parallel=per_channel
skip_when保留 条件跳过（设备缺失、前置条件不满足），编排层语义。 与 testconfig 的 applicable_when 二选一，统一到用例层
always_run保留 teardown 专用：异常中断也必须执行，防设备带电。 —

04

实测证据：现网校验器对每个字段的必填性

做法：取完整 cmd_suit 的一条用例，逐个删掉字段后跑 validate_v2，看是否报错。

删除的字段现网是否拦下说明
name报错cmd_suit[1] 缺少 name（用例名称），空字符串同样报错
case报错cmd_suit[1] 缺少 case；且校验格式（module::function）
id / no / description / tags / optional /
depends_on / params / checks / exec /
scope / parallel / resources		 均不报错现网全部视为可选——这意味着只把多余字段删掉，不会撞任何校验
checks 引用未定义阈值报错唯一的跨字段校验：引用了未定义的阈值: TC_NOT_EXIST
case 指向不存在的函数不报错缺口：只校验字符串格式，不校验 testcase/ 里是否真有这个函数——1:1 映射下这恰恰最该校验
要注意的一处连带改动

删 name 会把 7 条用例全撞成错误

实测拼回完整 TPS 后 validate_v2 返回 7 条 缺少 name （1 条 setup + 5 条 cmd_suit + 1 条 teardown）。所以精简必须成对进行：要么保留 name， 要么把 _validate_case 里的 name 必填检查降级为可选（推荐后者，名字交给 docstring 注入）。 只删字段不改校验，结果就是所有 TPS 都导不进来。

05

更根本的问题：cmd_suit 该显式枚举，还是从目录派生？

你问的是"字段有没有多余"，但把字段砍到剩 8 个之后，会露出一个更大的重复： 如果每个用例与 testcase/ 里的 py 用例 1:1，那 cmd_suit 这份清单本身是否也多余？ 两种设计各有取舍，我倾向保留显式清单。

设计 A · 显式清单（推荐）

uut.json 枚举跑哪些用例、按什么顺序

优点：这份 TPS 跑什么，是一个能被人评审、被 diff 的受控事实；py 目录里新增一个用例不会悄悄进产线。 代价：需要维护清单，所以要补一致性校验（见下）。

适合产线：可审计性优先于省事。

设计 B · 目录即清单

自动收集 testcase/ 下所有用例，uut.json 只写覆盖与排除

优点：零维护，加用例即生效。 代价：新增用例会自动进入产线执行——这恰恰是受控测试程序集最不希望发生的事；且顺序依赖文件命名约定，重组目录就会改变执行次序。

适合研发自测，不适合量产受控。

选了 A，就要补两条一致性校验把这套设计守住——否则清单和目录还是会各自漂移。

06

精简后需要补的 5 条校验

序校验为什么必须类型
1name 必填 → 降级为可选 不降级，删 name 会让所有 TPS 校验失败（实测 7 条错）。改现有规则
2case 存在性校验 升级为"在 testcase/ 中确实能找到该函数"。现在只校验字符串格式，写错函数名要到运行时才炸。新增
3清单 ↔ 目录双向一致 清单引用了不存在的用例 → 报错；目录里有用例未被清单引用 → 提示（可能是漏排，也可能是刻意不跑）。新增
4默认值补齐 scope.channels=all、parallel=per_channel、on_fail=continue 在解析期填入，让"不写"有确定含义。解析期
5resources ↔ slots.resource_bindings 一致 保留 resources 的前提是它不能成为第二个事实源：用例声明的资源必须是该通道 slot 里真实绑定过的。新增
07

删掉 name 之后，报告里的用例名从哪来

这是精简方案唯一的实现依赖，路径是现成的——你的运行环境已经在用 pytest collect：

  1. 01
    py 用例写 docstring
    函数 docstring 首行即报告里的用例名，marker 即 tags。这是唯一事实源。
  2. 02
    collect 阶段提取
    pytest --collect-only -q 已能拿到节点 id；要拿 docstring 与 marker， 在生成 test_tps_generated.py 的 wrapper 时顺带写入元数据，或改用带 JSON 输出的 collect。
  3. 03
    报告与前端消费
    报告标题、步骤列表文案都从 collect 结果取；uut.json 不再参与命名，从此不存在"改了名字报告没更新"的情况。

代价要说清楚：这一步让"改文案"从改 uut.json 变成改 py 代码——对测试工程师来说门槛变高了。 如果你更看重"现场工程师不碰代码就能改文案"，那就保留 name，并加一条校验：与 docstring 不一致时告警。 这是一次明确的取舍，两种都成立，别两种都留一半。
