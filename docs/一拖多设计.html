一拖多设计：单个测试站控制柜支撑多个测试台

01 · 问题背景

1.1 需求与约束

项说明
提效需求同一测试站控制柜下支撑多个测试台运行，提高工位利用率与产出
GPB 产能限制GPB（general process board）的数量与内部资源有限，无法为每个测试台各配一块
由此产生的约束单个控制柜需要连接同一个 GPB，并在该 GPB 上支撑多个测试台运行

1.2 当前方案

当前做法由上位机驱动机器上的 Python 测试脚本，经 SSH 连接 GPB，执行 GPB 上的 .sh 脚本，通过修改寄存器完成测试执行。一个测试站连接多个测试台时，分时向同一个 GPB 下发多条命令，每条命令对应一个进程。

环节当前做法
命令下发上位机工控机 PC 上的 Python 测试脚本，经 SSH 连接 GPB
测试执行执行 GPB 上的 .sh 脚本，脚本直接修改寄存器
多台支撑分时向同一个 GPB 下发多条命令，命令之间串行执行，每条命令一个进程
版本与部署脚本与内部工具随 GPB 部署，版本不在上位机侧受控

1.3 该方案可能存在的问题

编号问题性质
1.sh 脚本调用的是电子电气的内部工具，不适合对外暴露，也不适合作为测试台正式发布软件固定问题（已确认）
2多台测试台分时共用同一个 GPB：无法并行，排队时间随测试台数量增长待评估
3命令与进程数随测试台数量增长，运行状态与结果分散在各进程，缺少统一记录待评估
4脚本直接修改寄存器：缺少参数校验与通道隔离，多台并存时通道配置容易互相干扰待评估

02 · 正式方案：ATE Runner 一拖多

2.1 机制

ATE Runner 维护多个测试台相同的设备 BOM，通过设备 BOM 将测试台注册为多个工位实例，每一个实例有自己的执行网页页面。各测试台不同的设备通道配置写在装备属性配置模块的 DB 数据库中。测试执行时通过 pytest 将这些参数传递给测试用例，测试用例与 GPB 上的设备管理进程建立 gRPC 连接；这些测试工控机下发的命令实际都发给了同一个 GPB 上的设备管理服务，由此达成同时支撑多个测试台的目的。

环节做法
设备 BOM维护多个测试台相同的设备 BOM，多台共用同一份设备清单
工位实例通过设备 BOM 将测试台注册为多个工位实例，每个实例有独立的执行网页页面与运行上下文
通道配置各测试台不同的设备通道配置写入装备属性配置模块的 DB 数据库
参数注入测试执行时通过 pytest 将通道配置等参数传递给测试用例
连接方式测试用例与 GPB 上的设备管理进程建立 gRPC 连接
汇聚点各测试工控机下发的命令，实际都发给了同一个 GPB 上的设备管理服务

实际数据出处页面上的读法
测试台 BOM（7 台设备）backend/tree/bom/SPM-RH-DYN-01.json，由元数据管理 · 测试台 BOM 管理维护设备 BOM 是注册工位实例的依据，多台测试台共用同一份清单
工位实例记录backend/ate.db · 表 bench_registry（id、preset_id、serial、station）同一 preset_id 可注册多个工位实例，每个实例有自己的执行页面
通道与驱动配置backend/ate.db · 表 device_registry（interface、protocol、host、port、channel、driver）各台测试台不同的通道配置写入该表，执行时由 pytest 注入用例

2.2 与当前方案的差别

对比项当前方案正式方案（ATE Runner）
执行主体GPB 上的 .sh 脚本，调用电子电气内部工具工位实例中的 pytest 用例，调用通用驱动接口
通道差异集中在脚本与 GPB 侧，随台数增长而复杂写入装备属性配置模块的 DB，由 pytest 注入用例
多台支撑分时下发命令，多个独立进程串行执行多个工位实例同时在线，共用一个设备管理服务
对外发布内部工具随软件发布，存在暴露风险对外发布的软件只包含 ATE Runner 与通用驱动

2.3 待确认事项

编号事项
1GPB 设备管理服务的接口清单、并发上限与超时约定
2工位实例与设备通道的绑定关系落库位置（装备属性配置模块的 DB 表结构）
3设备管理服务的连接复用与断线重连策略
4单个工位故障时的隔离方式，是否影响其他工位的运行
5执行页面、工位实例与物理测试台三者的对应关系维护方式
本文与《一拖多设计》演示稿同源，机制描述以工位实例、装备属性配置模块 DB 与 GPB 设备管理服务三者的关系为主。
