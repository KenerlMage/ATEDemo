tps.json 的每个字段：为什么存在，谁在什么时候读它

逐字段核对了定义（manifest.py）、注入（workspace.py / conftest_template.py）、 报告与落库（main.py）。顶层 16 个字段里 只有 4 个必需；另有 3 个字段是声明了却无人执行的死胡同或双源。 设计意图可以概括成三条：声明式、引用而非配置、判据集中判定分离。

01

字段在生命周期中的六个落点

同一个字段在不同阶段由不同代码读，理解字段必须连着阶段看——这是"使用方式"的全貌。

01
发现load_tps_files
扫 testresource/：子目录里的 tps.json 是 v2 包，顶层 *.json 是 v1 单文件。
02
识别is_v2
schema == "tps.v2"，或兜底判据"有 cmd_suit 且无 steps"。
03
校验validate_v2
必需项：id / testconfig / device_config / cmd_suit；条目必需 case + name。
04
归一化normalize_tps
补默认值、展开 steps，产出 step_count / testconfig_count / device_alias_count。
05
生成与注入stage
按 workspace_dir 建目录、复制临时副本、渲染 test_tps_generated.py、写 ate_env.json。
06
执行与记录conftest
读运行副本的 testconfig / device_config，判定写 run_result.json → 报告 → test_records。

注意第 06 步的"副本"二字：每次运行都会 copytree 源 TPS 到 run_<task_id>，所以改源清单立即生效，各次运行互不污染——这也是为什么运行期读到的阈值一定等于当次快照。

02

五组字段

A · 身份与元信息

schema / id / name / version / description / project / dut

回答"这是哪个测试程序集、属于哪个项目与 DUT"。其中 project 与 dut 不只是展示——它们是记录查询的过滤维度。

报告标题 · 列表分组 · test_records.project/dut
version 无校验、无独立列
B · 落位与台架

workspace_dir / environment / bench

workspace_dir 决定运行目录名；environment 是人读快照；bench 声明"该跑在哪台/哪类台架"。

bench_id → preset_id → serial 依次匹配注册库
匹配失败只告警不阻断
C · 装备引用

device_config：别名 → device_id / role / category / model

解耦"业务命名"与"物理连接"。先按 device_id 精确命中，再按 role/category/model 模糊匹配；失败进 driver_errors。

IP/端口/串口 一律来自 SQLite device_registry
note 不参与匹配，只是注释
D · 判据

testconfig：阈值键 → label / min / max / unit / nominal

阈值是受控数据：可评审、可按批次调整、在报告里显示。判定动作由消费方执行（check / expect）。

至少给 min 或 max；min>max 报错
nominal / unit 不参与判定
E · 用例三段

setup[] / cmd_suit[] / teardown[]

顺序即执行顺序。条目字段：id / no / name / case / description / params / checks / config / optional。

case 指向 testcase/ 实现：module::function
整个条目会被 repr 进生成文件
F · 派生（不手写）

steps / step_count / *_count / _raw / _generated / kind / func

由归一化与 case_entries 产出，供既有任务模型、进度条、报告复用；_raw 保证写回副本时不带派生字段。

v1 的 steps 与 v2 的 cmd_suit 互斥
同时出现直接报错

04

14 条现网观察：死字段、双源与坑

每条都对应可复查的代码位置。前三条最值得优先处理。

01
optional
死字段：全库只在 manifest.py 出现（校验布尔类型 + 透传），conftest 与 runner 都不读。写了"可跳过"不产生任何效果。
02
checks ↔ ctx.expect
判定双轨：_apply_checks 只在"返回值 + checks 映射"路径生效；用例若已内部 expect，返回标量会被再判一次。需二选一并写进准则。
03
params 里的 *_alias
双源：样例里 psu_alias / dmm_alias / awg_alias / scope_alias / motion_alias / fixture_alias / eload_alias 共 7 个别名参数，而别名的事实源是 device_config。多通道并行时人工拼别名必错。
04
no
与数组顺序双源（缺省取下标）。重排顺序忘改 no，报告序号与执行次序不一致。
05
name
必填但纯展示，与 testcase/ 函数 docstring 重复。
06
description（条目级）
无渲染消费点：仅经 steps_of 透传，报告步骤表用的是 name 与运行期 detail。
07
version
无校验、无独立落库列，只出现在报告副标题里，无法按版本检索记录。
08
unit / nominal
不参与判定：check() 只用 min/max，unit 仅拼消息文本。
09
environment.interfaces
值是数组时会被原样字符串化进报告（f"<td>{v}</td>"），页面上显示为 Python 列表字面量。
10
workspace_dir
改它等于换运行落位：旧运行记录留在旧目录，list_runs() 不再扫到，现场会误判"记录丢失"。
11
bench 匹配失败
只返回 bench_warning 并继续准备运行；设备全未匹配要等用例调 ctx.driver() 才暴露。
12
project / dut
自由文本却是查询维度（记录查询按项目/批次过滤），同义不同字会让记录查不全。
13
device_config.note
不参与匹配，是注释；误当配置项会以为它有作用。
14
steps ↔ cmd_suit
v1/v2 双路径并存，互斥检查只在两者同时出现时触发；维护时容易混写。
05

三条设计意图

意图 1

声明式

清单只声明"测什么、按什么判"，实现留在 testcase/。所以 case 是引用、description 只是说明——没有执行逻辑藏在清单里。

意图 2

引用而非配置

装备只写"别名 → 设备编号/角色"，连接参数一律走 SQLite；台架只写"跑在哪台/哪类台架"。这让同一份 TPS 能跨台架复用。

意图 3

判据集中，判定分离

阈值集中在 testconfig（可评审、可按批次调整），判定动作由消费方执行。阈值是数据，判定是行为，两者不混。

按这三条回看样例：它的问题不在"写错了"，而在清单里塞了本该属于代码的东西（别名参数、用例描述、序号），以及声明了却不生效的东西（optional）。上面 14 条观察的共同根源就在这里。
