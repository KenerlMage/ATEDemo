# 设备驱动库的分发方式与「货架」方案建议

**日期**：2026-09-13　**状态**：设计建议（未实施）　**依据**：当前 `backend/drivers/` 实现 + 离线工控机部署约束

**一句话结论**：**分层分发**——平台内置「稳定契约 + 通用设备家族」，型号/品牌专用驱动走**货架包**，客户专有驱动走**现场侧载**；远端服务器只是三种驱动来源之一，安装器必须同时支持离线镜像（U 盘 / 内网目录 / 共享盘），否则离线工控机会被货架卡死。

---

## 一、先分清两类消费者，再谈"用什么方式提供"

现在的 `drivers/` 是**一份代码同时服务两种人**，这是分发方案要拆开的根本原因。

| 消费者 | 他要什么 | 变化频率 | 该给什么 |
| --- | --- | --- | --- |
| 测试用例开发者（TPS 作者） | 稳定的调用契约：类名、方法、单位、异常、示例 | 低（季度级） | **内置契约包 + 类型存根 + 示例用例 + 装备助手调试台** |
| 平台 / 集成工程师 | 具体型号的实现：SCPI 命令、解析、仿真模型 | 高（每来一个新设备型号一次） | **可插拔驱动包（货架 / 侧载）** |

对应到内容，也分三层：**契约（稳定 API）→ 通用实现 → 型号细节**。今天 `factory.py` 里的 `DRIVER_SPECS` 把这三层混在一张硬编码表里（`cls` 直接指向类对象），意味着**新增一个型号 = 改平台代码 + 重启后端**。

---

## 二、推荐架构：四层驱动

| 层 | 内容 | 分发方式 | 举例（对应现状） |
| --- | --- | --- | --- |
| **L0 契约层** | `Driver` 基类、`DeviceConfig`、错误类型、会话句柄、`scope.v1` / `dmm.v1` 这类 API 版本约定 | **随平台内置，冻结** | `drivers/base.py`、`models.py`、`errors.py` |
| **L1 通用家族** | 不挑品牌、靠 SCPI 通用命令就能干活的能力族 | **随平台内置** | `scpi.py` 的 `Dmm/Psu/ELoad/Awg/Motion`、`generic-scpi` 兜底 |
| **L2 型号专用包** | 型号级细节 + 仿真模型 + 自检清单 | **货架包，可下载** | `scope.py` 的泰克 MSO5 系列（现硬编码在内） |
| **L3 现场私有包** | 客户专有设备、保密协议下的实现 | **侧载，不上架** | 暂无（预留） |

**判断一个新驱动该放哪层，用三个问题**：① 它是否有跨品牌的稳定抽象？→ 有则属 L1 契约/通用层；② 换品牌后命令是否就得改？→ 是则属 L2 型号包；③ 客户是否要求代码不外流？→ 是则属 L3 私有包。**"常用"不是入内层的标准**——常见但命令各异的型号（如各家的电子负载）仍应做成包。

---

## 三、货架方式是否合适：合适，但要修正两点

你的方向是对的，且是这个规模的必经之路；需要修正的是边界。

| 方案 | 优点 | 致命问题 |
| --- | --- | --- |
| **A. 全部内置在平台代码**（现状） | 版本一致、最稳、无网络依赖 | 每加一个型号就要发版；现场离线升级成本高；平台代码随设备数量线性膨胀 |
| **B. 全部走远端货架下载** | 扩展快、平台体积小、可按需装 | **离线工控机直接不可用**；无签名则等于远程代码执行；版本漂移导致"同一版本平台行为不一致" |
| **C. 分层 + 多来源（推荐）** | 兼顾稳定性与扩展性；离线可用；可控可审计 | 需要先定义包规范与兼容矩阵，有一次性设计成本 |

需要修正的两点：

1. **"常用设备预装"的标准应改成"契约与通用家族预装"**。预装的是 L0/L1；型号细节即使常见，也应做成 L2 包，这样平台不会因为某个品牌命令变更而被迫发版。
2. **远端货架只能是"来源之一"，不能是唯一来源**。现场验收、产线断网、客户内网隔离都是常态。安装/更新界面必须同时提供：官方远端源、离线目录源（U 盘/共享盘）、本地 zip 侧载——**三者走同一套 manifest 与校验流程**。

## 四、驱动包标准（决定货架能不能跑起来）

每个驱动包 = 一个 zip（内含纯 Python 代码，零第三方依赖优先），根目录一个 `driver.json`：

```json
{
  "schema": "ate.driver.pkg.v1",
  "key": "tektronix-mso5",
  "version": "1.2.0",
  "family": "scope",
  "api": "scope.v1",
  "min_platform": "1.0.0",
  "entry": "driver:ScopeDriver",
  "match": { "model": ["mso5", "mso54", "mso64", "dpo5"], "vendor": ["tektronix"] },
  "priority": 20,
  "capabilities": ["identify", "acquire_waveform", "measure", "timebase", "channel"],
  "simulate": true,
  "depends": [],
  "files": [{ "path": "driver.py", "sha256": "…" }],
  "signature": "base64(ed25519(driver.json + files))"
}
```

关键字段的作用：

- `api`：声明实现哪套契约（`scope.v1`）。**平台按 api 版本判断兼容性，而不是死绑平台版本**——契约不变，平台小版本升级不必重编驱动。
- `match` + `priority`：直接并入现有 `resolve_spec()` 打分选择；平台侧只需把"内置 `DRIVER_SPECS`"与"已装包 manifest"**合并成一张注册表**，选择逻辑零改动。
- `simulate`：**必须声明是否带仿真模型**。工控机现场常常没有实机，装完包能在装备助手直接看波形，是货架可用性的底线。
- `signature`：Ed25519 签名，**离线也能验**。

### 加载与隔离

- 目录：`<ATE>/drivers/<key>/<version>/`；已装清单位于 `<ATE>/drivers/packages.json`（版本、来源、安装时间、启停状态、校验结果）。
- 装载：进程内 `importlib` 动态加载；**单个包加载失败只降级（回落到 `generic-scpi`）并告警，不阻断平台启动**。
- 风险控制：驱动包是可执行代码。一期用**签名 + 白名单 + 审计日志**；L3 私有包可显式关闭签名校验（需管理员操作并留痕）。若将来要跑第三方提供的代码，再考虑子进程隔离。

## 五、三种来源，一套流程

| 来源 | 场景 | 实现 | 校验 |
| --- | --- | --- | --- |
| 官方货架 | 联网 / 客户内网有镜像 | `GET index.json` → 下载包 | 签名 + `index.json` 自身签名 |
| 离线目录 | U 盘、共享盘、内网 HTTP 目录 | 指向目录，扫 `index.json` | 同上（离线镜像与官方同签） |
| 本地 zip 侧载 | 单个私有包、临时调试 | 直接选文件安装 | 签名可豁免（显式开关 + 审计） |

`index.json`（货架目录清单）建议只做静态文件 + 签名，**一期不要写服务**——用 Nginx/共享盘托一个目录就够，后期再考虑权限与统计。

## 六、版本与兼容治理（避免货架变垃圾场）

- **同 key 只允许一个 active 版本**，保留上一版以便回滚；禁止同 key 多版本并存参与打分（会导致结果不可复现）。
- 安装前做**兼容性预检**：`api` 是否受支持、`min_platform` 是否满足、`depends` 是否齐备，不满足则拒绝并给出明确原因。
- **双通道**：`stable` / `beta`，现场默认 stable。
- **兼容矩阵**：每个包在文档里给出「型号 → 驱动 key → api 版本 → 已验证固件/序列号」。
- **可复现**：报告与运行记录里落 `driver.key + version`，出问题能定位到具体驱动版本。

## 七、面向用例开发者，用什么方式交付"库"

| 交付形态 | 说明 | 优先级 |
| --- | --- | --- |
| 契约包 + 类型存根 | 内置 `ate_drivers`（`.pyi` 或纯 Python stub），用例里 `from ate_drivers import scope` 即有补全与签名提示 | 必做 |
| 示例用例 | 每个驱动包附 `examples/`（可直接抄进 TPS 的 pytest 片段） | 必做 |
| 装备助手即调试台 | 装包后工具卡片自动出现（现 `TOOL_CARDS` 机制），"边装边试"比纯文档有效 | 必做 |
| 兼容矩阵文档 | 型号 → key → api → 验证记录 | 建议 |
| **不建议**：把驱动源码给用例开发者改 | 会 fork 出私有分支，升级时无法合并——用 L3 私有包机制替代 fork | — |

## 八、可直接复用的现有资产

| 现有能力 | 复用到货架场景 |
| --- | --- |
| `factory.py` 的 `DRIVER_SPECS` 打分选择（`_score` / `priority` / 匹配字段权重） | 作为"内置 + 已装包"注册表合并入口，选择逻辑零改动 |
| `scope.py` 的 `_sim_samples` + `transport.py` 的 `SimulateTransport` | 驱动包自带仿真的既有范式，作为 L2 包的必备项 |
| `license_utils.py` 的 Ed25519 公钥验签 | 驱动包签名与 `index.json` 签名，**离线可验** |
| `instrument_tools.py` 的 `TOOL_CARDS` | 工具卡片随驱动包上架，形成"驱动 + 工具"一体的货架条目 |
| 打包方案里的嵌入式运行时与 `<ATE>/` 目录 | `<ATE>/drivers/` 天然可放安装目录内，升级只换 `app/`、`web/`、`drivers/` |

## 九、分阶段落地路线

| 阶段 | 内容 | 行为变化 | 预估 |
| --- | --- | --- | --- |
| 1 | `DRIVER_SPECS` 改为「内置 + 目录扫描合并」，定义 `driver.json` 规范；仍只加载官方包 | **零**（纯重构，回归全绿为准） | 1–2 天 |
| 2 | `<ATE>/drivers/` 目录 + 安装/卸载/启停/回滚接口 + 前端「驱动库」页（列表、版本、来源、校验、兼容性） | 新增界面与接口 | 2–3 天 |
| 3 | 签名校验（复用 Ed25519）+ `index.json` + 离线目录源 | 安装需过校验 | 1–2 天 |
| 4 | 官方货架（静态目录托管）+ beta 通道；把现有 MSO5 驱动抽成第一个包作为样板 | 第一个真实货架条目 | 1–2 天 |
| 5 | L3 私有包侧载 + 权限/审计；可选子进程隔离 | 支持客户专有设备 | 按需 |

阶段 1 是**纯搬运的零行为变化重构**，建议先做它——做完就能验证"驱动包注册表"这条路走得通，再往后投入界面与货架。

## 十、风险与对策

| 风险 | 对策 |
| --- | --- |
| 货架包成为远程代码执行入口 | Ed25519 签名 + 白名单 + 审计；L3 豁免需管理员显式开启 |
| 离线现场装不上 | 三种来源同流程；安装器内置"离线目录"入口，不依赖联网 |
| 版本漂移导致不可复现 | 同 key 单 active 版本 + 记录 `key@version` 到运行记录 + 支持回滚 |
| 平台升级后旧驱动失配 | 契约版本化（`scope.v1`）+ `min_platform` 预检 + 兼容矩阵 |
| 驱动包质量参差（无实机验证） | 上架要求：带仿真模型 + 自检清单通过 + 至少一台实机验证记录 |
| 货架内容膨胀、重复造包 | 上架评审：跨品牌稳定抽象一律进 L1，不进 L2 |
