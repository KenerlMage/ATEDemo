# 装备软件部署方案（合并版）

> 本文合并并取代 `deploy-design-dual-platform.md` 与 `deploy-design-target-binding.md`。实现位于 `backend/deploy.py`、`backend/deploy_api.py`、`D:\ATE_CONTROLLER\app.py`，界面在执行页。

## 一、目标与边界

把装备软件从「人工拷贝 + 手工执行脚本」变成「按 TPS 声明拉取、校验、部署、验证」。三条边界：

- 一个部署包只对应一个部署目标，不存在跨平台双目标；
- 部署必须显式指定目标，不通过探测或推断决定装到哪台；
- 本机只能是 PC（Windows），Linux 一律为远程服务器。

## 二、三种组合

| 组合 | 传输 | 执行 | 要点 |
| --- | --- | --- | --- |
| Windows + 本机 PC | 无，解压到 `deploy_runtime/<batch>/<seq>-<object>/package` | `subprocess`：`.ps1` / `.bat` / `.cmd` / `.py` / `.exe` | 需管理员的动作要求 Runner 以管理员运行，不静默提权 |
| Windows + 远程 PC | Agent（推荐）/ WinRM | 目标机本地解压执行并回传日志 | Runner 不持有目标机系统凭据 |
| Linux + 远程服务器 | Agent（推荐）/ SSH | `sftp` 投包 → `chmod +x` → `bash` → 回收日志 | `sudo` 仅白名单命令，禁用密码登录 |

统一抽象：`DeployTarget`（os / local|remote / host / transport / workdir）、`Transport`（put / run）、`PackageResolver`（object + version → 下载地址与脚本入口）。三者共用同一执行器，差异只在 `Transport` 实现。

## 三、TPS 的 deploy 字段

```json
"deploy": [
  { "key": "rh-driver", "package": "spm_rh_dyn@1.2.0",
    "target": { "id": "local" }, "mode": "ensure",
    "on_failure": "abort", "depends_on": [] },
  { "key": "line-svc", "package": "line_server@3.4.1",
    "target": { "id": "linux-srv-01" }, "mode": "force",
    "on_failure": "continue", "depends_on": ["rh-driver"] }
]
```

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `key` | 否 | 本 TPS 内唯一，缺省取 object 名；`[a-z0-9_-]{1,32}` |
| `package` | 是 | `object@version` 单字段；旧写法 `object` + `version` 自动合并 |
| `target` | 否 | `{"id": "..."}`，缺省 `local` |
| `mode` | 否 | `ensure`（默认，已装同版本跳过）/ `force` |
| `on_failure` | 否 | `abort`（默认，后续标 skipped）/ `continue` |
| `depends_on` | 否 | 引用其他 key，拓扑序执行；悬空或成环直接拒绝 |

已废弃：`name`、`required`、TPS 内的 `script`/`args`（改由包 manifest 提供，仅在需要覆盖时填 `script`）、`device_info`/`deploy_script` 兜底。

校验在 TPS 导入时执行（`tps_runtime/manifest.py`）：package 格式、key 唯一与字符集、mode/on_failure 枚举、target 形状、依赖引用与环。

## 四、包的 manifest

manifest 是随包发布的元数据，由 Controller 归档时生成，**在 zip 之外**，是唯一事实源。

包内不放 manifest：归档时若发现 zip 根目录存在 `manifest.json`，Controller 直接拒绝（400）。元数据只存在于仓库同级，Runner 通过 `/manifest` 读取，zip 目录仅用于校验 `entry` 与 `probe` 是否存在，不解压。


```json
{
  "object": "probe_ok", "name": "探测演示包", "version": "1.0.0",
  "entry": "deploy/install.bat", "platform": "windows",
  "sha256": "80fe00…", "size": 440, "uploaded_at": "2026-11-19T21:15:27+08:00",
  "deploy": { "probe": { "script": "deploy/probe.bat", "timeout_s": 10, "expect_exit_code": 0 } }
}
```

归档时的硬校验（均已实现）：

| 检查 | 失败表现 |
| --- | --- |
| `object` / `version` 字符集 | 400，防路径穿越 |
| `entry` 非绝对路径、不含 `..` | 400「entry 必须是包内相对路径」 |
| `entry` 真实存在于 zip 中 | 400「包内不存在 entry 指向的脚本」 |
| `entry` 后缀与 `platform` 匹配 | 400「脚本 .bat 与 platform=linux 不匹配」 |
| 同 `object@version` 已存在 | 409，必须发新版本 |
| `probe_script` 存在且路径合法 | 400 |

`sha256` 由 Controller 计算，下载响应头带 `X-Package-Sha256`，Runner 逐字节比对。

## 五、探测契约

部署记录只说明「平台做过什么」，不说明「机器上现在有什么」。因此包需提供探测脚本：

```json
{"installed": true, "version": "1.2.0", "path": "C:\\Program Files\\SPM\\rh", "detail": ""}
```

规约：只读、无副作用、无需管理员、10 秒内返回、`installed=false` 时必须给 `detail`、版本以目标机实际状态为准。

平台判定四态：`installed`（已装且版本一致）、`outdated`（已装版本不同）、`absent`（未安装）、`unknown`（探测缺失/超时/输出非法）。

执行策略：

1. 部署前先探测；`mode=ensure` 且 `installed` → 跳过；
2. 无 probe 的包回退到部署记录判断，并在消息中标注「未经验证」；
3. 安装后**强制再探测**，未通过或版本不符则该包失败；
4. 记录 `verified` 与 `probe_version` 供审计。

## 六、执行策略

- 单批次串行：同一时间只允许一个部署批次，执行中再次提交返回 409；
- 包内串行：按拓扑序执行，默认前序失败即中止，其余标 `skipped`；
- `mode=ensure` 支持幂等：已装同版本不重复下载执行（probe 优先，记录兜底）；
- 进程重启：遗留「执行中」批次标记为中断，释放执行位。

## 七、状态与接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/deploy/preview?tps_id=` | 预览待部署项，含 `installed_version`、`up_to_date` |
| `POST /api/deploy/run` | 提交批次（409 表示已有批次在执行） |
| `GET /api/deploy/status/{batch_id}` | 批次与逐项状态（含 `installed_verified`） |
| `GET /api/deploy/records?limit=` | 历史批次 |
| `GET /api/deploy/installed?object=&target=` | 已部署记录（对象+目标 → 版本、批次、路径、时间、verified） |
| `GET /api/deploy/controller` | Controller 连通性 |

数据表：`deploy_batch`、`deploy_item`、`deploy_installed`（含 `verified`、`probe_version`）。

## 八、现状与待办

已实现：TPS 字段与校验、包 manifest 与归档校验（含 platform、entry 存在性）、sha256 校验、脚本分派、探测验收、ensure 幂等、串行与失败中止、已部署查询、批次互斥与重启恢复。

待实现：目标注册表与前置校验（`target.os` / `platform` / `transport`）、Linux 执行器（`.sh` + `chmod`）、远程通道（Agent / SSH / WinRM）、探测结果四态接口与界面双状态对比、`requires` 前置条件。

## 九、风险

- 包与环境的耦合：`workdir`、`env` 写进包会让同一软件在不同现场需要重打包；约束是只写缺省值，允许 TPS 覆盖；
- 探测失真：探测脚本若读取包内文件而非安装位置，会永远返回未安装（示例包必须写到稳定路径）；
- 凭据：远程部署的管理员凭据集中托管，禁止出现在 TPS、包与日志中；
- 记录与实测不一致：必须以探测为准，记录仅作缓存与审计。

## 十一、沙盒与容器的适用性

结论：可以用，但必须按「软件形态」分层，不能把沙盒或容器作为所有部署包的统一承载方式。

### 11.1 适用性判断

| 场景 | 沙盒 | 容器 | 建议 |
| --- | --- | --- | --- |
| 纯软件服务（Linux 服务器：数据服务、报表、AI 推理） | — | 适合 | 用容器，镜像即版本 |
| Windows 桌面装备软件（写入 Program Files、注册服务、装驱动） | 仅用于试装验证 | 不适合 | 保持脚本安装 |
| 需要独占硬件的测试软件（串口、CAN、GPIB、PXI、USB 采集） | 不适合 | 仅在设备透传下可行 | 保持脚本安装 |
| 高风险驱动的隔离试验 | 适合（Windows Sandbox / AppContainer / Job Object） | 适合（namespace + seccomp） | 实验性使用，不进正式链路 |

判断依据只有一条：**是否直接操作硬件**。容器与沙盒隔离的是文件系统、注册表与进程视图，隔离不了「谁独占这台仪器」。

### 11.2 容器化的映射关系

若对纯软件服务引入容器，字段映射如下：

| 现有概念 | 容器方案 |
| --- | --- |
| `package`（object@version） | 镜像仓库地址 + tag，执行时锁定 digest |
| `entry`（部署脚本） | 镜像 ENTRYPOINT / 覆盖 command |
| `workdir` | 挂载目录（配置、数据、日志） |
| `probe` | HEALTHCHECK 或 `docker inspect` 状态 |
| `mode=ensure` | 比较运行中容器镜像 digest 与目标 digest |
| 部署记录 | 记录 digest、容器 ID、启动时间 |

manifest 需增加 `deploy.kind = script | container`：script 走现有流程，container 走镜像拉取与容器生命周期，两条分支共用 TPS 字段（`package`、`target`、`mode`、`on_failure`、`depends_on`）不变。

### 11.3 代价与限制

- **Windows 侧**：工控机跑 Linux 容器需要 WSL2/Hyper-V，产线环境不推荐；Windows 容器要求宿主版本匹配、镜像体积大，装仪器驱动仍要落到宿主。
- **硬件透传**：Linux 下需 `--device`、USB/IP 或设备网关；一旦开 privileged，隔离性基本失效，等于用复杂度换形式上的隔离。
- **运维**：容器引入了镜像仓库、运行时、日志采集三套东西，现场排障链路变长；脚本方案只有一个日志文件。
- **升级与回滚**：镜像用 digest 天然支持回滚，比脚本更干净，这是容器唯一的明显优势。

### 11.4 沙盒的正确用法

沙盒适合放在**部署前**而不是部署中：在 Windows Sandbox 或一次性 Linux 容器里执行 `install` + `probe`，验证三件事——脚本可重复执行、无残留副作用、卸载干净。这只证明脚本质量，不证明真机可用，与「仿真通过不等于真机通过」是同一原则。

### 11.5 建议

1. 纯软件服务（Linux）用容器，纳入 `deploy.kind=container` 分支；
2. Windows 装备软件与硬件相关软件保持脚本安装，不做容器化；
3. 沙盒作为部署包的预检手段，产出「可重复执行 / 无副作用」结论，不替代现场验收；
4. 高风险驱动可在沙盒中做隔离试验，验证通过后仍以脚本方式部署到真机。

## 十二、TPS 运行环境的依赖隔离（Windows）

### 12.1 问题

多个 TPS 在同一台工控机上运行，各自依赖的 Python 包版本可能互相冲突（例如 A 要 `numpy 1.26`，B 要 `numpy 2.1`）。共用平台虚拟环境时，后装的一方会覆盖前一方，表现为「昨天能跑的用例今天 import 报错」。容器能隔离，但 Windows 工控机上代价过高，且仪器驱动仍需落到宿主。

### 12.2 方案：按依赖指纹的环境缓存 + 每次运行独立运行目录

核心是两条：**环境按依赖指纹复用，运行现场每次清空**。

1. **声明**：TPS 增加 `runtime` 段

```json
"runtime": {
  "python": "3.12",
  "requirements": ["numpy==2.1.0", "pyserial==3.5"],
  "import_check": ["numpy", "serial"]
}
```

- `requirements` 与 `requirements_file` 二选一；
- `python` 可选，缺省用平台自带版本；现场存在多个嵌入运行时，按版本选择解释器；
- `import_check` 是可选自检项，环境就绪后执行 `import`，失败即判环境不可用；
- 未声明 `runtime` 的 TPS 沿用平台环境，行为与现状一致。

2. **指纹**：`sha256(python版本 + 依赖列表排序 + wheels 目录版本)` 取前 12 位作为 `profile`，同指纹只建一次环境。

3. **缓存**：`backend/runtime_envs/<python>-<profile>/` 存放 venv，只读复用；命中即跳过安装。缓存按 LRU 保留最近 N 套（默认 5），超出删除最旧。

4. **运行现场**：`workspace/<TPS>/run_<task>/env` 是指向缓存的目录链接（Windows 用 junction，Linux 用 symlink），TPS 在该环境下执行；运行结束后删除整个 `run_<task>` 目录，**依赖不残留在系统 Python 与用户目录**。

5. **安装来源**：优先离线 wheel 目录 `backend/runtime_wheels/<python>/`，`pip install --no-index --find-links`；缺失时才联网，并以 `--no-cache-dir` 避免污染用户 pip 缓存。

6. **执行**：用该环境的解释器直接跑 `pytest`，工作目录为 run 目录；平台 SDK（drivers）通过 `PYTHONPATH` 注入，不装进 TPS 环境，避免与 TPS 的依赖版本打架。

### 12.3 为什么不用其他方式

| 方案 | 结论 |
| --- | --- |
| 共用平台 venv | 冲突无法解决，就是当前问题 |
| 每次 `pip install --target` 到 run 目录 | 半隔离：平台包仍可见，同名包遮蔽规则难控；删除靠目录清理，脚本容易被残留文件干扰 |
| conda 环境 | 可行但体积与运维成本高，工控机不装 conda |
| 容器 | Windows 侧代价过高，仪器透传不可行（见第十一节） |
| uv 管理 venv | 值得作为加速项：创建与安装明显快于 pip，P1 阶段可评估替换 |

### 12.4 清理与验收

- 运行结束：删除 `workspace/<TPS>/run_<task>`（含 `env` 链接、临时文件），保留日志与报告副本；
- 运行失败或被强杀：启动时扫描 `run_*` 目录，超过保留期或所属任务已结束的一律删除；
- 缓存清理：超过 N 套按最后使用时间删除；缓存本身只读，不参与运行现场；
- 验收标准：连续跑 A、B 两个依赖冲突的 TPS，各自 import 正确；跑完后 `%TEMP%`、用户 `site-packages`、`run_*` 均无新增残留。

### 12.5 落地顺序

| 阶段 | 内容 | 出口条件 |
| --- | --- | --- |
| P0 | TPS `runtime` 字段与校验；按指纹建 venv 缓存；run 目录 junction；跑完删除 | 两个冲突依赖的 TPS 连续运行均通过，运行后无残留 |
| P1 | 离线 wheels 目录与 `--no-index` 安装；`import_check` 自检 | 断网环境可建环境 |
| P2 | 多 Python 版本选择；缓存 LRU 与磁盘配额 | 不同 Python 版本的 TPS 并存 |
| P3 | uv 加速评估与替换 | 环境就绪时间下降 50% 以上 |

### 12.6 风险

- **首次建环境慢**：在线安装可能 1–3 分钟，需在交付期预置 wheels；现场不允许联网时必须有 wheels 目录。
- **杀毒软件**：venv 创建会触发大量小文件扫描，需把 `runtime_envs` 加入白名单。
- **长路径**：Windows 路径长度限制，缓存目录名要短（`<python>-<hash12>`）。
- **磁盘**：每套环境 30–80 MB，按 5 套估算约 400 MB，需在安装包与运维文档中说明。
